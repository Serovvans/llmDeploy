# LLM-сервис на RTX PRO 5000 72 ГБ

Развёртывание self-hosted мультимодальной LLM (Qwen3.8-27B-FP8 на vLLM) с gateway
Bifrost (API-ключи, лимиты) за Caddy (TLS) на ВМ заказчика и портал сотрудников (чат,
база знаний, прикладные инструменты) на той же ВМ. Источник истины по архитектуре и
решениям — `docs/design.md`; по порталу — `docs/portal-design.md`; сетевые требования —
`docs/devops-request.md`.

## Структура

- `deploy/` — docker-compose, Caddyfile, конфиги Bifrost и мониторинга, `.env.example`.
- `scripts/` — uv-проект: preflight, установка по этапам, смоук-тест, ключи, бенчмарк.
- `portal/` — портал: `backend/` (FastAPI, uv), `frontend/` (React, Kontur UI), `dev/`
  (стенд без GPU с заглушкой модели), `code-sandbox/` (сервис сборки C#, с 0.9),
  `eval/code/` (контрольный набор раздела «Код», с 0.9).
- `docs/` — дизайн, заявка DevOps, runbook, запуск в VPN (`vpn-launch.md`).
- `.claude/agents/` — агенты разработки (ниже).

## Правила проекта

- Образы и зависимости пинятся по версии; `latest` запрещён.
- Наружу только Caddy: порты 443, 8080 (цель проброса из интернета) и 18443
  (`docs/portal-design.md` §3.2). vLLM и Bifrost публикуют порты только на `127.0.0.1`
  (8000 и 8081); сервисы портала портов на хост не публикуют.
- Секреты только в `.env` (в `.gitignore`); в репозитории — `.env.example` без значений.
- Всё, чего нет в `docs/design.md` или `docs/portal-design.md`, сначала вносится в
  дизайн, потом в код.
- Локально GPU нет: проверяем `docker compose config`, линтеры и тесты, портал — на
  стенде `portal/dev/`; всё, что требует GPU, помечаем как «проверить на ВМ».

Общие правила для агентов:
- Агент меняет файлы только в своей зоне. Нужна правка в чужой — описывает её в отчёте,
  оркестратор передаёт владельцу зоны.
- Дизайн-документы (`docs/design.md`, `docs/portal-design.md`) агенты не правят. Пробел
  или противоречие в них — повод остановиться и задать вопрос владельцу проекта.
- Агенты не коммитят и не пушат. Коммит делает оркестратор (основная сессия) после
  зелёных проверок и ревью.
- Каждый исполнитель сам прогоняет проверки своей зоны и в отчёте разделяет «проверено
  локально» и «проверить на ВМ».

## Пайплайн разработки портала

Оркестратор — основная сессия Claude Code: запускает агентов по этапам, передаёт отчёты
между ними, коммитит. Работа идёт в ветке `feat/portal`; в `main` сливает владелец
проекта. Агентов, перечисленных через «∥», запускать параллельно — их зоны не
пересекаются.

| № | Этап | Агенты | Результат | Проверка этапа |
|---|---|---|---|---|
| 1 | Контракт и концепция | `portal-architect` ∥ `ui-designer` | `docs/portal-api.md`, `docs/portal-ui.md` | `reviewer`: согласованность с `portal-design.md` и между собой. **Владелец утверждает оба документа** |
| 2 | Каркас | `backend-engineer` ∥ `frontend-engineer`, затем `infra-engineer` | Проекты бэкенда и фронтенда, миграции, вход, смена пароля, второй фактор (TOTP), управление пользователями, темы, заглушка модели; профиль `portal`, Caddyfile, образы, стенд | Проверки зон зелёные; на стенде можно войти, сменить пароль и настроить второй фактор в обеих темах |
| 3 | Чат | `backend-engineer` ∥ `frontend-engineer` | Чаты, поток, вложения, режимы ответа, история | Тесты; на стенде идёт потоковый ответ, работает остановка |
| 4 | База знаний | `rag-engineer`, затем `frontend-engineer` | Индексация, поиск, источники; экран базы знаний, карточки источников | Тесты; на стенде документ одного пользователя находится другим, личный — нет |
| 5 | Инструменты | `backend-engineer` ∥ `frontend-engineer` | SQL-помощник, помощник CoGIS, разбор документов, экспорт DOCX | Тесты; сценарии инструментов проходят на стенде |
| 6 | Развёртывание | `scripts-engineer` ∥ `infra-engineer` | `install.sh --stage portal`, цели `make`, смоук-тест, бэкап; финальная сверка compose | `make check` зелёный |
| 7 | Приёмка | `qa-engineer` ∥ `security-reviewer` ∥ `ui-designer` (дизайн-ревью) | Сквозные тесты, отчёт по безопасности, список расхождений с концепцией | Все критерии `portal-design.md` §10 без пометки [ВМ] закрыты; блокирующих находок нет |
| 8 | Документация | `docs-writer` | runbook, `vpn-launch.md`, `user-guide.md`, README | `reviewer`: команды в документах совпадают с кодом |
| 9 | Проверка на ВМ | владелец проекта | Запуск по `docs/vpn-launch.md` в VPN, чек-лист [ВМ]; затем домен и проброс порта | Критерии §10 с пометкой [ВМ]. Проброс порта в интернет — только после отчёта `security-reviewer` без блокирующих находок |

Цикл каждого этапа 2–8:

```
1. Исполнители этапа            → проверка: их отчёты, проверки зон зелёные
2. reviewer                     → проверка: вердикт «можно коммитить»
3. Исправления владельцами зон  → проверка: повторный reviewer по исправленному
4. Коммит в feat/portal         → проверка: `make check` зелёный на закоммиченном
```

- Не больше трёх кругов «ревью → исправления» на этап; если блокирующие находки
  остаются, оркестратор останавливается и показывает их владельцу проекта.
- Находки этапа 7 исправляют владельцы зон тем же циклом; после исправлений
  `qa-engineer` и `security-reviewer` запускаются повторно.
- Коммит — один на этап, Conventional Commits: `feat(portal): …`, `test(portal): …`,
  `docs: …`. Без push и без слияния в `main`.
- Изменение контракта после этапа 1 идёт только через `portal-architect`; изменение
  функциональности — только через правку `docs/portal-design.md` владельцем проекта.
- Вопросы к владельцу оркестратор собирает из отчётов и задаёт сразу, не дожидаясь
  конца этапа; этапы, которые от ответа не зависят, продолжаются.

## Пайплайн «Память диалога» (0.7–0.8)

Доработка по `docs/portal-design.md` §5.7 и §13: заполненность памяти модели, учёт пар,
сжатие, перенос, «Продолжить отсюда». Ветка `feat/context` от `main`. Действует общий
пайплайн выше; ниже — его уточнения для этой доработки.

- Этапы ведёт сценарий `.claude/workflows/dialog-memory.js`: Workflow `dialog-memory`,
  `args: {stage: "<код>", notes: "<краткие выводы прошлых этапов>"}`. Оркестратор
  запускает его только по команде владельца, по одному этапу. После этапа оркестратор
  показывает итог и вопросы, затем коммитит.
- Экономия токенов: Sonnet — для механической работы (документация, дизайн-ревью при
  приёмке); отдельный критик — только для рискованных этапов (контракт, реализация,
  безопасность); одно качественное ревью без голосования. Агенты сдают краткие отчёты
  по схеме; повторная проверка смотрит только открытые находки и правки; между этапами
  передаются только выводы (`notes`), а не история.
- Исследование до начала работ (план и карта кода) лежит в `.claude/notes/dialog-memory/`.
  Это справка: где она расходится с `portal-design.md`, прав дизайн.

| Код | Этап | Агенты | Результат | Проверка и остановка |
|---|---|---|---|---|
| `contract` | Контракт и концепция 0.7 и 0.8 | `portal-architect` ∥ `ui-designer` → `reviewer` | `portal-api.md`, `portal-ui.md`: оба релиза в одной редакции, пункты помечены 0.7 / 0.8 | `reviewer` согласовал. **Стоп: владелец утверждает оба документа** |

| `accept-0.8` | Приёмка 0.8 | как `accept-0.7` | Критерии 31–32 и повтор 29–30 | Как `accept-0.7` |

Правила качества (сверх общих):
1. **Одна оценка.** Заполненность для индикатора и сборка запроса к модели считаются одной
   функцией, с одним бюджетом. Тест: «переполнена» тогда и только тогда, когда следующий
   запрос отбросит начало диалога.
2. **Флаг выключен** — запрос собирается как в 0.6, с учётом уже сохранённых выборов
   (§7). Тест.
3. **Пересказ и перенесённое — недоверенные данные.** Они идут только в роли `user`
   через `data_block`, никогда в `system`. Тест на текст с закрывающим тегом и
   инструкцией.
4. **Изоляция.** Каждый новый маршрут фильтрует данные по владельцу. Для каждого
   маршрута есть тест «чужой диалог → 404».
5. **Во время ответа память не меняется:** ответ 409 `generation_in_progress`, тест.
   В 0.8 — не больше одного черновика на сотрудника; при перегрузке модели — 429.
6. **Миграции только добавляют поля**, со значениями по умолчанию. Есть тест `upgrade`
   на базе с данными прежнего релиза. Номер head обновлён в
   `tests/test_migrations_v05.py` и `tests/test_cli.py`.
7. **В журнал пишутся только числа** (оценка, факт, идентификаторы), без текста
   сообщений.
8. **Тексты интерфейса** берутся только из `portal-ui.md`. Русских слов «контекст» и
   «токен» в интерфейсе нет: это проверяется поиском по `portal/frontend/src`.
9. **Панель памяти — скрываемая колонка справа.** Фронтенд проверяет её глазами в
   обеих темах при ширине окна 1280 и 1920 px, в том числе с открытым просмотром
   источника и после перезагрузки страницы.
10. **Тесты — только самые важные:** корректность, безопасность, надёжность. Тестов ради
    покрытия не пишем.
11. **Что зависит от GPU, помечается «проверить на ВМ»:** точность оценки, `usage` от
    Bifrost, задержка пересказа.
12. **Коммиты** — по одному на этап: `docs: контракт и концепция «Память диалога»`,
    `feat(portal): память диалога 0.7`, `test(portal): приёмка памяти диалога 0.7`,
    `docs: релиз 0.7` и так же для 0.8.

Правила качества (сверх общих):
1. **Код не исполняется.** Песочница вызывает Roslyn без MSBuild, анализаторов и
   генераторов; правила и справочник — без загрузки сборок на исполнение. Тест: пакет с
   генератором исходного кода не исполняет его.
2. **Песочница без сети и без секретов портала.** Тест на стенде: исходящее соединение
   из контейнера не устанавливается; в окружении контейнера нет секретов `.env`.
3. **Недоверенное — только данные.** Файлы проекта, сообщения компилятора, схема,
   документы и ответ модели идут модели только в роли `user` через `data_block`,
   никогда в `system`. Тест на файл с закрывающим тегом и инструкцией в комментарии.
4. **Правка не применяется без «Принять».** Путь вне проекта, недопустимое
   расширение и превышение пределов в ответе модели отклоняются; модель не удаляет
   файлы. Тесты.
5. **Изоляция.** Каждый новый маршрут фильтрует по владельцу; тест «чужой проект /
   файл / версия / сборка / архив → 404».
6. **Одна сборка запроса.** Помощник, цикл исправления и контрольный набор используют
   одну функцию сборки запроса и одни промпты из `code_prompts.yaml`; набор не держит
   своих копий.
7. **Память диалога честная.** Файлы проекта, справочник и схема учитываются в той же
   оценке заполненности, что и сборка запроса (правило 1 пайплайна «Память диалога»).
8. **Миграции только добавляют** таблицы и поля; тест `upgrade` на базе с данными 0.8;
   номер head обновлён в `tests/test_migrations_v05.py` и `tests/test_cli.py`.
9. **Флаги.** Раздел «Код» выключен — прежний экран и API помощника CoGIS как в 0.8;
   сборка выключена или песочницы нет — «сборка недоступна», остальное работает. Тесты.
10. **Собственность заказчика не уходит в git и образы**: DLL CoGIS, PDF документации,
    файлы клиента CoGIS. Проверка: `git ls-files` и контекст сборки образов; заглушка
    SDK содержит только имена из инструкции заказчика.
11. **В журнал — только числа и идентификаторы**, без исходного кода, сообщений
    компилятора и текста сообщений.
12. **Тексты интерфейса** — только из `portal-ui.md`, без жаргона: «сборка», «правка»,
    «версия», а не «билд», «патч», «коммит»; слов «контекст» и «токен» по-прежнему нет.
13. **Monaco.** Раздаётся порталом и грузится только в разделе «Код» (основной бандл
    не растёт — сравнение до и после); CSP портала дополняется не больше чем
    `worker-src 'self'`. Экран проверяется глазами в обеих темах при 1280 и 1920 px.
14. **Предпросмотр (1.0)** изолирован: тест, что код во фрейме не читает cookie,
    хранилище и API портала и не делает сетевых запросов.
15. **Тесты — только самые важные:** корректность, безопасность, надёжность.
16. **«Проверить на ВМ»:** совпадение заглушки SDK с DLL CoGIS, качество кода модели,
    установка архива в CoGIS, время сборки и нагрузка на модель.
18. **Инструкции релиза краткие, но полные.** `docs/release-<версия>.md` ведёт от
    работающего предыдущего релиза до принятого нового: все действия по порядку,
    включая внешние (DLL и файлы клиента с сервера CoGIS — откуда и куда, загрузка
    офлайн-набора, включение флага сборки), без чтения других документов. Каждый шаг
    и каждая проверка нужны для работы, отката или критерия [ВМ] этого релиза —
    лишних нет; у шага одна проверка с ожидаемым результатом и действием при
    несовпадении. Приложение «Установка с нуля» — только отличия от `vpn-launch.md`
    с местом вставки. Подробно — в правилах `docs-writer`.
19. **Коммиты** — по одному на этап: `docs: контракт и концепция раздела «Код» 0.9`,
    `feat(portal): песочница сборки C#`, `feat(portal): раздел «Код» 0.9`,
    `test(portal): приёмка раздела «Код» 0.9`, `feat(portal): промпты раздела «Код» по
    замеру`, `docs: релиз 0.9` и так же для 1.0.
