## Часть 1. Руководство по картографическим проектам

## «Руководство по созданию картографических проектов» (CoGIS 13, QGS) → идеи для инструментов портала
Источник: `docs/CoGIS версия 13 - Руководство по созданию картографических проектов (1).pdf`, 138 стр. (печатные номера = PDF).
В основном — символика, подписи и диаграммы QGIS; для SQL, GPTool и JS полезны с. 8–13, 26–27, 38, 58–61, 66, 76–82, 92–97, 107–129.

### 1. Ключевые факты (с номерами страниц)
**База и таблицы**
- Источники данных QGS-проектов: **MSSQL или PostgreSQL/PostGIS** (с. 8).
- Типовая таблица на рисунке 6 (с. 10): `OBJECTID serial` — первичный ключ («OID ключевое поле»), `varchar`, `varchar(50)`, `integer`,
  `double precision`, `date`, `timestamp`, `uuid`. Для MSSQL — ещё `real`. Геометрия: POINT / LINESTRING / POLYGON
  (на рисунке 7 в поле SRID стоит 0). Типы слоёв: точечные, мультиточечные, линейные, полигональные (с. 22).
- У проекта всегда должна быть система координат, вариант «No projection» не поддерживается (с. 13). Растр из PostgreSQL добавляют с пирамидами и тайлом 256×256 или 128×128 (с. 22).
- Типы полей сервера: числа, текст, Дата, Дата и время, GUID, Boolean; домены — только у числовых, строковых и логических
  полей (с. 58–59). **Домены хранятся в QGS-проекте, а не в базе**: в схеме базы видны только коды.
- Значения по умолчанию (с. 59–60): `uuid()` для поля `uuid`/`varchar`; `now()` — дата и время UTC в поле `timestamptz`;
  `to_date(now())` — местная дата в поле `date`; `@user_account_name` — логин или null.
- Объединения таблиц (Join) сервер не поддерживает; связи задаются отношениями (Relations) «один-ко-многим» и «многие-ко-многим» (с. 14–19, 60).
  Для «многие-ко-многим» нужна промежуточная таблица с полями тех же типов, что у ключей, и переменные слоя
  `elitegis_relation_table`, `elitegis_relation_table_published` (с. 16–17, 80).
- Подтипы (с. 76–78): родительское поле — только `smallint/integer/bigint`, дочернее — целое, `text/char/varchar` или `uuid`.
  Фильтр домена дочернего поля — SQL с макросами `{code}` и `{subtype}`, например `{code} like concat('st',{subtype},'%')`.

**Служебные таблицы CoGIS (DDL дан в тексте)**
- Вложения в базе (с. 121–122): для каждого класса объектов отдельная таблица `"<таблица>__ATTACH"` с полями
  `"ATTACHMENTID" serial`, `"REL_OBJECTID" integer`, `"CONTENT_TYPE" varchar(255)`, `"ATT_NAME" varchar(255)`,
  `"DATA_SIZE" integer`, `"DATA" bytea`. Имена полей в верхнем регистре, в PostgreSQL — **только в кавычках**.
  Можно связать по GlobalID: в родительской таблице поле `uuid`/`GlobalID`, во вложениях — `REL_GLOBALID` (все буквы заглавные).
  Если имя таблицы нестандартное, слою вложений задают псевдоним `<псевдоним_родителя>__ATTACH`.
- Вложения на диске (с. 122–123): таблица `elitegis_attachment_groups` (`objectid`, `group_name`, `target_table_name` — имя или шаблон,
  `folder_path`, `is_enabled` 0/1, `target_id_field_name`, `attach_table_name`). Фильтр вложений — `{CurrentUser}`, `{CurrentGroup.<группа>}`;
  отключение — `elitegis_attachments_enabled=false` (с. 124–125).
- История изменений (с. 126): таблица `elitegis_edit_history` с полями `oid`, `id uuid`, `edited_user`, `edited_date date`,
  `target_table_name`, `target_oid integer`, `action_type`, `attributes_data text`. Работает только вместе с правилом SOE.
- Обновление тайлов (с. 127–129): таблица `elitegis_changed_extent_log` и триггер на каждый класс объектов.
  Триггер пишет в таблицу экстент `OLD`/`NEW` и `ST_SRID`; поле геометрии в нём жёстко названо `geom`.
- Отслеживание изменений (с. 66): поля «кто/когда создал/изменил» заполняет **сервер** при правке через сервис;
  имена — переменные `elitegis_edit_tracker_{created,last_edited}_{date,user}_field` или глобальные настройки.

**Ключевое поле**
- У представления (SQL-view) поле идентификатора должно быть **целым** и называться одним из имён `objectid, oid, fid, id,
  rowid, row_id` (регистр не важен); рекомендуется `oid` (с. 95–96). Слой запроса и виртуальный слой тоже
  требуют ключевого поля с уникальными значениями (с. 83–85). У вложений связь по целому `REL_OBJECTID`,
  у истории — по целому `target_oid`.

**Три разных языка «SQL» в проекте**
1. *Фильтр провайдера / определяющий запрос* (с. 26) — условие на языке СУБД.
   Макросы `{CurrentUser}`, `{CurrentGroups}`, `{CurrentGroup.x}`, `{CurrentDate}`, `{CurrentYear|Month|Day}`
   пишутся **в одинарных кавычках**, иначе QGIS не сохранит фильтр (с. 26–27).
2. *Переменные* `elitegis_where_clause` (только часть после WHERE, объединяется с другими условиями через AND; с. 96)
   и `elitegis_query` (полный SQL-запрос слоя; набор и типы полей должны совпадать с полями слоя; с. 81).
   Макросы: `{WhereClause}`, `{WhereClause:<условие по умолчанию>}`, `{AttributeFilter}`, `{SpatialFilter}`, `{TimeFilter}`,
   `{IsUserLoggedIn}`, `{CurrentUserFullName}`. `{CurrentGroups}` имеет вид `;g1;g2;` (с. 81–82, 96).
   Подзапросы в SQL-фильтрах запрещаются `elitegis_sql_subqueries_allowed` или глобально; итоговый фильтр слоя можно проверять
   регулярным выражением `elitegis_where_clause_regex_check` — не прошёл, данных нет (с. 107).
3. *Выражения QGIS* — подписи, отображаемое имя, символика по правилам, data-defined, диаграммы. Сервер понимает
   только ~40 функций: `concat, coalesce, substr, lower, upper, round, floor, scale_linear, to_string, now, date_part, replace…`
   (с. 38; у геокодера ещё `format_date`, с. 114; у времени — только `to_interval`, с. 63); `$area`, `$length`, `@map_scale`, `@cluster_size` (с. 47, 55, 68).
   Имена полей — в двойных кавычках: `concat("city",' ',"street")` (с. 114). **Целое, делённое на целое, даёт 0** — делите на `100000.0` (с. 45).
   Отображаемое имя может быть выражением, но тогда полнотекстовый поиск по нему не работает (с. 114).

**Номера слоёв, сортировка, исключение слоя**
- Номера слоёв сервис назначает сам, и они меняются при правке проекта; закрепляет номер `elitegis_layer_id` (с. 92).
- Также: `elitegis_features_order_by` (поле ASC/DESC), `elitegis_ignore` (с. 97), `elitegis_order_by_field_mappings` (с. 108).
- «Подмена источника» (с. 94–95): слой показывает представление, а правки идут в исходную таблицу
  `elitegis_view_source_table` (`schema.table`) и в поля `…_geometry_field`, `…_oid_field`, `…_spatial_reference`.

**Геокодирование (с. 109–120)**
- Только PostgreSQL. GIN-индекс на поля поиска: `CREATE INDEX ON public.buildings USING gin(to_tsvector('russian', COALESCE(city,'') || ' ' || COALESCE(street,'') || …));`.
  В слое оставляют только `primary_key` и поля поиска в **том же порядке**, что и в индексе. Тот же порядок
  должен быть в декларации сервиса (с. 113, 118).
- Переменные: `elitegis_geocode_search_fields` (поля поиска через запятую), `_replacement_exact`, `_replacement_words`
  (`ул=улица;пр-т=проспект;…`), `_score` (по умолчанию 100), `_score_bonuses`, `_coordinates_search`,
  `_replacement_regexes_<пара>_from/_to` (с. 114–116).

### 2. Предложения (по убыванию пользы)
1. **База знаний — загрузить руководство администратором** (без кода).
   Зачем: помощник CoGIS, раздел «Код» и чат получат `<база_знаний>` по переменным `elitegis_*`, служебным таблицам, геокодеру и вложениям.
   Эффект: ответы со ссылками [n] вместо «по общим знаниям». Риск: в скриптах руководства есть ошибки
   (раздел 3), модель может их скопировать. Поэтому вместе с загрузкой нужно предложение 2 — строка про проверку синтаксиса.
2. **SQL-помощник — абзац «Особенности CoGIS» в `app.yaml → sql.system_prompts` (write, debug, optimize).**
   Текст примерно на 8 строк:
   - ключ слоя и представления — целое поле `oid`/`objectid`/`fid`/`id`/`rowid`/`row_id`;
   - таблицы `"<t>__ATTACH"` и их поля в верхнем регистре — в двойных кавычках; вложения связаны с объектом по `"REL_OBJECTID"` = ключ объекта;
   - `elitegis_*` — служебные таблицы CoGIS, без просьбы их не менять;
   - коды доменов расшифровываются в проекте CoGIS, а не в базе: значение кода — спроси;
   - фильтр слоя — только условие после WHERE, без подзапросов (их могут запретить), макросы `'{CurrentUser}'` — в одинарных кавычках;
   - в DDL для CoGIS — `geometry(<тип>, <настоящий SRID>)`, не SRID 0; время — `timestamptz`;
   - в примерах документации CoGIS бывают ошибки, пиши по правилам PostgreSQL (`uuid`, а не `guid`).
   Зачем: схема из подключения (§5.8) покажет `__ATTACH`, `elitegis_*` и коды доменов, а без контекста модель их не поймёт.
   DDL песочница не исполняет (§5.3), значит, ошибки DDL ловит только модель.
   Эффект: правильные запросы к вложениям и представлениям с первого раза. Риск: длиннее системное сообщение (~150 токенов, учитывается в памяти); текст — общий для всех диалектов, а PostgreSQL сейчас единственный.
3. **Раздел «Код», GPTool — дополнить `gptool_rules` или `system.write` (`code_prompts.yaml`).**
   - Правка таблиц слоя прямо через Npgsql идёт **мимо сервера CoGIS**: поля отслеживания изменений (с. 66) и
     история SOE (с. 126) не заполнятся. Если в `<схема>` есть поля вида `created_user`/`last_edited_date`, заполняй их сам или спроси имена.
   - Тайлы обновятся, только если на таблице есть триггер `elitegis_changed_extent_log` (с. 127).
   - Геометрию приводи к SRID столбца из `<схема>`: `ST_Transform(ST_SetSRID(…,4326), <SRID>)`.
   - Новый объект получает ключ из `serial`; вложение — строка в `"<t>__ATTACH"` со всеми NOT NULL полями.
   Эффект: инструменты, которые правят данные, не ломают историю и кэш. Риск: правило выводится из руководства,
   прямо там не написано — нужно сверить на ВМ (возможно, у заказчика это делают триггеры). Нужен прогон контрольного набора «было → стало».
4. **JS-плагины — `api.d.ts` (JSDoc) и `web.system.write`.**
   - У `searchInLayer` и `addFilterToLayer`: «whereClause — условие SQL без слова WHERE; строки в одинарных кавычках;
     подзапросы сервер может запретить, а фильтр — отклонить по шаблону (настройки проекта CoGIS); objectIds — целые значения ключевого поля».
   - У `getLayer`: «номер слоя меняется при правке проекта, если в нём не задан `elitegis_layer_id`».
   - У `geocodeAddress`: «результат зависит от настроек геокодера в проекте (поля поиска, замены сокращений)».
   Эффект: меньше плагинов, которые молча ничего не находят. Риск: что фильтр плагина проходит проверки с. 107 — предположение [ВМ];
   `api.d.ts` меняется через контракт (§7.5.16) — `portal-architect`.
5. **Шаблон `templates/plugin.js`** — к строке `var layerId = 0;` добавить комментарий: «номер слоя смотрите в сервисе;
   чтобы он не менялся, в проекте QGIS задают слою переменную elitegis_layer_id». Это одна строка, риска нет.
6. **SQL-помощник — выражения QGS** (подписи, отображаемое имя, стиль по правилам).
   В prompt `write` добавить фразу: если просят выражение для подписи или стиля проекта CoGIS — это язык выражений QGIS,
   с функциями только из списка с. 38, с полями в `"…"` и с целочисленным делением.
   Отдельный диалект не нужен: `sqlglot` такие выражения не разберёт, поэтому новый режим потребует правки дизайна — РЕШЕНИЕ(человек).
   Эффект: модель не подставит PostGIS-функции в подписи. Риск: путаница режимов, если формулировка нечёткая.
7. **Контрольный набор `portal/eval/code/tasks.yaml`** — 2–3 задачи «как в CoGIS»: число вложений объекта по `"<t>__ATTACH"`;
   инструмент, который пишет объект с полями отслеживания; представление с ключом `oid`. Сейчас схемы набора не похожи на CoGIS:
   `parcels` с текстовым ключом, `bigserial`, нет `__ATTACH`. Эффект: замер предложений 2–3. Риск: набор растёт, нужен прогон на ВМ.
8. **Снимок схемы (1.0) — помечать служебные таблицы CoGIS** (`elitegis_*`, `*__ATTACH`) в списке выбора таблиц
   и по умолчанию не предлагать `"DATA" bytea` для образца. Двоичные данные уже не копируются (§5.8), так что польза небольшая,
   а для пометки нужна правка дизайна — РЕШЕНИЕ(человек).

### 3. Противоречия и неточности
**Внутри руководства** — важно, если загрузить его в базу знаний:
- с. 121–122: `CONSTRAINT <schema>."<t>__ATTACH" PRIMARY KEY` — имя ограничения нельзя указывать со схемой.
  К тому же оно совпадает с именем таблицы, и индекс с таким именем не создастся. Это синтаксическая ошибка PostgreSQL.
- с. 122: тип `guid` — в PostgreSQL его нет, нужен `uuid`.
- с. 129: `ON '<my_schema>.<my_featureclass>` — лишняя кавычка. `EXECUTE PROCEDURE <schema>.elitegis_changed_extent_log()` вызывает
  имя таблицы вместо функции `set_data_to_extentchangelog()`. Поле `geom` зашито в код триггера.
- с. 10 (рис. 7): SRID 0 в примере противоречит требованию задавать систему координат (с. 13).
- с. 38, 114: `cailing` — видимо, опечатка `ceiling`/`ceil` (проверить на сервере); с. 81, 85: типографские кавычки `’default’`, `“myschema”` ломают SQL.

**С файлами портала**
- `code_prompts.yaml` (GPTool): «обычно это Npgsql для PostgreSQL». В руководстве поддерживается и MSSQL (с. 8),
  а `sql.dialects` и подключения 1.0 — только PostgreSQL. Это не ошибка, если у заказчика только PostgreSQL. Надо подтвердить — РЕШЕНИЕ(человек).
- `templates/plugin.js` и `web.system.write` подразумевают, что номер слоя постоянный, а по с. 92 он меняется без `elitegis_layer_id` (предложение 5).
- `web.system.write`: «whereClause — выражение SQL по полям слоя» — верно, но не сказано про запрет подзапросов
  и проверку регулярным выражением (с. 107; предложение 4).
- `code_prompts.yaml` (GPTool, правило 6) и `AddContactTool.cs` пишут прямо в таблицы через Npgsql без оговорки про
  отслеживание изменений, историю и кэш тайлов (с. 66, 126–127; предложение 3).
- Схемы `portal/eval/code/tasks.yaml`: ключи `bigserial` и текстовые не совместимы с целыми `REL_OBJECTID`/`target_oid` CoGIS (с. 121, 126).
- Подтверждается (не противоречие): `cogis-js-html.md` («в РП-QGIS JS и HTML нет»); ключ `id` придуманного слоя предпросмотра допустим (с. 95).

### 4. Чего в руководстве нет
- Соглашений об именах таблиц, схем и полей геометрии (кроме `__ATTACH`, `elitegis_*`, имён ключа у представлений),
  рекомендуемых SRID, требования индекса GiST.
- На каком диалекте `whereClause` в JS API и `{AttributeFilter}` — PostgreSQL или MSSQL, проходит ли фильтр плагина
  проверки с. 107; формата адреса сервиса и номеров слоёв REST.
- Типов полей отслеживания изменений, формата `attributes_data` и `action_type` в истории, способа генерации GlobalID.
- Чего-либо о GPTool, JS, HTML и SDK: это есть только в «Руководстве по созданию картографических приложений».
  Модели геообработки и печати описаны в «Руководстве по публикации ГИС-сервисов», которого в наборе нет.
- Особенностей MSSQL, кроме `real` и доверенного соединения (с. 9–10).

## Часть 2. Отчёты, правила SOE, геотриггеры, сверка api.d.ts

## РП2 и «Описание платформы»: что полезно инструментам портала

Стр. — номер страницы PDF (печатный = PDF + 499). РП2 — «Руководство… часть2», ПП — «Описание платформы».

### 1. Ключевые факты

**Отчёты (п. 7.8, РП2 стр. 1–60)** — самый большой «язык», который пишут сотрудники.
- Шаблоны DOCX/XLSX; макросы в фигурных скобках — в тексте ячейки, в «Теге» элемента управления содержимым Word, в «Замещающем тексте» рисунка (`{Map1.Image}`, `{Map1.Scale}`), стр. 1–5, 20, 29.
- Грамматика макроса: `{Source.Rows.field}`, `{Source.Rows.N.field}`, `{Source.Stat.Sum.field}`, `{Source.Rows.Attachments.Name}`, группы `{Source.Groups.G.N.Data.Groups.G1.N1.Macros}`; служебные `__CentroidX`, `__Coordinates.x/y/pointNumber/directionToPoint/lengthToNextPoint…`, `__Index`, `__DisplayName` (табл. 11–14, стр. 8–11, 49–51).
- Форматы: `::F4`, `:ru:F2`, `::DMS`, `::F4:DMS`, `:ru:F4:DDMS`, `::dd.MM.yyyy`, `::code`/`::value`, обрезка `[0..20]`, пусто → `?? текст` или `=текст` (стр. 6–7, 9, 19).
- Управление таблицей в «Замещающий текст → Описание»: `3=Buildings.Rows`, `3=Buildings.Rows[0..6]`, `2,3=Buildings.Rows{3=Attachments}`; видимость `if=`/`ifnot=` с операторами `> < = != <> ~ ~*` и арифметикой; одна запись строк и одно условие на таблицу (стр. 21–25).
- Настройки отчёта: параметры 6 типов (строка, целое, дробное, да/нет, дата, дата и время), справочник «вручную / из атрибута слоя с SQL-фильтром / из домена», описание параметра — HTML (стр. 36–39); источник «слой/таблица» с фильтрами из параметров и дочерним отчётом (стр. 41–44); картматериал с экстентом по SQL-фильтру `ID={CurrentFeature.ID}` (стр. 45–47); пример фильтра `oid={CurrentFeature.oid}` (стр. 27); имя выходного файла с макросами (стр. 34); ЭЦП, «прикрепить к объекту» (стр. 34–36).

Постобработка: внешний процесс с `{ReportFolder}`, `{ReportName}`, `{ReportExtFile}`, `{PublicCertFile}`… (стр. 53–57); инструмент геообработки: `{ReportPath}`, `{Source}` → JSON для параметра Таблица/Слой или файл .json, `{Source.Attachments}` → zip, `{Map}` → png (табл. 15, стр. 57–59).

**Правила SOE (разд. 8, стр. 71–171)** — не код, а настройки в GUI администратора, хранятся XML-файлами (экспорт/импорт XML, стр. 71, 76, 88). 8 типов плагинов (Редактирование, Ограничение на просмотр, История, Загрузка/выгрузка, Галерея, Подсчёт, Расширенный поиск, Плагин администратора — последний не описан), стр. 74–75. Плагины и геотриггеры читаются снизу вверх, побеждает нижний (стр. 76, 88).
- Что сотрудник **пишет руками**: (а) «Определяющий запрос» — SQL-условие `Status = 'Выполнен'`, `Length > 20` почти в каждом плагине и геотриггере (стр. 80, 92, 154, 169); (б) «Условие на разрешение операций» — таблица БД + запрос (стр. 77); (в) расчётные выражения геотриггеров `[AREA] / 10000`, `Object.Shape.X` с выбором «интерпретатора» (какие — не сказано), стр. 99, 103, 116; (г) макросы значений по умолчанию `{CurrentUser.LastName}` (стр. 82) и шаблоны писем (табл. 18, стр. 121–125); (д) SQL-команда геотриггера «Вызов SQL-команды» — произвольный SQL в БД слоя с контекстом объекта, время запуска до/после обновления/после транзакции, нельзя обновить текущий объект (стр. 135–140; сам пример SQL только на рисунке 620).
- Порядок обработки: проверки плагина → новое состояние → геотриггеры каскадом → «Ограничения после редактирования» → коммит; условия «на исходное / изменяемое состояние» (стр. 83–87).
- Геотриггер «Вызов задачи геообработки»: URL, task, входы из полей и макросов, выходы в поля `{OutputFeatureLayer.N.myfield}`, `{prop.N.prop1}`, `{output_param.N}` (стр. 140–147). «Вызов .NET метода»: путь к DLL, класс с namespace, **статический** метод, аргументы, поля для записи результата, таймаут; сигнатура не описана (стр. 147–152).

**Задачи по расписанию (разд. 9, стр. 172–189)**: обновление объектов слоя (с геотриггерами), геообработка (разово или по объекту), отчёт, проверка сервиса, сторонний процесс; везде атрибутивный SQL-фильтр и макросы `{CurrentFeature.f::F2}`, `{CurrentFeature.f}+1`, `{ErrorMessage}`, `{LastSuccess}`, `{FirstDateOfCurrentMonth}` (табл. 19–20, стр. 178–179). Приложение А — общий список макросов (стр. 190–191).

**ПП**: СУБД источников — PostgreSQL/PostGIS, Postgres Pro, Pangolin SE, MS SQL Server, Oracle (стр. 24) → диалект определяющих запросов = диалект базы слоя (вывод). Типы параметров моделей геообработки — 18: Int, Double, Bool, String, Date-Time, File, Geometry, Coordinate System, SQL-expression, Workspace, Table, Standalone Table, Feature Class, Feature Layer, Map, Image/Tile/Dynamic Service (стр. 20–21). Сервисы: ArcGIS REST MapServer/FeatureServer 10.x, WMS 1.3.0, WMTS, WFS 2.0, TMS; сетевой анализ на TrueDrive (стр. 19, 22). Интеграция: HTTP/REST, прямое подключение к БД (стр. 28).

**Расхождения самой документации в макросах** (важно для помощника и ответов RAG):
- пусто → `{myfield=Не определено}` (стр. 7) и `{… ?? Не определено}` (стр. 19);
- формат через `:` (`{myfield:dd'.'MM'.'yyyy}`, `{MyField:ru:F4}`, стр. 6–7) и через `::` (`{…::F4}`, `{CurrentDate::dd-MM-yyyy}`, стр. 9, 19);
- фамилия: `{CurrentUser.LastName}` (стр. 40, 82) и `{CurrentUserLastName}` (стр. 190);
- геотриггеры: `Object.ID`/`Objects.Caption` (табл. 17, стр. 105) и `Object.Id`/`Object.Caption` (табл. 18, стр. 123); у `Object.CaptionBeforeUpdate` написано «после изменения» (стр. 123) — вероятно опечатка;
- `{CurrentDay}` в примере `if=` отчёта (стр. 25), но в табл. 11 его нет (есть в табл. 17, 19); сдвиг без суффикса `{CurrentDate-2}` описан только для задач по расписанию (стр. 178).

### 2. Ошибки и пропуски в `api.d.ts`, шаблонах и промптах (п. 7.9–7.10)

`api.d.ts` уходит модели как `<описание_api>` (code_prompts.yaml, `web`), поэтому обязательность параметров влияет на код модели; в Monaco семантика отключена (`web.ts:17`), красных подчёркиваний нет.
1. Объявлены обязательными, хотя по документации необязательны (нотация `=значение` или пример без аргумента):
   - `goTo(geometry, maxScale, minScale, …)`: «необязательный минимальный и максимальный масштаб», пример `api.goTo(point)` (стр. 66, 68) → `maxScale?`, `minScale?`;
   - `getLayer(serviceUrl, layerId, existsIn)`: `existsIn=map/legend/search/attributeTable`, примеры `api.getLayer(url, 0)` (стр. 66, 68–69) → `existsIn?`; шаблон `plugin.js` передаёт `"map"` — допустимо, но модель будет считать аргумент обязательным;
   - `showPushpin(geometry, icon)`: `icon=Иконка по умолчанию или заданная по URL` (стр. 66) → `icon?`;
   - `geocodeAddress(address, filters)`: `filters={…}` (стр. 66) → `filters?`;
   - `createColor(r, g, b, alpha)`: пример `api.createColor(255, 2, 2)` (стр. 67) → `alpha?`; в JSDoc — диапазон из примера `0.5` (0–1);
   - `createSimplePointSymbol(color, size, outline, type)`: пример с двумя аргументами (стр. 67) → `outline?`, `type?`;
   - `searchInLayer(layer, whereClause, objectIds, geometry)`: шаблон `plugin.js` зовёт с двумя — `objectIds?`, `geometry?` (документация прямо не говорит; согласовать d.ts с шаблоном).
2. Смысл: `identify` — «имитация щелчка по координате» (стр. 67), а в d.ts «в точке или области»; `openIdentify` — «для ранее найденного объекта» (результат `searchInLayer`), в d.ts нет; `showPushpin` — метка исчезает при сдвиге или смене масштаба (стр. 66), в d.ts нет.
3. `generateReport(template, source, options)`: нет описания полей — `template` — имя файла шаблона `.docx/.xlsx` из папки шаблонов (стр. 32, 69), `source` — `{serviceUrl, layerId, whereClause, orderBy}`, `options` — `{Caption}` (смысл Caption не описан). Добавить JSDoc и `@example` из стр. 69.
4. Нет `@example` у `constructServiceArea`/`findRoute` (`'Geodesic_Length'`, `[3, 6]`, `['Car']`, стр. 67) — для модели это единственная подсказка, какие значения `cost`/`restrictions` бывают.
5. Хук `onCesiumKmlInit(kmlLayer)` (п. 7.9.2, стр. 63–64) не объявлен в `Window`, а промпт `card_hooks` утверждает «хуков три… других CoGIS не вызывает» — неверно в общем виде (этот хук задаётся через HTML-кастомизацию, а не `\Customer\openProject\`). Промпт `catalog` его тоже не знает.
6. Промпт `catalog` и вид «Кастомизация Каталога карт»: по стр. 61 кастомизация задаётся «для элементов картографического приложения или папки», то есть и для карт, не только для Каталога; применение «по иерархии» — только у папок. Пропуск формулировки; доступен ли `api` в кастомизации карты — неизвестно.
7. Шаблоны: `card-hooks.html` возвращает список ошибок `ko.observable(errors)`, документация — `ko.observable` со списком без `null` (стр. 64–65) — совпадает. `widget.html` и `catalog.css` повторяют примеры верно. Расхождений с документацией нет, кроме п. 1.

### 3. Предложения (по убыванию ценности)

1. **SQL-помощник: режим «Условие для CoGIS»** (`app.yaml` → `sql.system_prompts`, новое действие или переключатель). Что: модель пишет не запрос, а условие WHERE для определяющего запроса, SQL-фильтра отчёта, задачи по расписанию, `searchInLayer` — с макросами `{CurrentFeature.поле}` там, где они допустимы. Проверка: портал оборачивает условие в `SELECT * FROM <таблица> WHERE …`, подставляет вместо макросов значения образца и прогоняет в той же песочнице/sqlglot. Почему: такие условия сотрудники пишут чаще всего (стр. 27, 38, 46, 77, 80, 154, 169, 181–184), а нынешние промпты просят «один запрос». Эффект: правильные фрагменты без ручной обрезки, проверка на тестовых данных работает и для них. Риск: диалект слоя может быть MS SQL/Oracle (ПП стр. 24) — проверка только для PostgreSQL; набор допустимых макросов в каждом месте разный. **Нужна правка §5.3 дизайна.**
2. **Справка по макросам и отчётам в базе знаний** (действие администратора + контрольные вопросы RAG у `rag-engineer`). Загрузить оба PDF; таблицы макросов при извлечении текста рвутся по ячейкам (табл. 11–20 многострочные), поэтому добавить к ним короткую выверенную справку `.md` «макросы CoGIS по местам применения» с перечнем расхождений из §1. Эффект: ответы чата «как вывести координаты поворотных точек в отчёт», «почему не срабатывает геотриггер» опираются на точный синтаксис. Риск: справка отстанет от версии CoGIS; держать ссылки на страницы. Дизайн менять не нужно.
3. **Исправить `api.d.ts` и промпты по §2** (`code_web/api.d.ts`, `code_prompts.yaml` → `web.kinds.card_hooks`, `catalog`). Дёшево, точечно; эффект — модель не выдумывает `maxScale`/`existsIn`, знает поля `generateReport` и хук 3D. Риск минимальный; контракт `portal-api.md` §7.5.16 описывает файл, состав функций не меняется (только `?` и JSDoc, плюс `onCesiumKmlInit` в `Window` — через `portal-architect`).
4. **Вложения чата: разрешить `.xml`** (`chat.attachment_extensions`). Почему: всё, что сотрудник настраивает в GUI CoGIS — правила SOE, шаблоны геотриггеров, отчёты, кастомизации, задачи по расписанию, — выгружается в XML (стр. 36, 62, 70, 76, 88, 173). Тогда «объясни/проверь мою настройку» работает в обычном чате с опорой на базу знаний (порядок «снизу вверх», пустое поле «Сервис», условия до/после обновления). Риск: формат XML не описан — модель объясняет по именам элементов; файл только текст (без разбора XML, XXE нет); может содержать логины/пароли (стр. 145, 180 — «шифровать логин-пароль» опционален) — предупреждать в интерфейсе. **Нужна правка §5.1 дизайна** (там форматы перечислены: изображения, PDF, DOCX, TXT/MD).
5. **«Код», GPTool: контекст вызова инструмента** (мастер `wizard.yaml` + `code_prompts.yaml`). Инструменты сотрудников вызываются не только кнопкой: постобработка отчёта (вход File = `{ReportPath}`/`{Source}` JSON/`{Map}` png, стр. 58), геотриггер (выходы пишутся в поля через `{output_param.N}`, `{OutputFeatureLayer.N.field}`, стр. 145–146), задача по расписанию по каждому объекту (входы из `{CurrentFeature.f}`, массив — многострочное поле, стр. 182–183). Предложение: поле мастера «Где будет вызываться» → подсказка модели о формате входов/выходов и памятке установки. Плюс расширить типы мастера File, Geometry, SQL-expression, Feature Layer/Table после сверки с DLL (А-103, ПП стр. 20–21). Риск: имена C#-типов этих параметров не описаны — только [ВМ]. **Нужна правка §5.4.**
6. **Новый инструмент (кандидат): помощник шаблона отчёта.** Сотрудник описывает отчёт и источники (имя, поля из подключения §5.8) → модель выдаёт таблицу «где что вписать»: теги элементов управления, текст ячеек, запись «Замещающий текст → Описание» (`2,3=Src.Rows{3=Attachments}`, `if=`), макросы групп; детерминированный линтер проверяет синтаксис макроса (форматы, `[k..l]`, `??`, имена источников и полей) по грамматике из §1. Дальше — генерация готового `.docx` с элементами управления содержимым (экспорт DOCX в портале уже есть). Почему: 60 страниц документации, отчёты — «одна из серьёзных функциональных возможностей» (стр. 184), ошибка в макросе видна только после генерации в CoGIS. Риск: раздел XLSX-шаблонов 7.8.2.1–7.8.2.5 в наборе отсутствует; расхождения документации в синтаксисе (§1) — линтер должен принимать оба варианта до проверки на ВМ. **Новый раздел — правка дизайна владельцем.**
7. **Новый инструмент (слабее): метод для геотриггера «Вызов .NET метода»** — вид проекта C# «статический метод» (стр. 147–152) в той же песочнице. Отложить: сигнатура, типы аргументов и возврата, версия .NET не описаны; нужен рабочий пример у заказчика. То же для DLL предобработки отчёта (стр. 48).
8. **Помощник правил SOE как отдельный инструмент — не предлагаю**: правила — GUI-настройки, единственный «код» в них — SQL-условия, расчётные выражения и макросы; их покрывают п. 1, 2, 4.
