# Развёртывание с доменом: сертификат и доступ из интернета

Пошаговая инструкция: от DNS-записи до работающего адреса `https://llm.<домен>:18443`.
Делается один раз. Решения и схема — `docs/portal-design.md` §3.2; проверки перед
открытием доступа сотрудникам и после — `docs/vpn-launch.md`, часть B.

Все команды, кроме отмеченных, выполняются на ВМ из каталога `/opt/llm`. Пометка
**[ВМ]** — шаг не проверялся вживую, результат подтвердить при первом запуске.

## Исходные данные

| Что | Значение |
|---|---|
| Поддомен | `llm.<домен>` — в командах ниже подставьте своё имя |
| Внешний IP | `195.122.229.203` |
| ВМ | `192.168.25.8`, репозиторий в `/opt/llm` |
| Проброс (настраивает сисадмин) | TCP `195.122.229.203:18443 → 192.168.25.8:8080` |
| Адрес портала | `https://llm.<домен>:18443` |
| Адрес API | `https://llm.<домен>:18443/v1` |

Порты ВМ: Caddy слушает 443, 8080 и 18443 — на всех один и тот же сайт. Админ-порт
Bifrost — `127.0.0.1:8081`, vLLM — `127.0.0.1:8000`; наружу они не открыты.

Что нужно иметь на руках:

- имя поддомена и доступ к панели, где ведётся DNS-зона домена (Timeweb);
- API-токен Timeweb Cloud с правом управления DNS-зоной домена — только если домен
  добавлен в панель Timeweb Cloud; для домена на виртуальном хостинге Timeweb токена
  нет, сертификат выпускается с `MANUAL=1` (шаг 1);
- e-mail для учётной записи Let's Encrypt;
- доступ к ВМ по SSH с `sudo`;
- исходящий доступ с ВМ по HTTPS к Let's Encrypt и к API Timeweb Cloud
  (`docs/devops-request.md` §1.4) — без него `make cert` и продление не работают;
- пройденный этап 1 (`make model`, `docs/runbook.md` §2.3) — он создаёт `deploy/.env`.

## 1. DNS-запись

В панели Timeweb создайте A-запись `llm.<домен>` → `195.122.229.203`.

Проверка (с любой машины):

```bash
dig +short llm.<домен>          # ожидается: 195.122.229.203
dig +short NS <домен>           # кто обслуживает зону
```

Автоматический выпуск и продление сертификата работают, только если домен добавлен в
панель **Timeweb Cloud** (`timeweb.cloud`): токен API создаётся там и управляет только
её зонами. Одних NS-серверов Timeweb для этого мало — виртуальный хостинг Timeweb
(`hosting.timeweb.ru`) использует те же NS, но API-токенов для DNS в его панели нет.

Определите свой случай по панели, в которой создавали A-запись:

| Где ведётся домен | Как выпускать сертификат |
|---|---|
| Timeweb Cloud | Автоматически: токен в `deploy/.env` (шаг 2), `make cert` |
| Виртуальный хостинг Timeweb | Вручную: `make cert MANUAL=1` (шаг 3), токен не нужен, продление раз в 60 дней (шаг 8) |
| Другой провайдер DNS (NS чужие) | Так же вручную: `make cert MANUAL=1` |

Сертификат «SSL Let's Encrypt» из раздела «SSL-сертификаты» панели хостинга не
подходит: он ставится на сайт, размещённый на серверах Timeweb, а поддомен указывает на
наш IP и к сайту не привязан. Заказывать и покупать сертификат в панели не нужно.

Чтобы перейти на автоматическое продление, домен нужно перенести из аккаунта хостинга в
аккаунт Timeweb Cloud — через поддержку Timeweb; после переноса заполните токен (шаг 2)
и выполните `make cert`.

- Если не так (A-запись): запись ещё не разошлась — подождите и повторите.

## 2. Переменные в `deploy/.env`

```bash
sudoedit deploy/.env
```

| Переменная | Значение |
|---|---|
| `LLM_HOSTNAME` | `llm.<домен>` — доменное имя, не IP. Вписать до `make cert` |
| `ACME_EMAIL` | контактный адрес учётной записи Let's Encrypt |
| `TIMEWEBCLOUD_AUTH_TOKEN` | токен API Timeweb Cloud; при `MANUAL=1` оставить пустым |

Токен создаётся в панели Timeweb Cloud, раздел «API и Terraform». Он даёт управление
DNS-зоной: тот, кто его украдёт, сможет перенаправить домен и
выпустить на него чужой сертификат. Выдавайте токен с минимальными правами, если панель
это позволяет (только DNS или отдельный проект под этот домен), и храните только в
`deploy/.env` (root, 600).

Писем об истечении срока на `ACME_EMAIL` не приходит: за продлением следит таймер (шаг 4).

- Если не так: `make cert` на следующем шаге сам назовёт пустую или неверную переменную.

## 3. Выпуск сертификата

```bash
make cert                 # домен не в Timeweb Cloud: make cert MANUAL=1
```

Проброс порта для этого не нужен: владение доменом подтверждается записью в DNS, её
создаёт и удаляет сама команда.

При `MANUAL=1` запись добавляете вы **[ВМ]**:

1. Команда показывает имя `_acme-challenge.llm.<домен>` и значение TXT-записи и ждёт
   Enter. Не нажимайте его и не закрывайте терминал.
2. В панели, где ведётся домен, добавьте TXT-запись с этим именем и значением. В панели
   хостинга Timeweb: «Домены и поддомены» → настройки DNS домена → добавить запись типа
   TXT. Если панель не даёт задать такое имя — обратитесь в поддержку Timeweb.
3. С другой машины дождитесь, пока запись станет видна:

   ```bash
   dig +short TXT _acme-challenge.llm.<домен>      # ожидается: значение из шага 1
   ```

4. Нажмите Enter. После выпуска команда попросит удалить запись — удалите её в панели.

Ожидаемый результат — строка «сертификат разложен: …» с датой окончания срока и файлы:

| Где | Что |
|---|---|
| `deploy/certs/fullchain.pem`, `deploy/certs/privkey.pem` | сертификат с цепочкой и ключ — их читает Caddy |
| `deploy/lego/` | состояние ACME-клиента: ключ учётной записи Let's Encrypt, выпущенные сертификаты и их ключи |

`deploy/lego/` и токен в `deploy/.env` — секреты. В репозиторий и в копию `make backup`
они не входят: сохраните их отдельно, в хранилище секретов, как и сам `deploy/.env`.

- Если не так: причина — в выводе выше строки «lego завершился с ошибкой». Обычно это
  неверный токен или домен не в Timeweb Cloud (тогда `make cert MANUAL=1`); при
  `MANUAL=1` — TXT-запись ещё не разошлась или добавлена не под тем именем.
  Работающий сертификат и Caddy при сбое не тронуты; команду можно повторять.

## 4. Запуск

```bash
make gateway LLM_HOSTNAME=llm.<домен> TLS_MODE=corp
```

Если профиль `embeddings` ещё не включён, а портал нужен — добавьте
`PROFILES=embeddings`. `PROFILES` заменяет набор дополнительных профилей целиком: если
мониторинг уже включён, указывайте `PROFILES=embeddings,monitoring`. Команда проверяет сертификат (срок, имя, ключ), поднимает Caddy и
Bifrost и сама проверяет сайт на портах 443, 8080 и 18443.

Портал, если он ещё не развёрнут, — `docs/vpn-launch.md`, часть A, шаги 6–7
(`make key NAME=portal`, `make portal`, `make portal-admin`). Если портал уже работал по
IP, перенастраивать его не нужно: пользователи, чаты и второй фактор сохраняются, все
входят заново.

Этот же этап включает таймер продления `llm-cert-renew.timer` — при трёх условиях:
`TLS_MODE=corp`, сертификат выпущен через `make cert`, `TIMEWEBCLOUD_AUTH_TOKEN` не
пуст. При пустом токене этап пишет «автопродление сертификата не включено».

```bash
systemctl list-timers llm-cert-renew.timer    # ожидается: таймер в списке, есть время следующего запуска
sudo journalctl -u llm-cert-renew             # журнал проверок продления
```

- Если не так (ошибка сертификата): повторите шаг 3, затем этот шаг.
- Если не так (таймера нет): проверьте три условия выше и повторите `make gateway`.

## 5. Порты на ВМ

```bash
sudo ss -ltnp | grep -E ':(443|8080|18443|8000|8081) '
sudo ufw status
```

Ожидается: 443, 8080 и 18443 — на всех интерфейсах (`0.0.0.0`); 8000 и 8081 — только
`127.0.0.1`.

- Если не так (`ufw` в состоянии `active`):
  `sudo ufw allow 443/tcp && sudo ufw allow 8080/tcp && sudo ufw allow 18443/tcp`.
- Если не так (порт занят другим процессом): `make gateway` сообщит об этом сам;
  освободите порт и повторите шаг 4.

После этого шага сисадмин включает проброс `195.122.229.203:18443 → 192.168.25.8:8080`.

## 6. Проверка снаружи [ВМ]

Не из сети заказчика и без VPN — например, с мобильного интернета:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://llm.<домен>:18443/v1/models   # 401 или 403
curl -sS -o /dev/null -w '%{http_code}\n' https://llm.<домен>:18443/            # 200 — страница входа; без портала — 404
```

Предупреждения о сертификате быть не должно.

Смоук-тесты — на ВМ:

```bash
make key NAME=smoke
make smoke KEY=sk-bf-... LLM_BASE_URL=https://llm.<домен>:18443/v1
make smoke-portal LLM_BASE_URL=https://llm.<домен>:18443/v1
make keys && make revoke ID=<id>
```

На самой ВМ имя разрешается во внешний IP, и запрос может не вернуться. Для тестов с ВМ
добавьте строку в `/etc/hosts` (или заведите внутреннюю DNS-запись, шаг 7):

```
192.168.25.8  llm.<домен>
```

Параметр `CA=` для сертификата Let's Encrypt не нужен.

Из `/v1` снаружи доступны только `/v1/chat/completions`, `/v1/completions`,
`/v1/embeddings` и `/v1/models`; остальное под `/v1` — 404:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' -X POST https://llm.<домен>:18443/v1/async/chat/completions   # 404
curl -sS -o /dev/null -w '%{http_code}\n' https://llm.<домен>:18443/v1/skills                          # 404
```

- Если не так (`curl` не соединяется): проброс не включён или цель не 8080 — к сисадмину.
- Если не так (тест на ВМ не соединяется): нет строки в `/etc/hosts`, см. выше.

## 7. Тот же адрес из сети заказчика и из VPN

Во внутреннем DNS заказчика заведите запись `llm.<домен>` → `192.168.25.8`. ВМ сама
слушает 18443, поэтому `https://llm.<домен>:18443` открывается изнутри напрямую,
настраивать hairpin NAT на роутере не нужно.

Проверка с ПК в сети заказчика или в VPN:

```bash
dig +short llm.<домен>          # ожидается: 192.168.25.8
curl -sS -o /dev/null -w '%{http_code}\n' https://llm.<домен>:18443/v1/models   # 401 или 403
```

- Если не так: ПК использует не внутренний DNS-сервер — к сисадмину.

## 8. Продление сертификата

Сертификат Let's Encrypt действует 90 дней. Таймер `llm-cert-renew.timer` раз в сутки
(со случайной задержкой до часа) запускает проверку; сертификат продлевается, когда до
конца срока остаётся меньше 30 дней. Caddy перечитывает новый сертификат без перезапуска.

```bash
make cert-renew                              # то же вручную; при достаточном сроке ничего не делает
sudo journalctl -u llm-cert-renew            # что было при последних проверках
systemctl status llm-cert-renew              # failed — последнее продление не удалось
```

При сбое продления работающий сертификат и Caddy не тронуты: файлы в `deploy/certs/`
заменяются только после успешного выпуска. Причину смотрите в журнале, после
исправления выполните `make cert-renew`. Перед обращением к Let's Encrypt клиент может
выждать случайную паузу — команда в это время не зависла.

| Сообщение | Что произошло | Что делать |
|---|---|---|
| «lego завершился с ошибкой: сертификат не получен» | Новый сертификат не выпущен; прежний работает | Причина — в выводе выше; проверить токен и исходящий доступ, повторить `make cert-renew` |
| «не удалось скопировать сертификат и ключ в …/deploy/certs» | Обычно нет места на диске; рабочие файлы не тронуты | Освободить место, повторить `make cert-renew` |
| «сертификат разложен, но Caddy его не перечитал и отдаёт прежний» | Файлы новые, Caddy отдаёт прежний сертификат; юнит `llm-cert-renew` в состоянии `failed` | `make logs SERVICE=caddy`; повторить `make cert-renew` — перечитывание повторит и таймер при следующем запуске |

Сертификат, выпущенный с `MANUAL=1`, таймер не продлевает. Продлевайте его не позже чем
через 60 дней после выпуска: `make cert-renew MANUAL=1` — с новой TXT-записью, как на
шаге 3. Команда обращается к Let's Encrypt, только когда до конца срока меньше 30 дней;
раньше она ничего не делает. Поставьте себе напоминание: писем об истечении срока не
приходит.

## 9. Что сообщить

- Сотрудникам: портал — `https://llm.<домен>:18443`, VPN для него не нужен. Памятка —
  `docs/user-guide.md`.
- Приложениям: `base_url=https://llm.<домен>:18443/v1`, `api_key=sk-bf-...`,
  `model="default"`. Ключи прежние.
- Администраторам: UI Bifrost и Grafana — через туннель
  `ssh -L 8081:127.0.0.1:8081 -L 3000:127.0.0.1:3000 <админ>@<вм>`.

До того как сообщать адрес сотрудникам, пройдите `docs/vpn-launch.md`, часть B: условия
открытия (шаг 0), обязательную проверку адреса клиента (шаг 5.1) и действия после
открытия.
