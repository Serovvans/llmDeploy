## 1. Цель и пользователи

Веб-интерфейс к LLM-сервису для сотрудников заказчика. Они строят ГИС на базе CoGIS и
решают задачи земельно-имущественных отношений; это не программисты, но им приходится
писать SQL-скрипты и плагины CoGIS на C#. Портал даёт им чат с моделью, общую базу
знаний компании и три прикладных инструмента — без API-ключей, терминала и настройки.

**В рамках первой версии:**
- вход по логину, паролю и одноразовому коду из приложения-аутентификатора (TOTP);
  учётные записи создают администраторы;
- чат с моделью: потоковые ответы, вложения (с версии 0.5 — и короткие аудио- и
  видеозаписи), история;
- база знаний (RAG): общая, пополняемая всеми сотрудниками, и личная у каждого;
  ответы со ссылками на источники; сканы распознаются при загрузке. С версии 0.5 —
  коллекция «Министерства», которую ведут администраторы, теги документов, картинки из
  документов в ответах, расшифровка аудио- и видеозаписей;
- инструменты: SQL-помощник (с версии 0.5 — с проверкой запросов на искусственных
  данных), помощник по плагинам CoGIS (C#), разбор документов и сканов;
- экспорт ответа и диалога в DOCX;
- светлая и тёмная темы, интерфейс на русском, дизайн-система Контур.

**Вне рамок** (не делаем, пока не внесено сюда): самостоятельная регистрация, SSO,
восстановление пароля по почте или SMS, статистика использования для администраторов, библиотека шаблонов запросов, выполнение
SQL на базах заказчика, компиляция C#, поиск в интернете, мобильное приложение,
интерфейс на других языках, совместные чаты; агентный поиск по базе знаний (несколько
кругов поиска по решению модели) и вызов инструментов моделью (tool calling);
распознавание речи на других языках, кроме русского, и разделение записи по говорящим.

Поиск в интернете в пакет 0.5 не вошёл: источник выдачи согласуется с заказчиком,
варианты и вопросы к нему — `docs/web-search-options.md`. Архитектура предрешена:
пайплайн под управлением кода портала — шаги (запрос к поисковику, загрузка страниц,
отбор фрагментов) выполняет портал, а не модель по своему усмотрению через вызов
инструментов. Когда функция будет вноситься сюда, решать останется источник выдачи,
доступ и квоты.

| Вопрос | Решение | Почему |
|---|---|---|
| Основа интерфейса | Свой портал: React + TypeScript + `@skbkontur/react-ui` | Требование дизайнера (Контур); готовые чаты (Open WebUI) его не выполняют и не дают своих инструментов |
| Запасная дизайн-система | Apple HIG — не используется | `@skbkontur/react-ui` 6.4.2: MIT, React ≤ 19, тёмная тема есть |
| Размещение | Та же ВМ с GPU, compose-профиль `portal`, за тем же Caddy | Один сервер и один бэкап; эмбеддинги рядом |
| Бэкенд | Python, FastAPI, uv | Тот же стек, что `scripts/` |
| Данные | PostgreSQL (пользователи, чаты, документы, очередь) + Qdrant (векторы) | Выбор заказчика |
| Путь к модели | Через Bifrost по docker-сети, отдельный virtual key портала | Единый учёт и лимиты; vLLM остаётся за gateway |

| Доступ после проброса порта | Из интернета по домену, без VPN (и портал, и `/v1`) | Выбор заказчика: сотрудники работают без VPN |
| Второй фактор | TOTP обязателен для всех учётных записей с первого входа | Страница входа открыта интернету; пароль, выданный вручную, — слабая единственная защита |
| База знаний | Любой сотрудник добавляет сразу в общую; плюс личная коллекция | Выбор заказчика; удалить документ может автор или администратор |
| Приватность | Чаты личные: администратор не видит переписку | Выбор заказчика |
| Git | Агенты работают в ветке `feat/portal`, коммит на этап; в `main` сливает человек | Выбор заказчика |
| Проверка SQL (0.5) | Отдельный контейнер-песочница PostgreSQL + PostGIS; в `portal-db` запросы не исполняются (§3.3, §5.3) | Запрос от модели — недоверенный код; единственный диалект проверяется настоящей СУБД, включая функции PostGIS |
| Коллекция «Министерства» (0.5) | Третья коллекция базы знаний: ведут администраторы, пользуются все (§4, §5.2) | Выбор владельца |
| Теги (0.5) | Свободные, с подсказкой существующих, во всех коллекциях (§5.2) | Выбор владельца |
| Картинки в базе знаний (0.5) | Извлекаются уже используемыми библиотеками, описывает основная модель (§5.2) | Без новых зависимостей и новых моделей на GPU |
| Качество поиска (0.5) | Переписывание запроса, разбиение по структуре, контекст фрагментов, реранкер на GPU; агентного поиска нет (§5.2) | Выбор владельца по итогам исследования; один проход поиска — предсказуемая задержка |
| Распознавание речи (0.5) | GigaAM-v3 на CPU в `portal-worker`, только русский язык (§3.3) | GPU не занимает; по опубликованным замерам на русском точнее Whisper — на записях заказчика не проверено |

| Обновление сервиса (0.5) | Один релиз в одно окно обслуживания; переобработка документов — после него в фоне (§8.2) | Выбор владельца |

## 3. Архитектура

```
 Браузер сотрудника (до домена — из VPN, после проброса порта — из интернета)
        │ HTTPS :443
        ▼
 ┌────────────────────────────── ВМ ──────────────────────────────────────────┐
 │ Caddy ── /v1 (4 маршрута API) ─▶ bifrost:8080                [gateway]     │
 │       ── /api/* ─▶ portal-api:8000                           [portal]      │
 │       ── прочее ─▶ portal-web:8080 (статика SPA)             [portal]      │
 │                                                                            │
 │ portal-api (FastAPI) ──┬─▶ portal-db (PostgreSQL)                          │
 │ portal-worker ─────────┼─▶ qdrant                                          │
 │   (индексация, OCR,    ├─▶ volume portal-files (оригиналы, картинки, звук) │
 │    речь на CPU)        └─▶ bifrost:8080 /v1/chat/completions,              │
 │                              /v1/embeddings, /v1/rerank                    │
 │                              └─▶ vllm, vllm-embed, vllm-rerank             │
 │                                                                            │
 │ portal-api ── своя сеть без выхода наружу ─▶ sql-sandbox (PostGIS)         │
 └────────────────────────────────────────────────────────────────────────────┘
```

Сервисы профиля `portal`:

| Сервис | Образ | Назначение | Порты на хост |
|---|---|---|---|
| `portal-web` | свой, статика SPA на `caddy` | Отдаёт собранный фронтенд | нет |
| `portal-api` | свой, `portal/backend` | REST + SSE, авторизация, чат, инструменты | нет |
| `portal-worker` | тот же образ, другая команда | Очередь заданий: разбор, OCR, описание картинок, расшифровка аудио и видео (CPU), эмбеддинги | нет |
| `portal-db` | `postgres`, точный тег | Реляционные данные и очередь заданий | нет |
| `qdrant` | `qdrant/qdrant`, точный тег | Векторный индекс | нет |
| `sql-sandbox` | свой, на `postgres` того же точного тега + PostGIS | Песочница проверки SQL на искусственных данных (§3.3); сервис необязательный | нет |

Реранкер (`vllm-rerank`) — не сервис профиля `portal`: это третий экземпляр vLLM рядом
с `vllm` и `vllm-embed`, в собственном профиле `rerank` (§3.3, `design.md` §3.9).

Правила:
- Профиль `portal` требует `gateway` и `embeddings`; `install.sh` отказывается включать
  его без них. Песочница SQL и реранкер для запуска портала не обязательны: без них
  портал работает, проверка SQL недоступна, поиск идёт без переранжирования (§3.3).
  Песочница входит в профиль `portal` и поднимается вместе с ним, но `portal-api` от
  неё не зависит (`depends_on` нет). Реранкер включается отдельным профилем `rerank` —
  по образцу `embeddings`; установка этапа его допускает, но не требует (§7).
- Ни один сервис портала не публикует порты на хост. Наружу по-прежнему только Caddy
  (порты — §3.2).
- Docker-сети: `portal-api` — в `edge` (Caddy, Bifrost) и новой `portal`
  (`portal-db`, `qdrant`); `portal-worker` — в `edge` (только ради Bifrost) и `portal`;
  `portal-db` и `qdrant` — только в `portal`. В сеть `inference` портал не входит.
  `sql-sandbox` — только в собственной внутренней сети без выхода наружу; кроме него в
  эту сеть входит один `portal-api`. `portal-worker`, `portal-db`, `qdrant`, Caddy и
  Bifrost в неё не входят.
- Портал и API живут на одном origin, поэтому CORS не настраивается, а имя хоста в
  конфигурации портала не участвует: смена IP на домен не требует правок портала.
- Без профиля `portal` Caddy ведёт себя как сейчас: всё, кроме маршрутов API под `/v1/`
  (`design.md` §3.3), — 404
  (выбор сниппета по переменной, как уже сделано для `TLS_MODE`).
- `/api/*` через 443 теперь принадлежит порталу. Админ-API Bifrost
  (`/api/governance/*`) и `/metrics` через 443 по-прежнему недоступны: у портала таких
  маршрутов нет, он отвечает 404. Смоук-тест обвязки обновляется под это.
- Очередь заданий — таблица в PostgreSQL (`SELECT … FOR UPDATE SKIP LOCKED`), без
  Redis/Celery. С версии 0.5 через неё идёт и расшифровка записей, в том числе
  вложений чата (§5.1); порядок обслуживания — §5.2.
- Оригиналы файлов — в volume `portal-files`, без объектного хранилища. Там же лежит
  производное от них: картинки документов и сжатый звук записей (§5.2).

### 3.1 Доступ по IP до привязки домена

`LLM_HOSTNAME=192.168.25.8`, `TLS_MODE=internal`: Caddy выпускает сертификат на IP из
собственного CA. Клиент, обращающийся по IP, не передаёт SNI, а внутри контейнера
локальный адрес соединения — адрес docker-сети, поэтому Caddy не найдёт сертификат сам.
В глобальные опции Caddyfile добавляется `default_sni {$LLM_HOSTNAME}` — для доменного
имени опция безвредна. **Проверить на ВМ.** Запасной вариант, если не заработает:
временное имя через файл `hosts` на тестовых ПК.

### 3.2 Доступ из интернета после проброса порта

Схема окончательная (сисадмин заказчика, 2026-10-05): поддомен `llm.<домен>` в
Timeweb, A-запись — на внешний IP `195.122.229.203`, проброс TCP
`195.122.229.203:18443 → 192.168.25.8:8080`. Адрес сервиса —
`https://llm.<домен>:18443` (портал) и `https://llm.<домен>:18443/v1` (API).
Портал живёт на одном origin с API, адрес в его конфигурации не участвует.

- **Порты ВМ.** Caddy принимает TLS на трёх портах хоста, все ведут на один и тот же
  сайт: `8080` — цель проброса из интернета; `18443` — чтобы тот же адрес
  `https://llm.<домен>:18443` работал из сети заказчика и из VPN при внутренней
  DNS-записи на `192.168.25.8`, не требуя hairpin NAT на роутере; `443` — доступ по IP
  в VPN до домена (§3.1). Админ-порт Bifrost на хосте переезжает с `127.0.0.1:8080` на
  `127.0.0.1:8081`: порт 8080 занят пробросом. vLLM остаётся на `127.0.0.1:8000`.
  Кроме 22 и этих трёх портов Caddy ВМ ничего не принимает извне.
- **Сертификат.** `LLM_HOSTNAME=llm.<домен>`, `TLS_MODE=corp`, сертификат Let's Encrypt.
  Внешние 80 и 443 не проброшены, поэтому подтверждение владения — только DNS-01 через
  API DNS Timeweb Cloud. Выпуск и продление делает отдельный ACME-клиент (lego,
  закреплённая версия образа) одной целью `make`; файлы кладутся в `deploy/certs/`,
  Caddy перечитывает их. Продление — по расписанию (systemd-таймер), без участия
  человека; неудача продления видна в журнале и не ломает работающий сертификат.
  Токен API DNS и ключ учётной записи ACME — секреты на ВМ вне репозитория. Если зона
  домена не обслуживается DNS Timeweb Cloud (нет API), запасной путь — выпуск с ручным
  добавлением TXT-записи и напоминанием о продлении раз в 60 дней.
- Порядок действий — `docs/domain-setup.md` (выпуск сертификата и развёртывание) и
  `docs/vpn-launch.md`, часть B (проверки перед открытием и после).

Следствия публичного доступа:
- второй фактор обязателен (§4), ограничение перебора — по логину и по адресу клиента;
- Caddy выставляет заголовки безопасности: HSTS, `Content-Security-Policy` (только свой
  origin), запрет встраивания во фреймы, `X-Content-Type-Options`, `Referrer-Policy`.
  Единственное послабление CSP — `'unsafe-inline'` в `style-src`: `@skbkontur/react-ui`
  вставляет стили во время работы. Скрипты, изображения, шрифты и соединения — только
  свой origin. Ответы портала сжимаются (бандл интерфейса — сотни килобайт);
- адрес клиента бэкенд берёт из `X-Forwarded-For`, которому доверяет только от Caddy.
  Если роутер при пробросе подменяет адрес источника своим, все внешние клиенты будут
  выглядеть одним адресом — тогда ограничение по адресу бесполезно и остаётся
  ограничение по логину. **Проверить на ВМ**;
- документация API бэкенда (`/docs`, `/openapi.json`) и служебные маршруты через Caddy
  недоступны;
- до проброса порта должны быть закрыты блокирующие находки `security-reviewer`.

### 3.3 Сервисы пакета 0.5

**Песочница SQL (`sql-sandbox`).** Отдельный контейнер PostgreSQL + PostGIS, в котором
портал исполняет проверяемые запросы на искусственных данных (§5.3). В `portal-db`
запросы пользователей и модели не исполняются никогда: ошибка изоляции открыла бы
данные портала.
- Образ — свой: `postgres` того же точного тега, что у `portal-db`, плюс пакет PostGIS
  закреплённой версии.
- Данные живут только в памяти (tmpfs с пределом размера): после перезапуска песочница
  пуста; тома у неё нет, в резервную копию она не входит.
- Проверки исполняет `portal-api`. Одновременно идёт не больше двух проверок (значение —
  в конфигурации); остальные ждут своей очереди.
- Сервис необязательный: при выключенной проверке (§7) портал запускается и работает
  без него. Сбой или отсутствие песочницы не ломает ответ: проверка получает статус
  «проверка недоступна».
- Изоляция контейнера, права роли и лимиты — §8.1.

**Реранкер (`vllm-rerank`).** Третий экземпляр того же образа vLLM на той же карте, с
моделью `bge-reranker-v2-m3` (`design.md` §3.9). Переупорядочивает кандидатов поиска по
базе знаний (§5.2).
- Портал обращается к нему через Bifrost по docker-сети (`/v1/rerank`) со своим virtual
  key, которому разрешается модель реранкера; в сеть `inference` портал по-прежнему не
  входит. Наружу маршрут не открывается: список маршрутов `/v1` в Caddy прежний
  (`design.md` §3.3). **Проверить на ВМ**: Bifrost v2.2.0 проксирует `/v1/rerank`
  провайдеру vLLM и не меняет запрос.
- Запасной вариант, если Bifrost этот маршрут не проксирует: отдельная внутренняя сеть
  между порталом и реранкером. В сеть `inference` портал и тогда не входит, а экземпляр
  реранкера получает собственный ключ, не совпадающий с `VLLM_API_KEY`: ключ основной
  модели порталу не выдаётся.
- Если реранкер выключен флагом (§7) или недоступен, поиск возвращает результаты в
  прежнем порядке — без ошибки для пользователя.

**Распознавание речи.** Модель GigaAM-v3 (вариант e2e — с пунктуацией) работает на CPU
внутри `portal-worker` через ONNX Runtime. Отдельного сервиса и сетевого интерфейса у
неё нет, через Bifrost звук не идёт, GPU не используется. Язык — только русский;
разделения по говорящим нет.
- Звуковую дорожку из аудио- и видеофайлов извлекает ffmpeg закреплённой версии в
  образе воркера; меры защиты — §8.1.
- Число потоков CPU под распознавание ограничено настройкой (по умолчанию 8). Предел
  общий на воркер, а не на задание: одновременные расшифровки делят его между собой
  (§5.2).
- Веса модели загружаются при подготовке релиза, до окна обслуживания (§8.2); в работе
  воркер за ними в интернет не обращается. По данным исследования веса берутся с
  Hugging Face — он уже есть в `docs/devops-request.md`; источник сверяет исполнитель
  при закреплении версии, и если он другой, заявка DevOps дополняется. Веса лежат в
  томе на ВМ, а не в слое образа; загружает их установка этапа (§7). Кеш весов в
  резервную копию не входит: он восстановим загрузкой.
- Длинная запись расшифровывается по частям; уже расшифрованное при перезапуске воркера
  не теряется — как распознанные страницы сканов.

### 3.4 Бюджет ресурсов ВМ

Факты, снятые на ВМ 2026-10-11: 16 vCPU; 70 ГБ RAM (занято 13, доступно 57), подкачка
7 ГБ; диск `/` — 68 ГБ, свободно 8,7 ГБ (занято 87 %); видеопамять — занято 66 057 из
73 415 МиБ при долях 0.85 и 0.06.

**Видеокарта.** На карте становится три процесса vLLM. Память делится долями от общей
памяти карты (`design.md` §3.6):

| Процесс | Доля | Примечание |
|---|---|---|
| Основная модель (`vllm`) | ~0.81 (было 0.85) | KV-кеш меньше примерно на 3 ГБ |
| Эмбеддинги (`vllm-embed`) | 0.06 | Без изменений |
| Реранкер (`vllm-rerank`) | ~0.04 | Около 3 ГБ |
| Сумма | ≤ 0.92 | Предел из `design.md` §3.6 |

Точные доли — **уточнить на ВМ**: предел 0.92 рассчитан на два процесса, у третьего
свой CUDA-контекст, и запаса может не хватить. Там же перепроверяются критерий
`design.md` §5 — не меньше 8 параллельных запросов при контексте 65 536 — и порядок
запуска: строго по очереди, каждый экземпляр после healthcheck предыдущего.
Распознавание речи и песочница SQL видеопамять не занимают. Описание картинок,
дописывание контекста к фрагментам, переписывание запроса и проверка SQL добавляют
обращения к основной модели — это время GPU, а не память (§5.2, §5.3).

**Процессор.** Под распознавание речи — до 8 потоков из 16 vCPU (настройка);
остальное — серверам vLLM, PostgreSQL, Qdrant, бэкенду и песочнице. Предел общий на
воркер: место под вложения чата (§5.2) получает долю из тех же 8 потоков, а не сверх
них, — иначе две расшифровки заняли бы все ядра. Число потоков — настройка библиотеки,
а не граница, поэтому у контейнера `portal-worker` заданы ещё и пределы CPU и памяти
(значения закрепляет `infra-engineer`, **уточнить на ВМ**). У песочницы и у
запусков ffmpeg свои пределы CPU (§8.1). Оценка скорости: три часа записи — порядка
10–20 минут на 8 потоках; это пересчёт с опубликованных замеров на другом процессоре,
**проверить на ВМ**.

**Оперативная память.** Оценки: модель речи — 1–2 ГБ на экземпляр (если место под
вложения чата держит свой экземпляр — ещё столько же); песочница — 0,2–0,3 ГБ в покое
плюс её tmpfs (он считается оперативной памятью, поэтому ограничен); память процесса
реранкера — **измерить на ВМ**. При 57 ГБ доступной памяти запас есть.

**Диск.** Свободных 8,7 ГБ на пакет не хватает: расширение диска — предусловие релиза
(§8.2). Требование `design.md` §10 — не меньше 300 ГБ; фактический объём и способ
расширения — вопрос владельцу и DevOps (§11). Что займёт место (оценки, **уточнить на
ВМ**):

| Что | Оценка |
|---|---|
| Веса реранкера | ~2,5 ГБ |
| Модель распознавания речи | ~1 ГБ |
| Образ песочницы; ffmpeg и ONNX Runtime в образе воркера | 1–2 ГБ |
| Образы портала двух релизов (новый и предыдущий — для отката), кеш сборки на ВМ | Измерить; несколько ГБ |
| Резервная копия перед релизом | Размер базы, файлов и векторов — измерить; хранить не на диске `/` (место — §11) |
| Восстановление из копии | Копия разворачивается рядом с действующими данными: на время восстановления нужно ещё столько же места, сколько занимают база, файлы и векторы |
| Медиафайл в обработке | До 2 ГБ исходника и до ~0,35 ГБ развёрнутого звука (16 кГц, моно) на трёхчасовую запись |
| Сжатый звук записей | ~45 МБ на три часа записи (при ~32 кбит/с) |
| Картинки документов | Зависит от корпуса; не больше 50 картинок на документ |

Минимум свободного места после расширения — около 135 ГБ. Расчёт: веса, образы и кеш
сборки — ~15 ГБ; квота на медиа — 50 ГБ; тома портала с ростом (база, файлы, векторы,
картинки) — 10 ГБ; восстановление из копии — ещё раз медиа и тома, 60 ГБ. Квота и
размер томов здесь — допущения: квоту задаёт владелец (§11), тома измеряются на ВМ; при
других значениях минимум равен 15 ГБ + 2 × (квота + тома). Идущие загрузки и временные
файлы извлечения звука отдельной статьи не дают: они входят в квоту (ниже). Резервная
копия в расчёт не входит: она хранится не на диске `/`. Требование `design.md` §10 —
300 ГБ общего объёма при занятых сейчас 56 ГБ — этот минимум покрывает с запасом; его
и стоит запрашивать у DevOps.

Квота на медиа. Суммарный объём медиа на диске ограничен настройкой. В квоту входят
все байты медиа независимо от статуса: исходники записей в очереди, в обработке и с
ошибкой обработки, медиавложения чата, сжатый звук, временные файлы извлечения звука и
место, зарезервированное под идущие загрузки. Второе, независимое условие — порог
свободного места на томе `portal-files`: ниже порога медиа не принимается, даже если
квота не выбрана. Диск `/` общий с базой, Qdrant и Bifrost, и его заполнение
остановило бы весь сервис. Число одновременных загрузок медиа ограничено настройкой.
При отказе пользователь получает объяснение. Правила приёма — §8.1; значения задаются
после расширения диска (§11).

## 4. Учётные записи и доступ

- Роли: `admin` (владелец проекта и гендиректор) и `employee`.
- Первый администратор создаётся командой на ВМ (CLI бэкенда, цель `make`), остальные
  учётные записи — в интерфейсе администратора.
- Администратор: создаёт пользователя (ФИО, логин, роль) и получает одноразовый
  временный пароль; меняет ФИО и роль другого пользователя (логин не меняется, удаления
  учётных записей нет); сбрасывает пароль; блокирует и разблокирует; удаляет любой документ
  общей базы знаний; ведёт коллекцию «Министерства» (ниже). Содержимое чатов и личных
  коллекций ему недоступно — ни в интерфейсе, ни через API.
- Коллекция «Министерства» (§5.2): видеть её документы и искать по ним могут все.
  Добавлять и удалять документы, отправлять их на повторную обработку и менять их теги
  могут только администраторы. Право даёт текущая роль, а не авторство: администратор,
  ставший сотрудником, теряет его и для документов, которые добавил сам.
- Теги документа (§5.2) после загрузки меняют автор и администратор: в общей базе —
  автор документа или администратор; в личной коллекции — только владелец (личные
  коллекции администратору недоступны); в «Министерствах» — только администратор.
- При первом входе и после сброса пользователь обязан сменить пароль.
- Пароли: Argon2id; минимальная длина (не меньше 12 символов) и прочие параметры — в
  конфигурации; пароли из списка распространённых отклоняются.
- Второй фактор (TOTP) обязателен для всех и включён с самого начала, в том числе на
  этапе теста в VPN: при первом входе после смены пароля пользователь сканирует QR-код
  приложением-аутентификатором (Яндекс Ключ, Google Authenticator и т. п.), подтверждает
  кодом и получает одноразовые резервные коды. Пока второй фактор не настроен, доступа
  к порталу нет. QR-код формируется самим порталом, без внешних сервисов.
- Секрет TOTP хранится зашифрованным (ключ — `PORTAL_SECRET_KEY`), резервные коды — в
  виде хешей. Использованный код повторно не принимается.
- Сброс второго фактора: администратор — сотруднику; администратору — другой
  администратор или команда на ВМ. После сброса настройка проходит заново.
- Сессия ограничена по общему времени жизни и по времени бездействия (значения — в
  конфигурации).
- Сессии: случайный непрозрачный токен, в БД хранится его хеш; cookie `HttpOnly`,
  `Secure`, `SameSite=Strict`. Блокировка пользователя и смена пароля гасят его сессии.
  Уже идущий ответ модели обрывается при любом завершении сессии: блокировка, сброс
  пароля или второго фактора, смена роли, выход, смена пароля.
  Изменяющие запросы дополнительно требуют заголовок, который не может выставить чужой
  сайт (защита от CSRF).
- Ограничение перебора: после N неудачных попыток подряд (пароль или код) — временная
  блокировка входа для логина с нарастающей задержкой; отдельно — ограничение частоты
  попыток с одного адреса (значения — в конфигурации). Ответ на неверный логин и на
  неверный пароль одинаков по тексту и времени.
- Сброс пароля или второго фактора администратором снимает временную блокировку входа
  для логина.
- Администратор видит в списке пользователей, что вход сотрудника временно заблокирован
  после серии неудач, и снимает эту блокировку отдельным действием — без сброса пароля
  и второго фактора: если ошибался сам сотрудник, он сразу входит со своим паролем и
  кодом. Действие пишется в журнал аудита. То же доступно командой на ВМ — на случай,
  когда заблокирован вход администратора. Ограничение по адресу этим не снимается.
- Журнал аудита: входы, неудачные входы, смена пароля самим пользователем, действия
  администратора, загрузка и удаление документов. Без текста сообщений и содержимого файлов. Журнал читается командой на
  ВМ; экрана в интерфейсе нет.
- Каждая выборка чатов, сообщений, вложений, личных документов фильтруется по владельцу
  на уровне запроса к БД и к Qdrant, а не в интерфейсе. То же относится ко всему
  производному от документов и вложений: картинкам, расшифровкам, сжатому звуку, тегам
  и их подсказкам (§8.1).

## 5. Функциональность

### 5.1 Чат

- Потоковый ответ (SSE), остановка генерации, повторная генерация последнего ответа.
- История: список чатов, переименование, удаление; название нового чата предлагает модель.
- Вложения: изображения, PDF, DOCX, TXT/MD. Изображения и страницы сканов передаются
  модели как картинки (не более 8 на запрос — лимит vLLM), текст — как текст.
  Вложение, в котором больше 8 изображений или страниц скана, отклоняется с
  объяснением; первые 8 страниц молча не берутся.
- Аудио и видео во вложении: короткая запись на русском — до 20 минут (значение — в
  конфигурации) — расшифровывается, и расшифровка идёт в вопрос как текст вложения;
  саму запись модель не получает. Расшифровка выполняется в фоне через очередь воркера
  (§3): на вложении виден её статус, и пока она не готова, отправить сообщение с этим
  вложением нельзя. Более длинные записи загружаются в базу знаний (§5.2). Форматы,
  хранение и меры защиты — те же, что в базе знаний (§5.2, §8.1).
- Режим ответа: «Быстро» и «Вдумчиво». «Быстро» — `reasoning_effort: "low"`. При
  «Вдумчиво» портал поле `reasoning_effort` не передаёт: действует значение шаблона
  модели по умолчанию — `xhigh`. Причина: шлюз Bifrost v2.2.0 переписывает `xhigh` в
  `high`, а `high` шаблон Qwen3.8 отклоняет с HTTP 400 (`design.md` §3.1) — режим не
  работал. Значения `low` и `medium` шлюз не меняет (проверено на ВМ 2026-10-11).
  Размышления модели показываются свёрнутым блоком.
- Выбор базы знаний: набор коллекций из «Общая», «Моя» и «Министерства» — отмечается
  любое сочетание; пустой набор означает «без базы знаний». По умолчанию набор пуст;
  последний выбор запоминается в браузере. Рядом — выбор тегов (§5.2): если теги
  выбраны, поиск идёт только по документам, у которых есть хотя бы один из выбранных
  тегов; если не выбраны — по всем документам выбранных коллекций.
- Картинки из базы знаний: если ответ ссылается сноской на источник-картинку (§5.2),
  она показывается под ответом и в карточке источника. Адреса картинок модель не
  пишет; markdown-картинки из текста модели по-прежнему не загружаются (§8.1).
- Markdown, таблицы, подсветка кода, кнопка «Скопировать» у блоков кода.
- Экспорт ответа или всего диалога в DOCX (§5.6).
- Портал сам следит за длиной контекста (65 536 токенов): при переполнении старые
  сообщения отбрасываются, пользователю показывается заметка об этом.

### 5.2 База знаний (RAG)

- Коллекции: общая (видят все), личная (видит только владелец) и «Министерства» (видят
  все, ведут администраторы — §4). При загрузке пользователь выбирает, куда положить
  документ; общий документ сразу доступен всем. «Министерства» предлагаются для выбора
  только администратору. Справочника министерств нет: внутри коллекции документы
  размечаются тегами.
- При добавлении в общую базу документ можно пометить как документацию CoGIS (§5.4).
  Отметку ставит любой сотрудник; после добавления она не меняется. В «Министерствах»,
  как и в личной коллекции, такой отметки нет.
- Теги. При загрузке документу можно задать теги — свободный текст с подсказкой уже
  существующих. Теги есть во всех трёх коллекциях. У документа не больше 10 тегов, тег
  не длиннее 50 символов; пробелы по краям отбрасываются, регистр не различается
  («Аренда» и «аренда» — один тег). Списком тегов никто отдельно не управляет: тег
  существует, пока стоит хотя бы на одном документе. После загрузки теги меняют автор
  и администратор (права — §4); смена тегов сразу действует на поиск и не требует
  повторной обработки документа. Подсказки показывают только теги документов, которые
  видит сам пользователь: теги чужих личных документов не раскрываются никому, включая
  администратора. На экране базы знаний список документов отбирается по тегам; в чате
  теги сужают поиск (§5.1).
- У документа видны название, автор, дата, число страниц, статус индексации
  («в очереди», «обрабатывается», «готов», «ошибка» с понятной причиной). Документ с
  ошибкой автор или администратор может отправить на повторную обработку без
  повторной загрузки; интерфейс предлагает это, когда повтор может помочь (сбой
  распознавания, внутренняя ошибка), иначе ведёт к замене файла. У DOCX, TXT и MD
  страниц нет: число страниц и страница в источнике для них не показываются. У аудио-
  и видеозаписи вместо числа страниц — длительность, в источнике — таймкод; ход
  расшифровки виден в статусе.
- Удаление: автор или администратор (в «Министерствах» — только администратор, §4).
  Удаляются оригинал, фрагменты и векторы, а также картинки, расшифровка и сжатый звук.
  Карточки источников с цитатами в прежних ответах остаются, но документ по ним
  больше не открывается, а его картинки и звук не показываются.
- Форматы: PDF (с текстовым слоем и сканы), DOCX, TXT/MD, изображения JPG/PNG; аудио —
  MP3, WAV, M4A, OGG, FLAC; видео — MP4, MKV, WebM, MOV.
  Повторная загрузка того же файла в ту же коллекцию распознаётся по хешу содержимого;
  чтобы сменить теги, правят уже загруженный документ.
- Обработка — в `portal-worker`: извлечение текста и структуры (заголовки) → для
  страниц без текстового слоя распознавание основной моделью (зрение) → извлечение и
  описание картинок → разбиение на фрагменты с сохранением номера страницы →
  дописывание контекста к фрагментам → эмбеддинги (`model="embeddings"` через Bifrost)
  → запись в Qdrant. У записи вместо первых шагов — извлечение звуковой дорожки и
  расшифровка, а вместо номера страницы — таймкод.
- Картинки. Из DOCX и PDF извлекаются встроенные картинки — теми же библиотеками,
  которыми документ разбирается (`python-docx`, `pypdfium2`), без новых зависимостей;
  файл-картинка (JPG, PNG) берётся как есть. Мелкие картинки (значки, линейки)
  отбрасываются: меньшая сторона короче 100 px или площадь меньше 20 000 px². На
  документ — не больше 50 картинок; одинаковые картинки внутри документа (по хешу
  содержимого) считаются одной. Пороги и лимит — в конфигурации.
- Для каждой картинки основная модель (зрение) составляет описание и выписывает текст,
  который на ней есть. Описание индексируется как фрагмент документа и находится
  поиском наравне с текстом. При ответе модель получает описание, а не саму картинку,
  и ссылается на неё обычной сноской; картинку показывает интерфейс — под ответом, в
  карточке источника (§5.1) и в просмотре источника.
- Аудио и видео. Запись на русском языке расшифровывается на CPU, с пунктуацией
  (§3.3); другие языки и разделение по говорящим не поддерживаются. Пределы: файл до
  2 ГБ, запись до 3 часов. Из видео берётся только звуковая дорожка, само видео не
  хранится. От записи хранится сжатый звук (Opus) — чтобы прослушать её с нужного
  момента; исходный файл удаляется после успешной обработки. Расшифровка разбивается
  на фрагменты с таймкодами и индексируется как текст документа. При загрузке записи
  коллекция по умолчанию — личная: записи совещаний чувствительнее документов;
  пользователь может выбрать другую.
- Распознавание сканов занимает GPU основной модели, поэтому число одновременных
  заданий воркера ограничено конфигурацией: чат не должен заметно замедляться. То же
  относится к описанию картинок и дописыванию контекста к фрагментам — это фоновые
  обращения к основной модели; сколько их идёт одновременно, задаёт отдельная
  настройка — ею регулируют нагрузку от переобработки (§8.2). Расшифровка речи GPU не
  занимает, но занимает ядра CPU (§3.4).
- Порядок в очереди: расшифровка вложений чата (§5.1) обслуживается раньше индексации
  базы знаний и не ждёт конца уже идущего длинного задания — сообщение ждёт человек.
  Для этого у воркера есть отдельное место только под вложения чата: задания базы
  знаний его не занимают. Остальные задания по-прежнему идут по одному (значение — в
  конфигурации); предел потоков распознавания речи общий на оба места (§3.4). Новые
  загрузки обслуживаются раньше массовой переобработки (§8.2). Этот приоритет действует
  на границе заданий: идущее задание не прерывается. Чтобы граница наступала часто,
  дописывание контекста к фрагментам — отдельный этап, который идёт порциями
  ограниченного размера (в конфигурации): между порциями воркер берёт задания с более
  высоким приоритетом.
- Поиск — гибридный: векторный плюс лексический (кадастровые номера, номера
  документов, фамилии нужно находить по точному совпадению), объединение результатов.
  Лексический поиск находит фамилию и в косвенном падеже (в индекс кладутся слово и
  его основа), не различает похожие латинские и кириллические буквы в номерах и
  пробелы вокруг дефиса и дроби; лучшие точные совпадения всегда входят в выдачу.
  Страница PDF с негодным текстовым слоем распознаётся как скан.
  Фильтр доступа (общая ∪ «Министерства» ∪ личная текущего пользователя) накладывается
  в самом запросе к Qdrant и строится только из сессии; выбор коллекций и тегов в чате
  может его лишь сузить (§8.1).
- Запрос для поиска. Уточняющий вопрос («а какой срок у него?») перед поиском
  переписывается моделью в самостоятельный запрос с учётом истории диалога — одним
  коротким обращением; для первого сообщения диалога шаг пропускается. Переписанный
  текст используется только для поиска: вопрос пользователя модель получает без
  изменений. При сбое переписывания поиск идёт по исходному тексту вопроса.
- Разбиение на фрагменты учитывает структуру документа: заголовки, а в нормативных
  текстах — статьи и пункты. В текст, по которому строятся эмбеддинг и лексический
  индекс, добавляются название документа и раздела («Документ: … / Раздел: …»); цитата
  в источнике остаётся дословным отрывком документа.
- Контекст фрагмента (contextual retrieval): при индексации основная модель в фоне
  дописывает к каждому фрагменту короткое пояснение, к чему он относится в документе.
  Для этого она получает не документ целиком — большой документ в контекст модели не
  помещается, — а ограниченное окно: название документа, заголовок раздела и соседние
  фрагменты. Предел окна в токенах и предел длины пояснения — в конфигурации.
  Пояснение используется только в поиске: в эмбеддинге, лексическом индексе и
  переранжировании. В запрос к отвечающей модели, в цитату и в сохранённые источники
  оно не попадает: пользователь пояснения не видит и не смог бы сверить по нему ответ
  (§8.1). Включается флагом (§7).
- Реранкер: из 40 кандидатов гибридного поиска модель переранжирования (§3.3) отбирает
  8 лучших (значения — в конфигурации). Правило о точных совпадениях сохраняется:
  лучшие точные совпадения входят в выдачу независимо от оценки реранкера. Включается
  флагом (§7); если реранкер выключен или недоступен, кандидаты идут в прежнем порядке.
- В контекст ответа вместе с отобранным фрагментом подтягиваются соседние фрагменты
  того же документа — в пределах прежнего бюджета контекста базы знаний.
- Агентного поиска нет: поиск — один проход под управлением кода портала; модель сама
  не решает, искать ли ещё раз, и инструментов не вызывает (§1).
- Улучшения поиска действуют везде, где портал ищет по базе знаний: в чате и в
  помощнике CoGIS (§5.4).
- Ответ содержит пометки-ссылки; под ответом — карточки источников: документ,
  страница (у записи — таймкод), цитата; у источника-картинки — сама картинка. По
  клику открывается документ на нужной странице: распознанный текст страницы с
  подсвеченной цитатой и ссылка «Открыть оригинал» в новой вкладке; встроенного
  просмотра PDF и сканов в портале нет. У записи открывается расшифровка на нужном
  месте и проигрыватель, который начинает со звука этого момента; ссылки «Открыть
  оригинал» у записи нет — исходный файл не хранится. У источника-картинки в просмотре
  видны картинка и её описание. Если в базе ничего подходящего не нашлось, модель так
  и говорит, а не выдумывает.
- Содержимое документов — недоверенный ввод: оно передаётся модели как данные, а не как
  инструкции, и не может менять системные правила инструмента. То же относится ко
  всему, что получено из загруженных файлов: к расшифровкам записей, описаниям
  картинок и тексту с них. Пояснения, дописанные к фрагментам, отвечающей модели не
  передаются вовсе (§8.1).
- Качество поиска проверяется на контрольном наборе вопросов (русский язык,
  юридические и технические тексты). В версии 0.5 набор расширяется: больше вопросов и
  уточняющие вопросы в диалоге. Метрики считаются по этапам: полнота среди кандидатов
  (recall@k) — до реранкера, nDCG и MRR — после него; так видно, какой этап теряет
  ответ. Замер делается до и после включения каждого улучшения. Набор строится на
  документах общей базы и «Министерств»; личные документы и переписка сотрудников в
  него не попадают (§4).
- Модель эмбеддингов в пакете 0.5 не меняется — `Qwen3-Embedding-0.6B`. Сравнение с
  `bge-m3` (`design.md` §3.6) остаётся возможным на расширенном наборе; смена модели —
  отдельное решение.
- При релизе 0.5 все существующие документы обрабатываются заново — с картинками,
  новым разбиением и контекстом фрагментов (§8.2). Переобработка не убирает документ
  из поиска: его статус для поиска не меняется, прежние фрагменты и векторы остаются
  до конца задания и заменяются новыми разом. Если переобработка не удалась, документ
  остаётся «готов» с прежним индексом и отметкой о сбое с причиной; его можно
  отправить на переобработку снова.
- Библиотека разбора PDF — с разрешительной лицензией (`pypdfium2`); PyMuPDF (AGPL) не
  используется.

### 5.3 SQL-помощник

- Действия: «Написать запрос», «Объяснить запрос», «Найти ошибку», «Оптимизировать».
- Диалект выбирается из списка в конфигурации (по умолчанию PostgreSQL + PostGIS).
- Пользователь может сохранить схему своей базы (DDL или описание таблиц) и выбрать её —
  она подставляется в контекст. Схемы личные.
- Сгенерированный запрос проходит синтаксическую проверку (`sqlglot`); опасные операции
  (`DROP`, `TRUNCATE`, `UPDATE`/`DELETE` без `WHERE`) подсвечиваются предупреждением.
  Запрос, который вставил сам пользователь, проверяется на опасные операции; итог
  синтаксической проверки под ним не показывается — синтаксис разбирает модель.
  Запросом в вопросе считается блок кода или текст, начинающийся с ключевого слова SQL.
- Портал **не подключается к базам заказчика**; запросы он проверяет в изолированной
  тестовой базе на искусственных данных (ниже). Так же сказано в интерфейсе — вместо
  прежнего «портал не выполняет запросы».
- Проверка на тестовых данных:
  - включается переключателем «Проверять на тестовых данных» на экране (§6); выбор
    пользователя запоминается. Общий выключатель — флаг в конфигурации (§7); по
    умолчанию проверка выключена для всех;
  - доступна только при выбранной сохранённой схеме: без схемы переключатель неактивен
    и объясняет почему. Проверяется единственный диалект конфигурации — PostgreSQL +
    PostGIS; для другого диалекта, если он появится, переключатель тоже неактивен;
  - проверяются запросы из ответа модели. Ответ показывается сразу, как раньше;
    проверка идёт после него и приходит отдельным статусом под блоком кода: тестовые
    данные по таблицам, результат запроса (не больше 50 строк) или ошибка исполнения;
  - тестовые данные готовит модель под конкретный запрос: упрощённый DDL по схеме
    пользователя и 5–15 строк на таблицу. Ограничения (ключи, уникальность, `CHECK`)
    проверяет сама СУБД, а не код портала;
  - при ошибке исполнения модель исправляет запрос — не больше двух попыток;
    исправленный запрос приходит в том же статусе с пометкой «исправлено» и указанием
    ошибки. Запрос, который выполнился, не переписывается;
  - `INSERT`, `UPDATE`, `DELETE` исполняются в транзакции, которая всегда откатывается
    (откатывается и вся проверка целиком — §8.1);
  - DDL, `DROP`, `TRUNCATE` и блок из нескольких операторов не исполняются: статус «не
    проверялось»;
  - пустой результат — предупреждение «данные не покрыли условия»; запрос при этом не
    исправляется. План запроса не показывается: на десятке строк он вводит в
    заблуждение о скорости;
  - рядом со статусом — постоянная оговорка: данные придуманы моделью; проверка
    показывает, что запрос исполняется и что он возвращает на примере, но не
    доказывает его правильность;
  - если песочница недоступна, статус — «проверка недоступна»; если проверка не
    уложилась в общий срок (§8.1), статус говорит об этом; ответ в обоих случаях не
    страдает;
  - итог проверки сохраняется в истории вместе с ответом. Идущая проверка обрывается
    при завершении сессии, как и идущий ответ (§4);
  - устройство песочницы — §3.3, её изоляция и ограничения — §8.1.
- Своя сохраняемая история запросов и уточняющие вопросы в режиме диалога, как в чате.

### 5.4 Помощник по плагинам CoGIS (C#)

- Действия: «Написать плагин», «Объяснить код», «Разобрать ошибку сборки».
- Отвечает с опорой на документы общей базы знаний, помеченные как документация CoGIS;
  источники показываются так же, как в чате.
- Код не компилируется и не запускается порталом.
- Своя сохраняемая история запросов и уточняющие вопросы в режиме диалога, как в чате.
- Зависимость от заказчика: документация и примеры плагинов CoGIS должны быть загружены
  в базу знаний; без них помощник работает на общих знаниях модели и предупреждает об этом.

### 5.5 Разбор документов и сканов

- Загрузка скана, PDF, DOCX или фото → выбор шаблона: «Выписка ЕГРН», «Договор
  аренды», «Постановление / распоряжение», «Произвольный документ».
- Результат: таблица извлечённых реквизитов (структурированный вывод по JSON-схеме
  шаблона), краткое содержание, затем вопросы по документу в режиме диалога.
- Шаблоны (поля и их описания) — в YAML-конфигурации, новые добавляются без правки кода.
- Реквизит, которого нет в документе, остаётся пустым, а не придумывается; рядом с
  таблицей — напоминание сверить значения с оригиналом.
- Многостраничные сканы обрабатываются пачками по 8 страниц: пачка — единица хода,
  модели уходит один запрос на страницу. Изображения — JPG и PNG; HEIC не принимается.
- Разбор идёт внутри запроса, не в очереди: до появления таблицы вкладку нельзя
  закрывать. Оборванное краткое содержание заново не формируется.
- Своя сохраняемая история разборов, как в чате. Разбор сохраняется, как только
  получена таблица реквизитов: сбой или остановка на кратком содержании её не стирают.

### 5.6 Экспорт в DOCX

Формируется на сервере (`python-docx`): заголовки, списки, таблицы, блоки кода.
Экспортируется один ответ или диалог целиком. Картинки из базы знаний в этой версии в
экспорт не попадают: сноска остаётся текстом.

## 6. Интерфейс

Задание дизайнера: дизайн-система Контур, интерфейс удобный, интуитивный, оригинальный и
впечатляющий, светлая и тёмная темы, русский язык.

- Библиотека: `@skbkontur/react-ui` (закреплённая версия) и её официальные пакеты
  иконок. Свои компоненты — только там, где в библиотеке нет подходящего (лента
  сообщений, карточки источников, просмотр документа), и на токенах темы Контура.
- Темы: светлая и тёмная средствами библиотеки; по умолчанию — как в системе,
  переключатель в интерфейсе, выбор запоминается.
- Все тексты на русском, включая ошибки, пустые состояния и подсказки. Никакого жаргона:
  «база знаний», а не «RAG»; «источники», а не «чанки».
- Шрифты и все ресурсы раздаются с портала: внешних CDN нет (ВМ может быть без
  интернета). Фирменный шрифт Контура (Lab Grotesque) используется только если это
  позволяет его лицензия; иначе — свободный шрифт с кириллицей. Лицензия не позволяет:
  используются Golos Text и JetBrains Mono (для кода).
- Акцентный цвет — нейтральный, как у ссылок и кнопок самой библиотеки; сноски
  выделяются формой, а не цветом.
- Название в интерфейсе — «Портал сотрудников». Чат — лента-протокол со сносками на
  источники, без «пузырей».
- Логотипы и название «Контур» в интерфейсе не используются: берётся библиотека
  компонентов, а не бренд.
- Экраны: вход, ввод кода, смена пароля, настройка второго фактора, чат, база знаний, SQL-помощник, помощник CoGIS, разбор
  документов, администрирование (пользователи), профиль.
- Списки документов базы знаний и пользователей: отбор по тексту и сортировка; список
  документов — ещё и отбор по тегам.
- Экран SQL (перекомпоновка 0.5): «Диалект», «Схема базы», «Мои схемы» и переключатель
  «Проверять на тестовых данных» — в строке заголовка экрана, справа вверху. Выбор
  режима (написать, объяснить, найти ошибку, оптимизировать) — под полем ввода, в
  строке управления панели запроса, как «Быстро / Вдумчиво» в чате. Это отступление от
  общего для инструментов порядка «действие сверху» — только для SQL: экран помощника
  CoGIS не меняется.
- Экран базы знаний: третья вкладка «Министерства»; у документов видны теги, их можно
  править (права — §4); у записей — длительность и ход расшифровки.
- Панель запроса чата: выбор коллекций (несколько сразу) и тегов (§5.1); у аудио- и
  видеовложения — статус расшифровки.
- Карточка и просмотр источника: картинка у источника-картинки; таймкод и проигрыватель
  у записи (§5.2).
- Концепцию (структура экранов, навигация, «фирменные» решения, состояния) до начала
  вёрстки описывает `docs/portal-ui.md`; её утверждает человек.
- Рабочее разрешение — настольный браузер от 1280 px; на узком экране интерфейс не
  ломается, но отдельная мобильная версия не делается.
- Значок сайта (вкладка браузера) — собственный простой знак в акцентном цвете портала,
  отдаётся самим порталом; чужие логотипы не используются.

## 7. Конфигурация и секреты

Параметры приложения — YAML в `portal/backend/config/`, читаются одним классом
настроек: лимиты размера файлов, параметры разбиения и поиска, число заданий воркера,
политика паролей и блокировок, диалекты SQL, шаблоны разбора документов, системные
промпты инструментов. YAML вшит в образ; поверх него накладывается необязательный
файл `/etc/portal/config.override.yaml` (им стенд задаёт короткие блокировки для тестов).

Пакет 0.5 добавляет в YAML: пределы проверки SQL (число одновременных проверок, время
запроса, общий срок проверки, размер результата); пределы тегов; пороги и лимит
картинок; форматы и пределы аудио и видео (размер, длительность, длительность для
вложения чата, звуковые кодеки, квота на медиа, порог свободного места, число
одновременных загрузок); число потоков распознавания речи; число одновременных фоновых
обращений к модели; параметры переписывания запроса, реранкера (число кандидатов и
итоговых фрагментов) и контекста фрагментов (окно, длина пояснения, размер порции).
Имена ключей — в контракте.

Флаги функций 0.5 — тоже в YAML. Функцию выключают накладкой
`config.override.yaml` и перезапуском сервисов портала, без пересборки образа и без
отката релиза (§8.2):

| Флаг | По умолчанию | Если выключен |
|---|---|---|
| Проверка SQL на тестовых данных | выключена | Переключателя на экране нет; сервис песочницы не нужен |
| Реранкер | включён | Кандидаты поиска идут в прежнем порядке |
| Контекст фрагментов | включён | Фрагменты индексируются без пояснения |
| Переписывание запроса | включено | Поиск идёт по тексту последнего сообщения |
| Описание картинок | включено | Картинки не извлекаются; уже извлечённые показываются |
| Приём аудио и видео | включён | Записи не принимаются ни в базу знаний, ни в чат; уже расшифрованные доступны |

Коллекция «Министерства», теги и перекомпоновка экрана SQL флагов не имеют: это
изменения модели данных и вёрстки. Значения по умолчанию утверждены владельцем
2026-10-11 (§11).

Новые переменные `deploy/.env` — секреты. `PORTAL_DB_PASSWORD`, `QDRANT_API_KEY` и
`PORTAL_SECRET_KEY` обязательны при любом наборе профилей (compose подставляет их во все
сервисы); `PORTAL_LLM_API_KEY` выдаёт Bifrost, он обязателен только при профиле `portal`:
с пустым ключом `portal-api` и `portal-worker` не стартуют.

| Переменная | Назначение |
|---|---|
| `PORTAL_DB_PASSWORD` | Пароль PostgreSQL портала |
| `PORTAL_LLM_API_KEY` | Virtual key Bifrost для портала (`make key NAME=portal`) |
| `QDRANT_API_KEY` | Ключ доступа к Qdrant |
| `PORTAL_SECRET_KEY` | Шифрование секретов TOTP в БД; копия — вне ВМ, без неё второй фактор всем придётся настраивать заново |

Пакет 0.5 добавляет учётные данные песочницы SQL: они отдельные от
`PORTAL_DB_PASSWORD` (секреты портала в песочницу не попадают, §8.1) и нужны только при
включённой проверке. Модель и доля памяти реранкера — несекретные переменные
`deploy/.env` (`design.md` §6.1). Имена переменных закрепляют контракт и
`infra-engineer`.

`COMPOSE_PROFILES` получает значение `portal`, а `SITE_MODE` — значение `portal`
(`api` по умолчанию: всё, кроме маршрутов API под `/v1/`, — 404); обе выставляет установка этапа.
Секреты портала обязательны в `.env` при любом наборе профилей — `install.sh`
дополняет ими `.env` на всех этапах. Этап включается как
`install.sh --stage portal` (цель `make portal`).

Пакет 0.5: `install.sh` допускает дополнительный профиль `rerank` (§3) и загружает
веса реранкера и модели речи так же, как веса основной модели и эмбеддингов;
`make check` проверяет `docker compose config` и с профилем `rerank`. Сейчас установка
знает только профили `embeddings` и `monitoring` и загружает только две модели.

## 8. Безопасность

- После проброса порта страница входа и `/v1` доступны из интернета: меры — §3.2 и §4.
- Наружу только Caddy (порты — §3.2); сервисы портала без портов на хост; `portal-db` и `qdrant` — только
  во внутренней сети `portal`.
- Размер тела запроса ограничен: точный предел держит бэкенд, внешнюю границу — Caddy.
  Для маршрутов загрузки аудио и видео предел поднят до 2 ГБ, для остальных он прежний
  (§8.1).
- Загрузка файлов: проверка типа по содержимому, лимит размера, имена файлов на диске
  генерируются сервером; путь никогда не строится из пользовательского имени файла.
- Изоляция данных пользователей — на уровне запросов (§4); покрывается тестами
  «чужой чат / чужой документ → 404», с версии 0.5 — и «чужая картинка / чужой звук /
  тег чужого личного документа».
- Ответы модели и содержимое документов отображаются как данные: HTML из Markdown
  санируется, картинки из Markdown не загружаются.
- В логи не попадают пароли, токены сессий, тексты сообщений и содержимое файлов.
- Bifrost по умолчанию сохраняет содержимое запросов в `logs.db` (`design.md` §13). Раз
  чаты личные, хранение содержимого запросов и ответов в Bifrost отключено
  конфигурацией шлюза — для всех ключей, включая ключ портала; учёт расхода и лимиты
  по ключам остаются. **Проверить на ВМ**: после запроса через портал в журнале Bifrost
  нет текста сообщений и вложений.
- Бэкап: volumes `portal-db-data`, `qdrant-data`, `portal-files` — вместе с
  `bifrost-data`. Векторы восстановимы переиндексацией, база и файлы — нет. База
  копируется дампом, а не каталогом работающего сервера; на время копирования
  пишущие сервисы останавливаются, чтобы файлы и векторы соответствовали снимку базы.
  `deploy/.env` и `caddy-data` в копию не входят и хранятся отдельно; копия содержит
  переписку и личные данные и хранится как секрет. С версии 0.5 в `portal-files` лежат
  также картинки документов и сжатый звук записей — копия растёт вместе с ними.
  Песочница SQL данных не хранит и в копию не входит; веса реранкера и модели речи —
  тоже: они восстановимы загрузкой.
- Прерванное восстановление оставляет следы, по которым его видно. Пока они есть,
  пишущие сервисы не запускаются сами: ни автозапуском стека после перезагрузки ВМ, ни
  `make up` — иначе портал заработал бы на смешанных данных (новая база со старыми
  файлами или наоборот). Причина отказа видна в журнале юнита и в выводе команды;
  выход — повторить `make restore`. Модель и точка входа при этом запускаются как обычно.
- Образы и зависимости (Python и npm) закреплены по версии; lock-файлы в репозитории.
- Журналы контейнеров ограничены по размеру и числу файлов (ротация в compose), чтобы
  диск ВМ не заполнялся.

### 8.1 Меры безопасности пакета 0.5

**Песочница SQL.** Исходная посылка: запрос и тестовые данные пишет модель, на которую
влияют текст пользователя и его схема, поэтому всё, что уходит в песочницу, считается
враждебным кодом.
- Что исполняется. Подготовка: упрощённый DDL (создание таблиц) и вставка строк —
  только в схеме этой проверки. Проверяемый запрос: ровно один оператор `SELECT` или
  DML. Вся проверка — создание схемы и таблиц, вставка строк и проверяемый запрос,
  включая `SELECT`, — идёт в транзакции, которая всегда откатывается: ни одна попытка
  ничего не фиксирует. DDL в PostgreSQL транзакционен, поэтому незафиксированные
  объекты не видны другим сеансам ни по имени, ни через каталоги, а после проверки в
  базе не остаётся ничего — в том числе побочных эффектов `SELECT` (например, large
  objects). DDL, `DROP`, `TRUNCATE`, несколько операторов и служебные команды (`SET`,
  `DO`, `COPY`, создание функций и подобные) не исполняются. Разбор запроса до
  исполнения — вторая линия защиты; первая — права роли и изоляция контейнера.
- Контейнер. Собственная внутренняя сеть без выхода наружу, в ней только `portal-api`
  и песочница; портов на хост нет. Корневая файловая система только для чтения, данные
  на tmpfs с пределом размера. Привилегии сняты (`cap_drop`, `no-new-privileges`);
  минимум, нужный для запуска СУБД, — **проверить на стенде**. Заданы пределы памяти,
  CPU и числа процессов. Секретов портала и общих томов с `portal-db` в контейнере нет.
  Журнал сервера песочницы не содержит ни текста операторов, ни значений из данных:
  запись операторов и сообщений об ошибках запросов отключена параметрами сервера
  (`log_statement`, `log_min_duration_statement`, `log_min_error_statement`,
  `log_min_messages`). По умолчанию PostgreSQL пишет в журнал текст каждого оператора,
  завершившегося ошибкой, и запросы из ответов модели вместе с DDL, выведенным из личной
  схемы, оседали бы в журнале контейнера в обход правила §8.
- Роль, под которой исполняются подготовка и запрос. Не суперпользователь; не создаёт
  роли и расширения (PostGIS ставится при инициализации); не читает и не пишет файлы
  сервера и не запускает программы (`COPY` с файлами и программами закрыт); расширений
  для обращения к другим базам нет. Объекты создаются только в схеме своей проверки;
  откат транзакции убирает схему со всем содержимым. Проверки разных пользователей не
  видят друг друга: схемы пользователей личные (§5.3). Это дают два правила. Первое:
  всё созданное проверкой живёт только в её незафиксированной транзакции (выше).
  Второе: одновременные проверки идут под разными ролями входа — ролей столько,
  сколько допускается одновременных проверок (§3.3). Под общей ролью сеанс видел бы
  текст чужого запроса в `pg_stat_activity` и мог бы снять чужой сеанс. Поведение
  PostgreSQL здесь взято из документации — **проверить на стенде** (§10, п. 18).
- Лимиты. Предел времени запроса (секунды), ожидания блокировки и простоя в
  транзакции; пределы памяти запроса и временных файлов; без параллельных
  исполнителей; предел соединений роли и не больше двух проверок одновременно (§3.3).
  Результат читается с жёстким пределом строк и байт; пользователю показывается не
  больше 50 строк. Параметры сеанса — вторая линия: роль меняет их сама, в том числе
  вызовом функции внутри обычного `SELECT`. Поэтому общий срок проверки (подготовка,
  запрос, попытки исправления) держит `portal-api`: по его истечении запрос
  отменяется, сеанс песочницы принудительно завершается на сервере, а пользователь
  видит, что проверка не уложилась во время (§5.3). На каждую проверку — отдельное
  соединение, которое после неё закрывается: настройки сеанса, временные объекты и
  блокировки следующей проверке не достаются. Пределы времени портал выставляет заново
  перед каждым недоверенным оператором. Жёсткая граница памяти и CPU — пределы
  контейнера, а не параметры сервера.
- Результат и сообщения СУБД — недоверенные данные: в интерфейсе экранируются, в
  журналы не пишутся, в цикл исправления подаются модели как данные, а не как
  инструкции.

**Аудио и видео.** Медиафайл — недоверенный ввод для ffmpeg.
- Файл принимается по белому списку контейнеров (§5.2); тип определяется по сигнатуре,
  а не по расширению. Плейлисты и «виртуальные» форматы (HLS/m3u8, concat, SDP) не
  принимаются.
- Сигнатура сама ffmpeg не ограничивает: формат он определяет собственным анализом
  содержимого. Файл с сигнатурой MP3 и телом плейлиста открывается как плейлист и
  подмешивает в результат звук соседних файлов (проверено на ffmpeg 8.0.1). Поэтому
  формат, определённый порталом, передаётся ffprobe и ffmpeg явно, а демультиплексоры
  и звуковые декодеры ограничены белыми списками; несовпадение — отказ с причиной
  «недопустимый файл». Список кодеков — в конфигурации (ориентир: AAC, MP3, Opus,
  Vorbis, FLAC, ALAC, PCM).
- ffmpeg запускается с запретом сетевых протоколов — разрешён только локальный файл.
  Воркер подключён к сети `edge`, и без запрета специально подготовленный файл мог бы
  заставить его обратиться к внутренним сервисам или прочитать посторонние файлы.
- Запуск — отдельным процессом без прав root, с пустым окружением (секреты воркера —
  пароль базы, ключи Qdrant и Bifrost — в него не попадают), с пределами времени, CPU,
  памяти и размера результата. Входной файл лежит один в пустом временном каталоге
  задания — на томе `portal-files`, отдельно от каталогов хранилища, а не в слое
  контейнера; временные файлы учитываются квотой (§3.4). Берётся только первая
  звуковая дорожка; видео и субтитры не декодируются. До расшифровки проверяются
  длительность и наличие звука; запись, не прошедшая проверку, получает понятную
  причину отказа.
- Версия ffmpeg закреплена в образе и обновляется вместе с ним.
- Загрузка. Предел тела запроса поднят до 2 ГБ только для маршрутов медиа — и в
  бэкенде, и в Caddy; остальные маршруты сохраняют прежний предел. Тело принимается
  только после проверки сессии и прав и пишется потоком сразу в том `portal-files` —
  не в память и не во временный файл в слое контейнера (так сейчас принимаются
  документы: файл формы сначала ложится на диск `/`, потом копируется в том). До приёма
  тела по заявленной длине проверяются квота на медиа и порог свободного места (§3.4):
  место под загрузку резервируется на время приёма, запрос без заявленной длины не
  принимается. Число одновременных загрузок медиа ограничено настройкой.
- Исходный файл хранится только до успешной обработки; видео не хранится (§5.2).
  Исходник записи, не прошедшей проверку (нет звука, недопустимый контейнер или
  кодек, превышена длительность), удаляется сразу. Исходник записи с ошибкой
  обработки остаётся для повторной обработки и входит в квоту; срок его хранения
  задаётся в конфигурации (§11). Недописанные загрузки и временные каталоги, оставшиеся после
  обрыва или перезапуска, удаляются при старте сервисов.

**Картинки из документов.**
- Картинка отдаётся только порталом и только с той же проверкой доступа, что и её
  документ: картинка личного документа недоступна никому, кроме владельца, включая
  администратора; после удаления документа она не отдаётся.
- Адрес картинки строит интерфейс по данным источника, пришедшим от сервера. Модель
  адресов не пишет; markdown-картинки и ссылки на картинки из текста модели не
  загружаются — это канал утечки данных на чужой сервер. CSP по-прежнему разрешает
  изображения только со своего origin (§3.2).
- Тип содержимого задаёт сервер; отдаются только растровые картинки, без SVG и HTML, с
  заголовком `X-Content-Type-Options: nosniff`.
- При извлечении действуют пределы: число картинок на документ (§5.2) и размер
  картинки в пикселях — защита от «бомб» распаковки.

**Недоверенный текст из файлов.**
- Расшифровки записей, описания картинок и текст, распознанный на картинках, —
  недоверенный ввод наравне с содержимым документов (§5.2): модели они передаются как
  данные, а не как инструкции, в интерфейсе отображаются как текст, в журналы не
  пишутся.
- Пояснения, дописанные к фрагментам (§5.2), — тоже недоверенный текст: их пишет
  модель под влиянием содержимого документа, а пользователь их не видит. Поэтому они
  используются только в поиске — в эмбеддинге, лексическом индексе и переранжировании.
  В запрос к отвечающей модели, в цитаты, в сохранённые источники и в интерфейс они не
  попадают, в журналы не пишутся.
- Обращения к модели на этапе индексации — пояснение к фрагменту, описание картинки —
  подчиняются правилу, которое уже действует для распознавания страниц: содержимое
  документа — данные, указания из него не выполняются. Длина вывода ограничена
  настройкой.
- Запрос, переписанный моделью (§5.2), используется только как текст для поиска: он не
  может изменить фильтр доступа, набор коллекций и теги.

**Фильтр доступа, «Министерства» и теги.**
- Фильтр доступа строится на сервере только из сессии: общая ∪ «Министерства» ∪ личная
  коллекция текущего пользователя. Набор коллекций и теги из запроса клиента могут его
  только сузить: ни коллекция, ни тег не заменяют фильтр и не расширяют его. Текст
  вопроса и ответ модели на фильтр не влияют.
- Права на изменение «Министерств» — добавление, удаление, повторная обработка, теги —
  проверяются на сервере по роли из сессии (§4); скрытая кнопка в интерфейсе защитой
  не считается.
- Приватность тегов. Подсказки и отбор по тегам строятся только по документам, видимым
  пользователю. Тег, который стоит только на чужих личных документах, не появляется ни
  в подсказках, ни в списках, ни в текстах ошибок — ни у сотрудника, ни у
  администратора.
- Значения тегов — пользовательский текст: отображаются как данные.

### 8.2 Обновление работающего сервиса (релиз 0.5)

Пакет выкатывается одним релизом в одно окно обслуживания. Окно объявляется
сотрудникам и владельцам ключей API заранее: портал и `/v1` в это время не работают
или работают с перерывами. Технически закрыть доступ на время окна нечем: Caddy отдаёт
один сайт на всех трёх портах (§3.2), проброс из интернета постоянный, режима
обслуживания у портала нет — вопрос в §11. Переобработка документов идёт после релиза
в фоне, на работающем сервисе.

До окна:
1. Диск ВМ расширен (§3.4): места хватает на образы, веса, медиа и восстановление из
   копии, которое разворачивает её рядом с действующими данными. Определено место для
   резервной копии вне диска `/` (§11).
2. Критерии §10 без пометки [ВМ] закрыты на стенде; отчёт `security-reviewer` по
   пакету — без блокирующих находок: сервис открыт интернету (§3.2).
3. Подготовка — отдельный шаг, который не трогает ни работающие контейнеры, ни рабочий
   клон на ВМ: загрузка образов, сборка образов портала с тегом по коммиту релиза,
   загрузка весов реранкера и модели речи. Нынешний `install.sh --stage portal` для
   этого не годится: он одной командой собирает образы, загружает веса и перезапускает
   стек. Нужен режим подготовки либо отдельный клон релизного коммита — выбирает
   `scripts-engineer`. Рабочий клон переключается на релизный коммит только в окне,
   после резервной копии: иначе `make up` или перезагрузка ВМ (юнит `llm-stack`) до
   окна подняли бы новую конфигурацию без копии и проверок.
4. До сборки новых образов работающие образы портала помечены тегом своего коммита, и
   проверено, что они есть. Сейчас такого тега у них нет: compose собирает их без
   имени образа, и новая сборка оставила бы прежние образы безымянными. Помеченные
   образы — путь отката; до закрытия релиза образы на ВМ не чистятся
   (`docker image prune` не выполняется).
5. Репетиция миграций: дамп рабочей базы загружен во временную базу на самой ВМ, и
   миграции 0.5 на нём прошли. Данные ВМ не покидают: в базе переписка и личные
   данные (§8).
6. Репетиция восстановления: `make restore` выполнен на ВМ из свежей копии, его
   длительность записана. До сих пор восстановление на ВМ не выполнялось ни разу, а
   откат на него опирается. Это отдельный короткий простой до окна релиза,
   объявленный заранее.
7. Оценена длительность переобработки (ниже).

В окне:
1. Резервная копия (`make backup`); хранится не на диске `/`. После неё рабочий клон
   переключается на релизный коммит.
2. Основная модель перезапускается с новой долей памяти (~0.81); за ней строго по
   очереди, каждый после healthcheck предыдущего, поднимаются эмбеддинги и реранкер.
   Перезапуск основной модели — минуты простоя чата и `/v1` для всех клиентов API;
   длительность **измерить на ВМ**.
3. Конфигурация Bifrost дополняется моделью реранкера; ключ портала получает к ней
   доступ.
4. Сервисы портала поднимаются из подготовленных образов, без сборки в окне; миграции
   базы применяются при старте `portal-api`, как раньше, воркер стартует после него.
   С этого момента откат возможен только восстановлением из копии (ниже). Песочница
   SQL поднимается, но проверка выключена флагом (§7).
5. Проверки после релиза (ниже). После них сотрудникам сообщают, что окно закончено.

Проверки после релиза (**[ВМ]**):
- смоук-тест стека, включая шаг «вдумчиво через шлюз» (§5.1), и смоук-тест портала.
  Смоук-тест портала дополняется шагами пакета: реранкер отвечает через Bifrost,
  контейнер песочницы здоров;
- на карте три процесса, сумма долей ≤ 0.92; ёмкость KV-кеша в журнале vLLM даёт не
  меньше 8 параллельных запросов при контексте 65 536 (`design.md` §5);
- при остановленном реранкере поиск отвечает без ошибки;
- вход, чат в обоих режимах, поиск по базе знаний, загрузка документа с тегом,
  загрузка короткой записи;
- в журнале Bifrost по-прежнему нет текста запросов (§8);
- свободное место на диске — в пределах бюджета §3.4.

Проверки изоляции песочницы на боевом compose (§10, п. 18) в окно не входят: они
выполняются позже, перед включением флага проверки SQL.

После релиза:
- Переобработка всех документов запускается после проверок и после того, как
  окончательно выбран состав флагов индексации (контекст фрагментов, описание
  картинок): иначе её пришлось бы повторять. Она полная — с повторным разбором файлов,
  а не только пересчётом векторов; ранее распознанный текст страниц-сканов
  используется повторно. Существующая команда `make portal-reindex` для этого не
  годится: она сразу возвращает все документы в очередь, и до конца обработки поиск
  их не находит, а файлы заново не разбирает. Нужен отдельный режим переобработки.
- Переобработка не убирает документ из поиска (§5.2): пока документ не переобработан,
  он доступен поиску в прежнем виде; прежние фрагменты и векторы заменяются новыми
  разом, в конце задания. Итог по каждому документу — переобработан либо
  переобработка не удалась, с причиной; во втором случае документ остаётся в поиске с
  прежним индексом.
- Переобработка идёт с низшим приоритетом и с прежним ограничением параллельности
  воркера — по одному заданию базы знаний (§5.2). Нагрузку на GPU регулируют числом
  одновременных фоновых обращений к модели (§5.2).
- Длительность оценивается до окна. По базе считаются число документов, страниц и
  символов; время ≈ (фрагменты × секунды на пояснение + картинки × секунды на
  описание) / число одновременных обращений. Ориентир до замера, при ~4 с на обращение
  и двух одновременных: документ в 100 страниц — около 230 фрагментов и порядка
  8 минут; 100 таких документов — около 13 часов, 1000 — 5–6 суток. Секунды на
  обращение **уточняются на ВМ** на первых документах.
- Проверка SQL включается флагом после того, как проверки изоляции песочницы
  повторены на боевом compose (§10, п. 18) и тестовые данные от настоящей модели
  проверены (§10, п. 17).
- Реранкер и контекст фрагментов остаются включёнными, если замер на контрольном
  наборе не показал ухудшения (§10, п. 22).

Откат:
- Сбой одной функции — выключить её флаг (§7); релиз не откатывается.
- Сбой релиза до старта нового `portal-api` (шаги 1–3 окна) — вернуть рабочий клон на
  предыдущий коммит, вернуть основной модели прежнюю долю памяти (0.85) и остановить
  реранкер. Данные портала не затронуты.
- Сбой после старта нового `portal-api`: миграции уже применены, обратных команд нет,
  поэтому откат — всегда восстановление базы и файлов из копии (`make restore`) и
  предыдущая версия портала из помеченных образов, без пересборки. Прежний compose
  помеченные образы по тегу не знает: команду отката, которая их поднимает, готовит
  `scripts-engineer`, и она проверяется до окна.
- Восстановление из копии теряет всё созданное после неё: сообщения, документы,
  учётные записи — в том числе созданное сотрудниками, которые вошли во время окна.
  Пока окно не объявлено законченным, это допустимая цена. После — сбои лечатся
  флагами и исправлениями, а восстановление из копии — крайняя мера по решению
  владельца.
- Векторы восстановимы переиндексацией (§8); база и файлы — нет.

## 9. Структура репозитория

```
portal/
├── backend/            uv-проект: FastAPI, воркер, миграции, config/*.yaml, tests/
│   └── Dockerfile
├── frontend/           React + TypeScript + Vite, тесты
│   └── Dockerfile      сборка статики → образ portal-web
└── dev/                заглушка OpenAI-совместимого API и compose для стенда без GPU
docs/
├── portal-design.md    этот документ
├── portal-api.md       контракт API и схема БД (этап 1 пайплайна)
├── portal-ui.md        концепция интерфейса (этап 1 пайплайна)
├── vpn-launch.md       запуск до привязки домена и действия после неё
├── user-guide.md       памятка сотруднику (этап 8)
└── web-search-options.md  поиск в интернете: варианты и вопросы заказчику (вне рамок, §1)
```

Слои бэкенда: домен и сценарии не зависят от FastAPI, SQLAlchemy, Qdrant и HTTP-клиента
LLM; инфраструктура подключается через внедрение зависимостей.

Стенд без GPU (`portal/dev/`): заглушка отвечает на `/v1/chat/completions` (включая
поток) и `/v1/embeddings` детерминированно. На нём идут сквозные тесты и разработка
интерфейса. Всё, что зависит от настоящей модели (качество ответов, распознавание
сканов, скорость), помечается «проверить на ВМ». Стенд поднимается, пересоздаётся с
чистой базой и останавливается целями `make`; отдельная цель запускает сквозные тесты.

Для пакета 0.5: заглушка дополняется ответом реранкера и отвечает на
`reasoning_effort: "high"` и `"xhigh"` кодом 400, как настоящая модель за шлюзом:
заглушка стоит на месте Bifrost, а он переписывает `xhigh` в `high`, поэтому возврат
ошибки ловят тесты стенда; на ВМ то же проверяет шаг смоук-теста (§10, п. 15). Песочница SQL на
стенде настоящая: GPU ей не нужен, и её изоляция проверяется тестами там же. Извлечение
звука (ffmpeg) на стенде настоящее; чем заменить на стенде модель речи —
детерминированной подменой или настоящей моделью на CPU — решает исполнитель. Качество
описаний картинок, расшифровки речи, переранжирования и скорость — «проверить на ВМ».

## 10. Критерии приёмки

Отдельного документа с критериями нет; критерии — этот список.

1. Сотрудник входит по выданным логину и временному паролю, меняет пароль, настраивает
   второй фактор и попадает в чат; следующий вход требует пароль и код. Без кода, с
   неверным или повторно использованным кодом входа нет; резервный код срабатывает один раз.
2. Администратор создаёт, блокирует пользователя, сбрасывает пароль и второй фактор;
   заблокированный теряет доступ сразу. Серия неудачных входов временно блокирует логин;
   администратор снимает эту блокировку, и сотрудник входит с прежним паролем и кодом.
3. Чат отвечает потоково, принимает изображение и PDF, хранит историю между входами.
4. Документ, загруженный одним сотрудником в общую базу, находится в ответах другого;
   ответ содержит источник с документом, страницей и цитатой.
5. Скан без текстового слоя после загрузки в базу знаний находится поиском. **[ВМ]**
6. Личный документ и чужой чат недоступны другому пользователю и администратору
   (проверка через API).
7. SQL-помощник пишет запрос по выбранной схеме, объясняет чужой запрос, предупреждает
   об опасной операции.
8. Помощник CoGIS отвечает со ссылками на загруженную документацию.
9. Разбор документа возвращает таблицу реквизитов по шаблону. **[ВМ]** — на реальных сканах.
10. Ответ экспортируется в DOCX и открывается в Word.
11. Светлая и тёмная темы работают на всех экранах; все тексты на русском.
12. Через Caddy без сессии доступны только страница входа и статика; маршруты API под
    `/v1/` требуют ключ, остальное под `/v1/` — 404;
    админ-API Bifrost и `/metrics` недоступны.
13. Портал работает по `https://192.168.25.8` из VPN (до домена) и по
    `https://llm.<домен>[:порт]` из интернета (после) без изменения данных и конфигурации
    портала; ответы содержат заголовки безопасности из §3.2. **[ВМ]**
14. `make check` зелёный: линтеры, типы, тесты бэкенда и фронтенда, `docker compose config`.

Критерии пакета 0.5:

15. Режим «Вдумчиво»: запрос портала к модели не содержит `reasoning_effort` (тест
    полезной нагрузки); «Быстро» по-прежнему передаёт `low`. Через шлюз ответ в режиме
    «Вдумчиво» приходит с размышлениями; шаг смоук-теста «вдумчиво через шлюз» зелёный.
    **[ВМ]** — часть про шлюз.
16. Экран SQL: «Диалект», «Схема базы», «Мои схемы» и переключатель проверки — в строке
    заголовка справа; выбор режима — под полем ввода; экран работает в обеих темах;
    экран помощника CoGIS не изменился.
17. Проверка SQL: при включённой проверке и выбранной схеме под блоком кода появляется
    статус с тестовыми данными и результатом не больше 50 строк; запрос с ошибкой
    исполнения исправляется не больше двух раз и помечается «исправлено»; `UPDATE` и
    `DELETE` не оставляют изменений; DDL, `DROP`, `TRUNCATE` и несколько операторов
    получают «не проверялось»; без схемы переключатель неактивен; при остановленной
    песочнице ответ приходит со статусом «проверка недоступна»; при выключенном флаге
    переключателя нет. **[ВМ]** — тестовые данные от настоящей модели покрывают
    условия запроса.
18. Изоляция песочницы (тесты на стенде): из неё нет соединения ни с `portal-db`, ни с
    Bifrost, ни наружу; роль не читает файлы сервера, не запускает программы и не
    создаёт расширения; запрос дольше предела времени и запрос с неограниченным
    результатом прерываются — в том числе когда подготовка или сам запрос снимают
    предел времени; проверка, не уложившаяся в общий срок, завершается, и её сеанса на
    сервере не остаётся; во время идущей проверки другому пользователю недоступны её
    таблицы по полному имени, её объекты в каталогах, текст её запроса в
    `pg_stat_activity` и снятие её сеанса; после проверки в базе нет её объектов,
    включая large objects; после запроса с ошибкой и запроса, прерванного по времени,
    в журнале контейнера песочницы нет текста запроса и данных. **[ВМ]** — проверки
    сети, прав роли и лимитов повторяются на боевом compose до включения флага
    проверки (§8.2).
19. «Министерства»: документ, добавленный администратором, находится в ответе
    сотрудника при выбранной коллекции и не участвует в поиске, когда она не выбрана;
    сотрудник не может добавить или удалить документ этой коллекции, отправить его на
    повторную обработку и сменить его теги (проверка через API); при загрузке
    коллекция предлагается только администратору; на экране базы знаний есть вкладка
    «Министерства», доступная всем на чтение.
20. Теги: документ загружается с тегами; при выбранных в чате тегах источниками
    становятся только документы с любым из них; смена тегов действует на поиск без
    повторной обработки документа; тег без учёта регистра и краевых пробелов считается
    одним; одиннадцатый тег и тег длиннее 50 символов не принимаются; в общей базе
    теги чужого документа сотрудник сменить не может, автор и администратор — могут
    (проверка через API); список документов на экране базы знаний отбирается по тегу;
    подсказки не содержат тегов чужих личных документов (проверка через API, в том
    числе от имени администратора).
21. Картинки: картинка из DOCX и из PDF находится по своему описанию; ответ со сноской
    на неё показывает картинку под ответом и в карточке источника; картинка ниже
    порога не сохраняется; картинка личного документа другому пользователю не отдаётся
    (проверка через API); markdown-картинка из текста модели не загружается.
    **[ВМ]** — качество описаний на реальных документах.
22. Поиск: уточняющий вопрос без названия предмета находит документ из предыдущего
    хода диалога; документ с заголовками и статьями разбит по их границам; цитата в
    источнике дословна и не содержит ни строки «Документ: … / Раздел: …», ни
    дописанного пояснения; запрос по названию раздела находит фрагмент, в тексте
    которого этих слов нет; в запрос к модели вместе с найденным фрагментом попадает
    соседний фрагмент того же документа, а пояснение не попадает; при включённом флаге
    контекста фрагмент находится по слову из пояснения, при выключенном индексируется
    без пояснения; после реранкера в выдаче не больше 8 фрагментов, и точное
    совпадение (кадастровый номер) остаётся в ней при низкой оценке реранкера; при
    выключенном и при недоступном реранкере поиск отвечает без ошибки. **[ВМ]**: на
    расширенном контрольном наборе метрики (recall@k кандидатов, nDCG и MRR после
    реранкера) измерены до и после каждого улучшения и не ухудшились.
23. Записи в базе знаний: аудио- и видеозапись на русском после загрузки находится
    поиском; источник показывает таймкод, запись проигрывается с этого момента;
    исходное видео после обработки на диске не остаётся. **[ВМ]** — качество
    расшифровки на реальных записях и время обработки трёхчасовой записи.
24. Записи в чате и отказы: короткая запись во вложении попадает в вопрос текстом; пока
    расшифровка не готова, отправка недоступна; файл больше 2 ГБ, запись длиннее
    3 часов (в чате — длиннее предела вложения), файл с недопустимым контейнером,
    плейлист и файл с разрешённой сигнатурой, но телом плейлиста отклоняются с
    объяснением; загрузка сверх квоты на медиа отклоняется — в том числе параллельные
    загрузки, которые превышают квоту только вместе.
25. Релиз (§8.2): на стенде документ, который переобрабатывается, и документ, чья
    переобработка не удалась, находятся поиском в прежнем виде. **[ВМ]**: проверки
    после релиза пройдены; все документы переобработаны либо имеют понятную причину
    сбоя; во время переобработки чат отвечает, а поиск находит ещё не переобработанные
    документы.

## 12. Решения 0.5, принятые по предложению оркестратора

Решения ниже предложены оркестратором и записаны в разделах выше наравне с решениями
владельца. Владелец подтвердил их 2026-10-11.

Экран SQL и проверка на тестовых данных:
1. Выбор режима — в строке управления панели запроса, как «Быстро / Вдумчиво» в чате (§6).
2. Экран помощника CoGIS не меняется (§6).
3. Переключатель «Проверять на тестовых данных» — в строке заголовка, рядом со схемой (§6).
4. Общий флаг проверки в конфигурации, по умолчанию выключен; при выключенном флаге
   сервис песочницы не обязателен (§3.3, §7).
5. Проверка доступна только при выбранной сохранённой схеме; без схемы переключатель
   неактивен с объяснением (§5.3).
6. Образ песочницы — свой, на `postgres` того же тега, что `portal-db`
   (`16.15-bookworm`), с пакетом PostGIS (§3.3).
7. Проверки исполняет `portal-api`, не больше двух одновременно; сбой песочницы не
   ломает ответ — «проверка недоступна» (§3.3, §5.3).
8. Пустой результат — предупреждение «данные не покрыли условия» без исправления
   запроса; план запроса не показывается; постоянная оговорка, что проверка не
   доказывает правильность (§5.3).

«Министерства» и теги:
9. Выбор базы знаний в чате — набор коллекций из «Общая», «Моя», «Министерства»; пустой
   набор — без базы знаний (§5.1).
10. Справочника министерств нет; внутри коллекции документы размечаются тегами (§5.2).
11. На экране базы знаний — третья вкладка «Министерства» (§6).
12. Теги: пробелы по краям отбрасываются, регистр не различается; не больше 10 тегов на
    документ, тег не длиннее 50 символов (§5.2).
13. Отбор по тегам есть и на экране базы знаний, в списке документов (§5.2, §6).
14. Смена тегов обновляет индекс без повторной обработки документа (§5.2).
15. Подсказки показывают только теги документов, видимых пользователю (§5.2, §8.1).

Картинки:
16. Пороги: картинка отбрасывается, если меньшая сторона короче 100 px или площадь
    меньше 20 000 px²; не больше 50 картинок на документ; одинаковые картинки внутри
    документа считаются одной (§5.2).
17. Картинка видна и в просмотре источника (§5.2, §6).
18. В экспорт DOCX картинки в этой версии не попадают (§5.6).

Качество поиска:
19. Портал обращается к реранкеру через Bifrost (`/v1/rerank`), проверить на ВМ;
    запасной вариант — отдельная внутренняя сеть между порталом и реранкером (§3.3).
20. Модель эмбеддингов не меняется — `Qwen3-Embedding-0.6B` (§5.2).
21. Реранкер и контекст фрагментов включаются флагами; при недоступности реранкера
    поиск работает в прежнем порядке, без ошибки (§3.3, §5.2, §7).

Аудио и видео:
22. Форматы: MP3, WAV, M4A, OGG, FLAC, MP4, MKV, WebM, MOV; звук извлекает ffmpeg в
    образе воркера с мерами защиты — белый список контейнеров по сигнатуре, запрет
    плейлистов и сетевых протоколов, пределы времени и ресурсов (§5.2, §8.1).
23. При загрузке записи в базу знаний коллекция по умолчанию — личная (§5.2).
24. Расшифровка вложения чата идёт в фоне через очередь воркера; пока она не готова,
    сообщение с этим вложением отправить нельзя (§5.1).
25. Потоки CPU под распознавание речи ограничены настройкой, по умолчанию 8 (§3.3, §3.4).

Раскатка:
26. Перед релизом — резервная копия и образы портала с тегом по коммиту; путь отката —
    предыдущий коммит и копия; новые функции — за флагами конфигурации, чтобы сбой
    одной не требовал отката релиза (§7, §8.2).

Уточнения оркестратора сверх решений владельца. Их нет в решениях владельца ни как
выбранных, ни как предложенных по умолчанию; в разделах выше они записаны как решения
и подтверждены вместе с остальными:
27. Исходный файл аудиозаписи после успешной обработки удаляется, как и видео:
    хранится только сжатый звук, ссылки «Открыть оригинал» у записи нет (§5.2, §8.1).
28. Порядок очереди: вложения чата — раньше индексации базы знаний и на отдельном
    месте воркера, не дожидаясь идущего длинного задания; новые загрузки — раньше
    массовой переобработки, на границе заданий; дописывание контекста — отдельный этап
    порциями. Предел потоков распознавания речи (8) общий на оба места (§3.4, §5.2).
29. В «Министерствах» нет отметки «документация CoGIS»: помощник CoGIS по этой
    коллекции не ищет (§5.2, §5.4).
30. Право вести «Министерства» даёт текущая роль, а не авторство: администратор,
    ставший сотрудником, теряет его и для своих документов (§4).
31. Теги личного документа меняет только владелец (§4).
32. Итог проверки SQL сохраняется в истории вместе с ответом (§5.3).
33. Отдельные флаги «Переписывание запроса», «Описание картинок» и «Приём аудио и
    видео» — сверх флагов реранкера и контекста фрагментов из решений владельца (§7).
34. Пояснение к фрагменту используется только в поиске и отвечающей модели не
    передаётся; для пояснения модель получает ограниченное окно, а не документ
    целиком (§5.2, §8.1).
35. Проверка SQL, не уложившаяся в общий срок, обрывается; пользователь видит, что она
    не уложилась во время (§5.3, §8.1).
36. Медиа: запись со звуковым кодеком вне белого списка отклоняется; квота считает все
    байты медиа, включая исходники с ошибкой обработки и идущие загрузки; ниже порога
    свободного места медиа не принимается; число одновременных загрузок ограничено
    (§3.4, §8.1).
37. Переобработка не убирает документ из поиска; документ, чья переобработка не
    удалась, остаётся в поиске в прежнем виде с отметкой о сбое (§5.2, §8.2).
38. Релиз: подготовка отдельным шагом без изменения рабочего клона; репетиция миграций
    на копии базы на самой ВМ; репетиция восстановления — отдельный короткий простой
    до окна релиза (вариант — в начале самого окна, сразу после копии); после старта
    нового `portal-api` откат — только восстановлением из копии (§8.2).

Технические меры, добавленные по итогам ревью проекта дизайна, решений владельца не
меняют и здесь не перечислены: изоляция проверок песочницы и её журнал (§8.1), запуск
ffmpeg (§8.1), профили compose и установка (§3, §7), метки образов для отката (§8.2).
