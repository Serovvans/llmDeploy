## 1. Цель и пользователи

Веб-интерфейс к LLM-сервису для сотрудников заказчика. Они строят ГИС на базе CoGIS и
решают задачи земельно-имущественных отношений; это не программисты, но им приходится
писать SQL-скрипты и плагины CoGIS на C#. Портал даёт им чат с моделью, общую базу
знаний компании и три прикладных инструмента — без API-ключей, терминала и настройки.

**В рамках первой версии:**
- вход по логину, паролю и одноразовому коду из приложения-аутентификатора (TOTP);
  учётные записи создают администраторы;
- чат с моделью: потоковые ответы, вложения, история;
- база знаний (RAG): общая, пополняемая всеми сотрудниками, и личная у каждого;
  ответы со ссылками на источники; сканы распознаются при загрузке;
- инструменты: SQL-помощник, помощник по плагинам CoGIS (C#), разбор документов и сканов;
- экспорт ответа и диалога в DOCX;
- светлая и тёмная темы, интерфейс на русском, дизайн-система Контур.

**Вне рамок** (не делаем, пока не внесено сюда): самостоятельная регистрация, SSO,
восстановление пароля по почте или SMS, статистика использования для администраторов, библиотека шаблонов запросов, выполнение
SQL на базах заказчика, компиляция C#, поиск в интернете, мобильное приложение,
интерфейс на других языках, совместные чаты.

## 2. Принятые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Основа интерфейса | Свой портал: React + TypeScript + `@skbkontur/react-ui` | Требование дизайнера (Контур); готовые чаты (Open WebUI) его не выполняют и не дают своих инструментов |
| Запасная дизайн-система | Apple HIG — не используется | `@skbkontur/react-ui` 6.4.2: MIT, React ≤ 19, тёмная тема есть |
| Размещение | Та же ВМ с GPU, compose-профиль `portal`, за тем же Caddy | Один сервер и один бэкап; эмбеддинги рядом |
| Бэкенд | Python, FastAPI, uv | Тот же стек, что `scripts/` |
| Данные | PostgreSQL (пользователи, чаты, документы, очередь) + Qdrant (векторы) | Выбор заказчика |
| Путь к модели | Через Bifrost по docker-сети, отдельный virtual key портала | Единый учёт и лимиты; vLLM остаётся за gateway |
| Доступ до домена | Только из VPN: HTTPS по IP ВМ, `TLS_MODE=internal` | Не зависит от сисадмина и DNS; пароли не идут открытым текстом |
| Доступ после проброса порта | Из интернета по домену, без VPN (и портал, и `/v1`) | Выбор заказчика: сотрудники работают без VPN |
| Второй фактор | TOTP обязателен для всех учётных записей с первого входа | Страница входа открыта интернету; пароль, выданный вручную, — слабая единственная защита |
| База знаний | Любой сотрудник добавляет сразу в общую; плюс личная коллекция | Выбор заказчика; удалить документ может автор или администратор |
| Приватность | Чаты личные: администратор не видит переписку | Выбор заказчика |
| Git | Агенты работают в ветке `feat/portal`, коммит на этап; в `main` сливает человек | Выбор заказчика |

## 3. Архитектура

```
 Браузер сотрудника (до домена — из VPN, после проброса порта — из интернета)
        │ HTTPS :443
        ▼
 ┌────────────────────────────── ВМ ──────────────────────────────────────────┐
 │ Caddy ── /v1/*  ─▶ bifrost:8080                              [gateway]     │
 │       ── /api/* ─▶ portal-api:8000                           [portal]      │
 │       ── прочее ─▶ portal-web:8080 (статика SPA)             [portal]      │
 │                                                                            │
 │ portal-api (FastAPI) ──┬─▶ portal-db (PostgreSQL)                          │
 │ portal-worker ─────────┼─▶ qdrant                                          │
 │   (индексация, OCR)    ├─▶ volume portal-files (оригиналы документов)      │
 │                        └─▶ bifrost:8080 /v1/chat/completions, /v1/embeddings│
 │                                 └─▶ vllm (default), vllm-embed (embeddings)│
 └────────────────────────────────────────────────────────────────────────────┘
```

Сервисы профиля `portal`:

| Сервис | Образ | Назначение | Порты на хост |
|---|---|---|---|
| `portal-web` | свой, статика SPA на `caddy` | Отдаёт собранный фронтенд | нет |
| `portal-api` | свой, `portal/backend` | REST + SSE, авторизация, чат, инструменты | нет |
| `portal-worker` | тот же образ, другая команда | Очередь индексации: разбор, OCR, эмбеддинги | нет |
| `portal-db` | `postgres`, точный тег | Реляционные данные и очередь заданий | нет |
| `qdrant` | `qdrant/qdrant`, точный тег | Векторный индекс | нет |

Правила:
- Профиль `portal` требует `gateway` и `embeddings`; `install.sh` отказывается включать
  его без них.
- Ни один сервис портала не публикует порты на хост. Наружу по-прежнему только 443.
- Docker-сети: `portal-api` — в `edge` (Caddy, Bifrost) и новой `portal`
  (`portal-db`, `qdrant`); `portal-worker` — в `edge` (только ради Bifrost) и `portal`;
  `portal-db` и `qdrant` — только в `portal`. В сеть `inference` портал не входит.
- Портал и API живут на одном origin, поэтому CORS не настраивается, а имя хоста в
  конфигурации портала не участвует: смена IP на домен не требует правок портала.
- Без профиля `portal` Caddy ведёт себя как сейчас: всё, кроме `/v1/*`, — 404
  (выбор сниппета по переменной, как уже сделано для `TLS_MODE`).
- `/api/*` через 443 теперь принадлежит порталу. Админ-API Bifrost
  (`/api/governance/*`) и `/metrics` через 443 по-прежнему недоступны: у портала таких
  маршрутов нет, он отвечает 404. Смоук-тест обвязки обновляется под это.
- Очередь заданий — таблица в PostgreSQL (`SELECT … FOR UPDATE SKIP LOCKED`), без
  Redis/Celery.
- Оригиналы файлов — в volume `portal-files`, без объектного хранилища.

### 3.1 Доступ по IP до привязки домена

`LLM_HOSTNAME=192.168.25.8`, `TLS_MODE=internal`: Caddy выпускает сертификат на IP из
собственного CA. Клиент, обращающийся по IP, не передаёт SNI, а внутри контейнера
локальный адрес соединения — адрес docker-сети, поэтому Caddy не найдёт сертификат сам.
В глобальные опции Caddyfile добавляется `default_sni {$LLM_HOSTNAME}` — для доменного
имени опция безвредна. **Проверить на ВМ.** Запасной вариант, если не заработает:
временное имя через файл `hosts` на тестовых ПК.

### 3.2 Доступ из интернета после проброса порта

`LLM_HOSTNAME=llm.<домен>`, `TLS_MODE=corp`, сертификат Let's Encrypt по DNS-01
(`docs/domain-setup.md` §3). A-запись указывает на внешний IP, сисадмин пробрасывает
внешний порт (443 или 18443 — решает он) на 443 ВМ. Портал работает на любом внешнем
порте: он живёт на одном origin с API и адрес в его конфигурации не участвует. Порядок
действий — `docs/vpn-launch.md`, часть B.

Следствия публичного доступа:
- второй фактор обязателен (§4), ограничение перебора — по логину и по адресу клиента;
- Caddy выставляет заголовки безопасности: HSTS, `Content-Security-Policy` (только свой
  origin), запрет встраивания во фреймы, `X-Content-Type-Options`, `Referrer-Policy`.
  Единственное послабление CSP — `'unsafe-inline'` в `style-src`: `@skbkontur/react-ui`
  вставляет стили во время работы. Скрипты, изображения, шрифты и соединения — только
  свой origin. Ответы портала сжимаются (бандл интерфейса — сотни килобайт);
- адрес клиента бэкенд берёт из `X-Forwarded-For`, которому доверяет только от Caddy.
  Если роутер при пробросе подменяет адрес источника своим, все внешние клиенты будут
  выглядеть одним адресом — тогда ограничение по адресу бесполезно и остаётся
  ограничение по логину. **Проверить на ВМ**;
- документация API бэкенда (`/docs`, `/openapi.json`) и служебные маршруты через Caddy
  недоступны;
- до проброса порта должны быть закрыты блокирующие находки `security-reviewer`.

## 4. Учётные записи и доступ

- Роли: `admin` (владелец проекта и гендиректор) и `employee`.
- Первый администратор создаётся командой на ВМ (CLI бэкенда, цель `make`), остальные
  учётные записи — в интерфейсе администратора.
- Администратор: создаёт пользователя (ФИО, логин, роль) и получает одноразовый
  временный пароль; меняет ФИО и роль другого пользователя (логин не меняется, удаления
  учётных записей нет); сбрасывает пароль; блокирует и разблокирует; удаляет любой документ
  общей базы знаний. Содержимое чатов и личных коллекций ему недоступно — ни в
  интерфейсе, ни через API.
- При первом входе и после сброса пользователь обязан сменить пароль.
- Пароли: Argon2id; минимальная длина (не меньше 12 символов) и прочие параметры — в
  конфигурации; пароли из списка распространённых отклоняются.
- Второй фактор (TOTP) обязателен для всех и включён с самого начала, в том числе на
  этапе теста в VPN: при первом входе после смены пароля пользователь сканирует QR-код
  приложением-аутентификатором (Яндекс Ключ, Google Authenticator и т. п.), подтверждает
  кодом и получает одноразовые резервные коды. Пока второй фактор не настроен, доступа
  к порталу нет. QR-код формируется самим порталом, без внешних сервисов.
- Секрет TOTP хранится зашифрованным (ключ — `PORTAL_SECRET_KEY`), резервные коды — в
  виде хешей. Использованный код повторно не принимается.
- Сброс второго фактора: администратор — сотруднику; администратору — другой
  администратор или команда на ВМ. После сброса настройка проходит заново.
- Сессия ограничена по общему времени жизни и по времени бездействия (значения — в
  конфигурации).
- Сессии: случайный непрозрачный токен, в БД хранится его хеш; cookie `HttpOnly`,
  `Secure`, `SameSite=Strict`. Блокировка пользователя и смена пароля гасят его сессии.
  Уже идущий ответ модели обрывается при любом завершении сессии: блокировка, сброс
  пароля или второго фактора, смена роли, выход, смена пароля.
  Изменяющие запросы дополнительно требуют заголовок, который не может выставить чужой
  сайт (защита от CSRF).
- Ограничение перебора: после N неудачных попыток подряд (пароль или код) — временная
  блокировка входа для логина с нарастающей задержкой; отдельно — ограничение частоты
  попыток с одного адреса (значения — в конфигурации). Ответ на неверный логин и на
  неверный пароль одинаков по тексту и времени.
- Сброс пароля или второго фактора администратором снимает временную блокировку входа
  для логина.
- Журнал аудита: входы, неудачные входы, смена пароля самим пользователем, действия
  администратора, загрузка и удаление документов. Без текста сообщений и содержимого файлов. Журнал читается командой на
  ВМ; экрана в интерфейсе нет.
- Каждая выборка чатов, сообщений, вложений, личных документов фильтруется по владельцу
  на уровне запроса к БД и к Qdrant, а не в интерфейсе.

## 5. Функциональность

### 5.1 Чат

- Потоковый ответ (SSE), остановка генерации, повторная генерация последнего ответа.
- История: список чатов, переименование, удаление; название нового чата предлагает модель.
- Вложения: изображения, PDF, DOCX, TXT/MD. Изображения и страницы сканов передаются
  модели как картинки (не более 8 на запрос — лимит vLLM), текст — как текст.
  Вложение, в котором больше 8 изображений или страниц скана, отклоняется с
  объяснением; первые 8 страниц молча не берутся.
- Режим ответа: «Быстро» и «Вдумчиво» — `reasoning_effort` `low` и `xhigh`
  (значение `high` у Qwen3.8 даёт HTTP 500, `design.md` §3.1). Размышления модели
  показываются свёрнутым блоком.
- Переключатель базы знаний: «Не использовать» / «Общая» / «Общая и моя». По умолчанию —
  «Не использовать»; последний выбор запоминается в браузере.
- Markdown, таблицы, подсветка кода, кнопка «Скопировать» у блоков кода.
- Экспорт ответа или всего диалога в DOCX (§5.6).
- Портал сам следит за длиной контекста (65 536 токенов): при переполнении старые
  сообщения отбрасываются, пользователю показывается заметка об этом.

### 5.2 База знаний (RAG)

- Коллекции: общая (видят все) и личная (видит только владелец). При загрузке
  пользователь выбирает, куда положить документ; общий документ сразу доступен всем.
- При добавлении в общую базу документ можно пометить как документацию CoGIS (§5.4).
  Отметку ставит любой сотрудник; после добавления она не меняется.
- У документа видны название, автор, дата, число страниц, статус индексации
  («в очереди», «обрабатывается», «готов», «ошибка» с понятной причиной). Документ с
  ошибкой автор или администратор может отправить на повторную обработку без
  повторной загрузки; интерфейс предлагает это, когда повтор может помочь (сбой
  распознавания, внутренняя ошибка), иначе ведёт к замене файла. У DOCX, TXT и MD
  страниц нет: число страниц и страница в источнике для них не показываются.
- Удаление: автор или администратор. Удаляются оригинал, фрагменты и векторы.
  Карточки источников с цитатами в прежних ответах остаются, но документ по ним
  больше не открывается.
- Форматы: PDF (с текстовым слоем и сканы), DOCX, TXT/MD, изображения JPG/PNG.
  Повторная загрузка того же файла в ту же коллекцию распознаётся по хешу содержимого.
- Обработка — в `portal-worker`: извлечение текста → для страниц без текстового слоя
  распознавание основной моделью (зрение) → разбиение на фрагменты с сохранением номера
  страницы → эмбеддинги (`model="embeddings"` через Bifrost) → запись в Qdrant.
- Распознавание сканов занимает GPU основной модели, поэтому число одновременных
  заданий воркера ограничено конфигурацией: чат не должен заметно замедляться.
- Поиск — гибридный: векторный плюс лексический (кадастровые номера, номера
  документов, фамилии нужно находить по точному совпадению), объединение результатов.
  Фильтр доступа (общая ∪ личная текущего пользователя) накладывается в самом запросе к
  Qdrant.
- Ответ содержит пометки-ссылки; под ответом — карточки источников: документ,
  страница, цитата. По клику открывается документ на нужной странице: распознанный
  текст страницы с подсвеченной цитатой и ссылка «Открыть оригинал» в новой вкладке;
  встроенного просмотра PDF и сканов в портале нет. Если в базе ничего подходящего не
  нашлось, модель так и говорит, а не выдумывает.
- Содержимое документов — недоверенный ввод: оно передаётся модели как данные, а не как
  инструкции, и не может менять системные правила инструмента.
- Качество поиска проверяется на небольшом контрольном наборе вопросов (русский язык,
  юридические и технические тексты); на нём же сравниваются `Qwen3-Embedding-0.6B` и
  `bge-m3` (`design.md` §3.6).
- Библиотека разбора PDF — с разрешительной лицензией (`pypdfium2`); PyMuPDF (AGPL) не
  используется.

### 5.3 SQL-помощник

- Действия: «Написать запрос», «Объяснить запрос», «Найти ошибку», «Оптимизировать».
- Диалект выбирается из списка в конфигурации (по умолчанию PostgreSQL + PostGIS).
- Пользователь может сохранить схему своей базы (DDL или описание таблиц) и выбрать её —
  она подставляется в контекст. Схемы личные.
- Сгенерированный запрос проходит синтаксическую проверку (`sqlglot`); опасные операции
  (`DROP`, `TRUNCATE`, `UPDATE`/`DELETE` без `WHERE`) подсвечиваются предупреждением.
  Запрос, который вставил сам пользователь, проверяется на опасные операции; итог
  синтаксической проверки под ним не показывается — синтаксис разбирает модель.
  Запросом в вопросе считается блок кода или текст, начинающийся с ключевого слова SQL.
- Портал **не выполняет** SQL и не подключается к базам заказчика.
- Своя сохраняемая история запросов и уточняющие вопросы в режиме диалога, как в чате.

### 5.4 Помощник по плагинам CoGIS (C#)

- Действия: «Написать плагин», «Объяснить код», «Разобрать ошибку сборки».
- Отвечает с опорой на документы общей базы знаний, помеченные как документация CoGIS;
  источники показываются так же, как в чате.
- Код не компилируется и не запускается порталом.
- Своя сохраняемая история запросов и уточняющие вопросы в режиме диалога, как в чате.
- Зависимость от заказчика: документация и примеры плагинов CoGIS должны быть загружены
  в базу знаний; без них помощник работает на общих знаниях модели и предупреждает об этом.

### 5.5 Разбор документов и сканов

- Загрузка скана, PDF, DOCX или фото → выбор шаблона: «Выписка ЕГРН», «Договор
  аренды», «Постановление / распоряжение», «Произвольный документ».
- Результат: таблица извлечённых реквизитов (структурированный вывод по JSON-схеме
  шаблона), краткое содержание, затем вопросы по документу в режиме диалога.
- Шаблоны (поля и их описания) — в YAML-конфигурации, новые добавляются без правки кода.
- Реквизит, которого нет в документе, остаётся пустым, а не придумывается; рядом с
  таблицей — напоминание сверить значения с оригиналом.
- Многостраничные сканы обрабатываются пачками по 8 страниц: пачка — единица хода,
  модели уходит один запрос на страницу. Изображения — JPG и PNG; HEIC не принимается.
- Разбор идёт внутри запроса, не в очереди: до появления таблицы вкладку нельзя
  закрывать. Оборванное краткое содержание заново не формируется.
- Своя сохраняемая история разборов, как в чате. Разбор сохраняется, как только
  получена таблица реквизитов: сбой или остановка на кратком содержании её не стирают.

### 5.6 Экспорт в DOCX

Формируется на сервере (`python-docx`): заголовки, списки, таблицы, блоки кода.
Экспортируется один ответ или диалог целиком.

## 6. Интерфейс

Задание дизайнера: дизайн-система Контур, интерфейс удобный, интуитивный, оригинальный и
впечатляющий, светлая и тёмная темы, русский язык.

- Библиотека: `@skbkontur/react-ui` (закреплённая версия) и её официальные пакеты
  иконок. Свои компоненты — только там, где в библиотеке нет подходящего (лента
  сообщений, карточки источников, просмотр документа), и на токенах темы Контура.
- Темы: светлая и тёмная средствами библиотеки; по умолчанию — как в системе,
  переключатель в интерфейсе, выбор запоминается.
- Все тексты на русском, включая ошибки, пустые состояния и подсказки. Никакого жаргона:
  «база знаний», а не «RAG»; «источники», а не «чанки».
- Шрифты и все ресурсы раздаются с портала: внешних CDN нет (ВМ может быть без
  интернета). Фирменный шрифт Контура (Lab Grotesque) используется только если это
  позволяет его лицензия; иначе — свободный шрифт с кириллицей. Лицензия не позволяет:
  используются Golos Text и JetBrains Mono (для кода).
- Акцентный цвет — нейтральный, как у ссылок и кнопок самой библиотеки; сноски
  выделяются формой, а не цветом.
- Название в интерфейсе — «Портал сотрудников». Чат — лента-протокол со сносками на
  источники, без «пузырей».
- Логотипы и название «Контур» в интерфейсе не используются: берётся библиотека
  компонентов, а не бренд.
- Экраны: вход, ввод кода, смена пароля, настройка второго фактора, чат, база знаний, SQL-помощник, помощник CoGIS, разбор
  документов, администрирование (пользователи), профиль.
- Списки документов базы знаний и пользователей: отбор по тексту и сортировка.
- Концепцию (структура экранов, навигация, «фирменные» решения, состояния) до начала
  вёрстки описывает `docs/portal-ui.md`; её утверждает человек.
- Рабочее разрешение — настольный браузер от 1280 px; на узком экране интерфейс не
  ломается, но отдельная мобильная версия не делается.

## 7. Конфигурация и секреты

Параметры приложения — YAML в `portal/backend/config/`, читаются одним классом
настроек: лимиты размера файлов, параметры разбиения и поиска, число заданий воркера,
политика паролей и блокировок, диалекты SQL, шаблоны разбора документов, системные
промпты инструментов. YAML вшит в образ; поверх него накладывается необязательный
файл `/etc/portal/config.override.yaml` (им стенд задаёт короткие блокировки для тестов).

Новые переменные `deploy/.env` (все — секреты, обязательны при профиле `portal`):

| Переменная | Назначение |
|---|---|
| `PORTAL_DB_PASSWORD` | Пароль PostgreSQL портала |
| `PORTAL_LLM_API_KEY` | Virtual key Bifrost для портала (`make key NAME=portal`) |
| `QDRANT_API_KEY` | Ключ доступа к Qdrant |
| `PORTAL_SECRET_KEY` | Шифрование секретов TOTP в БД; копия — вне ВМ, без неё второй фактор всем придётся настраивать заново |

`COMPOSE_PROFILES` получает значение `portal`, а `SITE_MODE` — значение `portal`
(`api` по умолчанию: всё, кроме `/v1/*`, — 404); обе выставляет установка этапа.
Секреты портала обязательны в `.env` при любом наборе профилей — `install.sh`
дополняет ими `.env` на всех этапах. Этап включается как
`install.sh --stage portal` (цель `make portal`).

## 8. Безопасность

- После проброса порта страница входа и `/v1` доступны из интернета: меры — §3.2 и §4.
- Наружу только 443; сервисы портала без портов на хост; `portal-db` и `qdrant` — только
  во внутренней сети `portal`.
- Размер тела запроса ограничен: точный предел держит бэкенд, внешнюю границу — Caddy.
- Загрузка файлов: проверка типа по содержимому, лимит размера, имена файлов на диске
  генерируются сервером; путь никогда не строится из пользовательского имени файла.
- Изоляция данных пользователей — на уровне запросов (§4); покрывается тестами
  «чужой чат / чужой документ → 404».
- Ответы модели и содержимое документов отображаются как данные: HTML из Markdown
  санируется.
- В логи не попадают пароли, токены сессий, тексты сообщений и содержимое файлов.
- Bifrost по умолчанию сохраняет содержимое запросов в `logs.db` (`design.md` §13). Раз
  чаты личные, логирование содержимого в Bifrost для ключа портала должно быть
  отключено либо этот факт явно принят заказчиком — **проверить на ВМ**, открытый вопрос.
- Бэкап: volumes `portal-db-data`, `qdrant-data`, `portal-files` — вместе с
  `bifrost-data`. Векторы восстановимы переиндексацией, база и файлы — нет.
- Образы и зависимости (Python и npm) закреплены по версии; lock-файлы в репозитории.

## 9. Структура репозитория

```
portal/
├── backend/            uv-проект: FastAPI, воркер, миграции, config/*.yaml, tests/
│   └── Dockerfile
├── frontend/           React + TypeScript + Vite, тесты
│   └── Dockerfile      сборка статики → образ portal-web
└── dev/                заглушка OpenAI-совместимого API и compose для стенда без GPU
docs/
├── portal-design.md    этот документ
├── portal-api.md       контракт API и схема БД (этап 1 пайплайна)
├── portal-ui.md        концепция интерфейса (этап 1 пайплайна)
├── vpn-launch.md       запуск до привязки домена и действия после неё
└── user-guide.md       памятка сотруднику (этап 8)
```

Слои бэкенда: домен и сценарии не зависят от FastAPI, SQLAlchemy, Qdrant и HTTP-клиента

Стенд без GPU (`portal/dev/`): заглушка отвечает на `/v1/chat/completions` (включая

интерфейса. Всё, что зависит от настоящей модели (качество ответов, распознавание
сканов, скорость), помечается «проверить на ВМ».

## 10. Критерии приёмки

Отдельного документа с критериями нет; критерии — этот список.

1. Сотрудник входит по выданным логину и временному паролю, меняет пароль, настраивает
   второй фактор и попадает в чат; следующий вход требует пароль и код. Без кода, с
   неверным или повторно использованным кодом входа нет; резервный код срабатывает один раз.
2. Администратор создаёт, блокирует пользователя, сбрасывает пароль и второй фактор;
   заблокированный теряет доступ сразу. Серия неудачных входов временно блокирует логин.
3. Чат отвечает потоково, принимает изображение и PDF, хранит историю между входами.
4. Документ, загруженный одним сотрудником в общую базу, находится в ответах другого;
   ответ содержит источник с документом, страницей и цитатой.
5. Скан без текстового слоя после загрузки в базу знаний находится поиском. **[ВМ]**
6. Личный документ и чужой чат недоступны другому пользователю и администратору
   (проверка через API).
7. SQL-помощник пишет запрос по выбранной схеме, объясняет чужой запрос, предупреждает
   об опасной операции.
8. Помощник CoGIS отвечает со ссылками на загруженную документацию.
9. Разбор документа возвращает таблицу реквизитов по шаблону. **[ВМ]** — на реальных сканах.
10. Ответ экспортируется в DOCX и открывается в Word.
11. Светлая и тёмная темы работают на всех экранах; все тексты на русском.
12. Через 443 без сессии доступны только страница входа и статика; `/v1/*` требует ключ;
    админ-API Bifrost и `/metrics` недоступны.
13. Портал работает по `https://192.168.25.8` из VPN (до домена) и по
    `https://llm.<домен>[:порт]` из интернета (после) без изменения данных и конфигурации
    портала; ответы содержат заголовки безопасности из §3.2. **[ВМ]**
14. `make check` зелёный: линтеры, типы, тесты бэкенда и фронтенда, `docker compose config`.

## 11. Риски и открытые вопросы

| Риск / вопрос | Митигация |
|---|---|
| Сертификат на IP за docker-сетью: клиент без SNI | `default_sni` (§3.1); запасной вариант — имя через `hosts` |
| Bifrost может отбрасывать нестандартные поля и менять поток SSE | Портал использует только стандартные поля (`reasoning_effort`); проверка на ВМ |
| Bifrost хранит содержимое запросов | §8; решить до запуска сотрудников |
| Нет документации CoGIS SDK в базе знаний | Запросить у заказчика; до этого помощник предупреждает об ограничении |
| Распознавание сканов конкурирует с чатом за GPU | Ограничение параллельности воркера; метрики очереди vLLM |
| Память ВМ: +PostgreSQL, Qdrant, бэкенд (~4–8 ГБ RAM) | Характеристики ВМ уточнить (`design.md` §13) |
| Лицензия шрифта Lab Grotesque | Проверить; иначе свободный шрифт |
| Страница входа и `/v1` открыты интернету | Обязательный TOTP, ограничение перебора, заголовки безопасности, ревью `security-reviewer` до проброса порта (§3.2, §4) |
| Роутер может скрывать адрес клиента при пробросе | Ограничение по логину не зависит от адреса; проверить на ВМ |
| Сотрудник потерял телефон с аутентификатором | Резервные коды; сброс второго фактора администратором |
| Из офисной сети заказчика внешний адрес может не открываться (нет hairpin NAT) | Запись во внутреннем DNS на `192.168.25.8` или настройка роутера — вопрос сисадмину |
| Внешний порт (443 или 18443) не определён | Портал от порта не зависит; в инструкциях оба варианта |
| Точные теги образов PostgreSQL и Qdrant, версии библиотек | Закрепляет исполнитель с указанием источника |
