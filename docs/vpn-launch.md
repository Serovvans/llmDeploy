# Запуск внутри VPN до привязки домена и действия после неё

Порядок развёртывания всего стека (модель → API → портал сотрудников) на ВМ
`192.168.25.8` без домена и без участия сисадмина, и что сделать, когда домен появится.
Решения — `docs/design.md` §3.4, §3.7, §3.8 и `docs/portal-design.md` §3.1.

Пометки:
- **[ВМ]** — шаг не проверялся вживую, результат подтвердить при первом запуске.
- **[после этапа N]** — команда появится после соответствующего этапа пайплайна
  разработки портала (`CLAUDE.md`); до этого шага в репозитории её нет.

Что работает уже сейчас, без доработок: часть A, шаги 1–2 и доступ по временному имени
(шаг 3, вариант Б). Доступ по IP (вариант А) требует одной строки в Caddyfile
(`default_sni`, этап 2 пайплайна). Портал (шаги 6–8) — после этапа 6.

## Часть A. До привязки домена

Схема: сотрудники в VPN открывают `https://192.168.25.8`, Caddy работает с собственным
CA (`TLS_MODE=internal`). Проброс портов с внешнего IP и DNS не нужны.

### 1. Проверить, что ВМ видна из VPN

С рабочей станции, подключённой к VPN:

```bash
ping -c 3 192.168.25.8
nc -vz 192.168.25.8 22
```

Если адрес недоступен — VPN не маршрутизирует подсеть `192.168.25.0/24`; это вопрос к
сисадмину, без него часть A выполнима только через SSH-туннель (шаг 9).

### 2. Этап 1: модель

Если ещё не сделано (`docs/runbook.md` §2.1–2.4):

```bash
cd /opt/llm
sudo make host && sudo reboot
make preflight
make model
make smoke-model
```

### 3. Этап 2: API через HTTPS

**Вариант А — по IP (основной). [после этапа 2] [ВМ]**

```bash
make gateway LLM_HOSTNAME=192.168.25.8 TLS_MODE=internal PROFILES=embeddings
```

`PROFILES` заменяет набор дополнительных профилей целиком: если мониторинг уже включён,
указывайте `PROFILES=embeddings,monitoring`. Профиль `embeddings` нужен порталу для базы
знаний.

**Вариант Б — по временному имени (работает уже сейчас).** Если сертификат на IP не
заработал или этап 2 ещё не сделан:

```bash
make gateway LLM_HOSTNAME=llm.internal TLS_MODE=internal PROFILES=embeddings
```

и на каждом тестовом ПК добавить строку в файл `hosts`
(Windows: `C:\Windows\System32\drivers\etc\hosts`, macOS/Linux: `/etc/hosts`):

```
192.168.25.8  llm.internal
```

Дальше в инструкции вместо `192.168.25.8` в адресах используйте `llm.internal`.

Проверка на ВМ:

```bash
make ps
sudo ss -ltnp | grep -E ':443|:8080|:8000'   # 443 — 0.0.0.0; 8080 и 8000 — только 127.0.0.1
sudo ufw status                              # если active: sudo ufw allow 443/tcp
```

И с рабочей станции в VPN: `nc -vz 192.168.25.8 443`.

> Сразу после этого шага сохраните копию `BIFROST_ENCRYPTION_KEY` из `deploy/.env` вне
> ВМ (`docs/runbook.md` §2.6).

### 4. Корневой сертификат на тестовых ПК

`make gateway` выгружает корень CA Caddy в `deploy/caddy-root.crt`. Заберите его:

```bash
scp <админ>@192.168.25.8:/opt/llm/deploy/caddy-root.crt .
```

Варианты для браузера сотрудника:
- **Принять предупреждение браузера** один раз — достаточно для короткого теста, но
  приучает нажимать «всё равно перейти»; сотрудникам не рекомендуется.
- **Установить корень в хранилище пользователя** на время теста:
  - Windows: `certutil -user -addstore Root caddy-root.crt`
  - macOS: `security add-trusted-cert -r trustRoot -k ~/Library/Keychains/login.keychain-db caddy-root.crt`
  - Firefox: Настройки → Сертификаты → Импортировать (у него своё хранилище).

Ключ этого корня лежит на ВМ, поэтому доверие к нему — временная мера на период теста:
после перехода на домен корень с ПК удаляется (часть B, шаг 6). Сам файл
`caddy-root.crt` не секрет, секрет — volume `llm_caddy-data`.

### 5. Проверить API

На ВМ:

```bash
make key NAME=smoke REQUESTS=100
make smoke KEY=sk-bf-...
make keys && make revoke ID=<id>
```

С рабочей станции, из `scripts/`:

```bash
LLM_BASE_URL=https://192.168.25.8/v1 LLM_API_KEY=sk-bf-... \
  LLM_CA_CERT=../caddy-root.crt uv run smoke_test.py
```

### 6. Этап 3: портал [после этапа 6] [ВМ]

```bash
make key NAME=portal          # virtual key Bifrost для портала; значение — в PORTAL_LLM_API_KEY в deploy/.env
make portal                   # install.sh --stage portal: секреты портала, профиль portal, запуск, проверки
make portal-admin LOGIN=<логин> NAME="<ФИО>"   # первый администратор; команда выводит временный пароль
```

Точные имена целей и параметров сверить с `make help` после этапа 6 — этот раздел
обновляет `docs-writer` на этапе 8.

Проверка: `https://192.168.25.8` открывает страницу входа; `make ps` показывает
`portal-web`, `portal-api`, `portal-worker`, `portal-db`, `qdrant` в состоянии healthy.

### 7. Учётные записи

1. Войти под первым администратором, сменить временный пароль, настроить второй фактор:
   отсканировать QR-код приложением-аутентификатором (Яндекс Ключ, Google Authenticator)
   и сохранить резервные коды. Второй фактор обязателен для всех уже на этапе теста.
2. Создать вторую учётную запись администратора — для гендиректора.
3. Создать учётные записи сотрудников-тестировщиков. Временный пароль передавать
   отдельным каналом от адреса портала; при первом входе он меняется, затем сотрудник
   настраивает второй фактор.

### 8. Что проверить за время теста [ВМ]

Критерии приёмки — `docs/portal-design.md` §10. На ВМ проверяется то, что нельзя
проверить на стенде без GPU:

| Что | Как |
|---|---|
| Потоковый ответ и режимы «Быстро» / «Вдумчиво» | Задать вопрос в обоих режимах; ошибок 500 нет |
| Bifrost не ломает поток и поля запроса | То же, плюс вложение-изображение |
| Скан в базе знаний | Загрузить скан без текстового слоя, дождаться статуса «готов», спросить по содержимому |
| Источники | Ответ по базе знаний показывает документ, страницу, цитату |
| Изоляция | Личный документ одного тестировщика не находится у другого |
| Разбор документов | Реальная выписка ЕГРН и договор: таблица реквизитов сверена с оригиналом |
| Нагрузка | Индексация большого скана не делает чат заметно медленнее (`make logs SERVICE=vllm`, Grafana) |
| Эмбеддинги | Контрольный набор вопросов на `Qwen3-Embedding-0.6B` и `bge-m3` |
| Содержимое в логах Bifrost | Решить, отключать ли хранение содержимого запросов (`portal-design.md` §8) |
| Второй фактор | Вход без кода невозможен; повторный код отклоняется; резервный код работает один раз; администратор сбрасывает второй фактор |
| Блокировка перебора | Серия неверных паролей временно блокирует логин |
| Бэкап | Снять и восстановить volumes портала на тестовых данных |

### 9. Если из VPN доступен только SSH

Тестировать может только администратор, через туннель:

```bash
ssh -L 8443:127.0.0.1:443 <админ>@192.168.25.8
```

и запись `127.0.0.1  llm.internal` в `hosts` рабочей станции (вариант Б шага 3); адрес
портала — `https://llm.internal:8443`.

## Часть B. После привязки домена и проброса порта

Решение: после проброса порта портал и API доступны **из интернета по домену, без VPN**
(`docs/portal-design.md` §3.2). Базовые шаги по DNS, сертификату и запуску — в
`docs/domain-setup.md`; здесь — порядок с учётом портала. Внешний порт (`$PORT`) — 443
или 18443, решает сисадмин; при 443 порт из адресов убирается.

### 0. Условия, без которых порт не открываем

- Отчёт `security-reviewer` без блокирующих находок (этап 7 пайплайна).
- Чек-лист части A, шаг 8, пройден; у всех учётных записей настроен второй фактор,
  тестовые учётные записи со слабыми паролями удалены.
- Копии `BIFROST_ENCRYPTION_KEY` и `PORTAL_SECRET_KEY` сохранены вне ВМ.
- Настроен бэкап volumes портала.
- Решён вопрос хранения содержимого запросов в Bifrost (`docs/portal-design.md` §8).

### 1. DNS

A-запись `llm.<домен>` → `195.122.229.203` — `docs/domain-setup.md` §2.

### 2. Сертификат

Let's Encrypt по DNS-01 — `docs/domain-setup.md` §3. Проверка идёт через DNS-зону и не
зависит от проброса, поэтому сертификат можно выпустить заранее.

### 3. Переключить имя и режим TLS

Можно сделать до проброса — в VPN сервис продолжит работать, если имя резолвится во
внутренний адрес (шаг 6).

```bash
cd /opt/llm
make gateway LLM_HOSTNAME=llm.<домен> TLS_MODE=corp
make ps
```

Портал перенастраивать не нужно: он живёт на том же origin, что и API, и ни имя хоста,
ни порт в его конфигурации не участвуют. Пользователи, чаты, база знаний и настройки
второго фактора сохраняются. Сессии привязаны к старому адресу, поэтому все входят
заново.

### 4. Проброс порта

Сисадмин настраивает `195.122.229.203:$PORT → 192.168.25.8:443` (TCP). Цель — именно
443 ВМ; 8080 (админка Bifrost) и остальные порты не пробрасываются.

```bash
sudo ss -ltnp | grep -E ':443|:8080|:8000'   # 443 — 0.0.0.0; 8080 и 8000 — только 127.0.0.1
sudo ufw status                              # если active: sudo ufw allow 443/tcp
```

### 5. Проверить снаружи [ВМ]

Не из сети заказчика и без VPN (например, с мобильного интернета):

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://llm.<домен>:$PORT/                            # 200 — страница входа
curl -sS -o /dev/null -w '%{http_code}\n' https://llm.<домен>:$PORT/v1/models                   # 401 или 403
curl -sS -o /dev/null -w '%{http_code}\n' https://llm.<домен>:$PORT/api/governance/virtual-keys # 404
curl -sS -o /dev/null -w '%{http_code}\n' https://llm.<домен>:$PORT/metrics                     # 404
curl -sS -o /dev/null -w '%{http_code}\n' https://llm.<домен>:$PORT/docs                        # 404
curl -sSI https://llm.<домен>:$PORT/ | grep -i -E 'strict-transport|content-security|x-frame'   # заголовки есть
nc -vz -w 5 195.122.229.203 8080                                                                # недоступен
```

В браузере: страница входа без предупреждений о сертификате; вход с паролем и кодом;
чат и поиск по базе знаний работают; старые чаты на месте.

Адрес клиента: войти с неверным паролем с внешнего устройства и посмотреть журнал
аудита. Если вместо адреса устройства записан адрес роутера — роутер подменяет источник,
ограничение по адресу не работает (остаётся ограничение по логину); сообщить сисадмину.

Смоук-тест API с рабочей станции, из `scripts/`:

```bash
LLM_BASE_URL=https://llm.<домен>:$PORT/v1 LLM_API_KEY=sk-bf-... uv run smoke_test.py
```

### 6. Доступ из офисной сети заказчика

Обращение на собственный внешний IP изнутри сети может не работать (нет hairpin NAT).
Тогда во внутреннем DNS заводится запись `llm.<домен>` → `192.168.25.8`; при внешнем
порте 18443 этого недостаточно (внутри сервис слушает 443) — нужен hairpin NAT на
роутере. Ещё один довод в пользу внешнего порта 443.

### 7. Сообщить новый адрес

- Сотрудникам — `https://llm.<домен>[:$PORT]`, VPN для портала больше не нужен.
- Приложениям — `base_url=https://llm.<домен>[:$PORT]/v1`; ключи `sk-bf-...` прежние.
- Старый адрес `https://192.168.25.8` перестаёт работать: сертификат теперь на имя.

### 8. Убрать временное

- Удалить тестовый корень Caddy с ПК: Windows — `certutil -user -delstore Root "<имя>"`
  (точное имя — в `certmgr.msc`); macOS — «Связка ключей» → удалить сертификат; Firefox
  — Настройки → Сертификаты.
- Удалить строки `llm.internal` из файлов `hosts`, если использовался вариант Б.
- `deploy/caddy-root.crt` на ВМ больше не нужен.

### 9. После открытия

- Продление сертификата: Let's Encrypt действует 90 дней и сам не продлевается —
  `docs/domain-setup.md` §7.
- Первые дни смотреть журнал аудита портала и логи Caddy: перебор паролей и сканеры
  появятся сразу — это ожидаемо; важно, что блокировки срабатывают.
- Обновления безопасности ВМ и образов — регулярно (`docs/runbook.md` §4.2): сервис
  теперь стоит лицом к интернету.
- Потерянный телефон сотрудника: резервный код или сброс второго фактора
  администратором; уволенный сотрудник блокируется в тот же день.
