# Запуск внутри VPN до привязки домена и действия после неё

Порядок развёртывания всего стека (модель → API → портал сотрудников) на ВМ
`192.168.25.8` без домена и без участия сисадмина, и что сделать, когда домен появится.
Решения — `docs/design.md` §3.4, §3.7, §3.8 и `docs/portal-design.md` §3.1, §3.2.

Пометка **[ВМ]** — шаг не проверялся вживую, результат подтвердить при первом запуске.
Все команды документа есть в репозитории (`make help`); подробности установки, бэкапа и
эксплуатации — в `docs/runbook.md`.

## Часть A. До привязки домена

Схема: сотрудники в VPN открывают `https://192.168.25.8`, Caddy работает с собственным
CA (`TLS_MODE=internal`). Проброс портов с внешнего IP и DNS не нужны.

### 1. Проверить, что ВМ видна из VPN

С рабочей станции, подключённой к VPN:

```bash
ping -c 3 192.168.25.8
nc -vz 192.168.25.8 22
```

Если адрес недоступен — VPN не маршрутизирует подсеть `192.168.25.0/24`; это вопрос к
сисадмину, без него часть A выполнима только через SSH-туннель (шаг 9).

### 2. Этап 1: модель

Если ещё не сделано (`docs/runbook.md` §2.1–2.4):

```bash
cd /opt/llm
sudo make host && sudo reboot
make preflight
make model
make smoke-model
```

### 3. Этап 2: API через HTTPS

**Вариант А — по IP (основной). [ВМ]**

```bash
make gateway LLM_HOSTNAME=192.168.25.8 TLS_MODE=internal PROFILES=embeddings
```

`PROFILES` заменяет набор дополнительных профилей целиком: если мониторинг уже включён,
указывайте `PROFILES=embeddings,monitoring`. Профиль `embeddings` нужен порталу для базы
знаний.

**Вариант Б — по временному имени.** Если сертификат на IP не заработал (браузер или
`make gateway` сообщает об ошибке TLS):

```bash
make gateway LLM_HOSTNAME=llm.internal TLS_MODE=internal PROFILES=embeddings
```

и на каждом тестовом ПК добавить строку в файл `hosts`
(Windows: `C:\Windows\System32\drivers\etc\hosts`, macOS/Linux: `/etc/hosts`):

```
192.168.25.8  llm.internal
```

Дальше в инструкции вместо `192.168.25.8` в адресах используйте `llm.internal`.

Проверка на ВМ:

```bash
make ps
sudo ss -ltnp | grep -E ':(443|8080|18443|8000|8081) '   # 443, 8080, 18443 (Caddy) — 0.0.0.0; 8000 и 8081 — только 127.0.0.1
sudo ufw status                              # если active: sudo ufw allow 443/tcp
```

И с рабочей станции в VPN: `nc -vz 192.168.25.8 443`.

> Сразу после этого шага сохраните копию `BIFROST_ENCRYPTION_KEY` из `deploy/.env` вне
> ВМ (`docs/runbook.md` §2.6).

### 4. Корневой сертификат на тестовых ПК

`make gateway` выгружает корень CA Caddy в `deploy/caddy-root.crt`. Заберите его:

```bash
scp <админ>@192.168.25.8:/opt/llm/deploy/caddy-root.crt .
```

Варианты для браузера сотрудника:
- **Принять предупреждение браузера** один раз — достаточно для короткого теста, но
  приучает нажимать «всё равно перейти»; сотрудникам не рекомендуется.
- **Установить корень в хранилище пользователя** на время теста:
  - Windows: `certutil -user -addstore Root caddy-root.crt`
  - macOS: `security add-trusted-cert -r trustRoot -k ~/Library/Keychains/login.keychain-db caddy-root.crt`
  - Firefox: Настройки → Сертификаты → Импортировать (у него своё хранилище).

Ключ этого корня лежит на ВМ, поэтому доверие к нему — временная мера на период теста:
после перехода на домен корень с ПК удаляется (часть B, шаг 6). Сам файл
`caddy-root.crt` не секрет, секрет — volume `llm_caddy-data`.

### 5. Проверить API

На ВМ:

```bash
make key NAME=smoke REQUESTS=100
make smoke KEY=sk-bf-...
make keys && make revoke ID=<id>
```

С рабочей станции, из `scripts/`:

```bash
LLM_BASE_URL=https://192.168.25.8/v1 LLM_API_KEY=sk-bf-... \
  LLM_CA_CERT=../caddy-root.crt uv run smoke_test.py
```

### 6. Этап 3: портал [ВМ]

```bash
make key NAME=portal          # virtual key Bifrost для портала; значение sk-bf-... показывается один раз
sudoedit deploy/.env          # вписать его в PORTAL_LLM_API_KEY=
make portal                   # install.sh --stage portal: профиль portal, SITE_MODE=portal, сборка образов, запуск, проверки
make portal-admin LOGIN=<логин> NAME="<ФИО>"   # первый администратор; команда один раз выводит временный пароль
make smoke-portal             # что отдаёт сайт через 443 и здоровы ли сервисы
```

Если на шаге 3 профиль `embeddings` не включали: `make portal PROFILES=embeddings`
(с мониторингом — `PROFILES=embeddings,monitoring`). Что делает установка и что она
проверяет — `docs/runbook.md` §2.9.

Проверка: `https://192.168.25.8` открывает страницу входа; `make ps` показывает
`portal-web`, `portal-api`, `portal-worker`, `portal-db`, `qdrant` в состоянии healthy.

> Сразу после этого шага сохраните копию `PORTAL_SECRET_KEY` из `deploy/.env` вне ВМ,
> вместе с `BIFROST_ENCRYPTION_KEY`, и снимите первую резервную копию:
> `make backup DIR=<каталог вне репозитория>` (`docs/runbook.md` §4.4).

### 7. Учётные записи

1. Войти под первым администратором, сменить временный пароль, настроить второй фактор:
   отсканировать QR-код приложением-аутентификатором (Яндекс Ключ, Google Authenticator)
   и сохранить резервные коды. Второй фактор обязателен для всех уже на этапе теста.
2. Создать вторую учётную запись администратора — для гендиректора: раздел
   «Пользователи» → «Добавить пользователя», роль «Администратор».
3. Создать учётные записи сотрудников-тестировщиков. Временный пароль передавать
   отдельным каналом от адреса портала; при первом входе он меняется, затем сотрудник
   настраивает второй фактор. Сотрудникам выдать памятку `docs/user-guide.md`.

### 8. Чек-лист проверки на ВМ [ВМ]

Критерии приёмки — `docs/portal-design.md` §10. Здесь то, что нельзя проверить на
стенде без GPU; на стенде остальное закрыто сквозными тестами. Формат пункта: действие →
ожидаемый результат. Тексты в кавычках — как в интерфейсе.

### 9. Если из VPN доступен только SSH

Тестировать может только администратор, через туннель:

```bash
ssh -L 8443:127.0.0.1:443 <админ>@192.168.25.8
```

и запись `127.0.0.1  llm.internal` в `hosts` рабочей станции (вариант Б шага 3); адрес
портала — `https://llm.internal:8443`.

## Часть B. После привязки домена и проброса порта

Решение: после проброса порта портал и API доступны **из интернета по домену, без VPN**
(`docs/portal-design.md` §3.2). Схема окончательная: проброс TCP
`195.122.229.203:18443 → 192.168.25.8:8080`, адрес сервиса — `https://llm.<домен>:18443`.
DNS, выпуск сертификата, запуск и проверка портов — пошагово в `docs/domain-setup.md`;
здесь — что проверить перед открытием доступа сотрудникам и после.

### 0. Условия, без которых порт не открываем

- Отчёт `security-reviewer` без блокирующих находок (этап 7 пайплайна).
- Чек-лист части A, шаг 8, пройден. В том числе через настоящий Caddy проверены
  заголовки безопасности (п. 4), открытие оригинала PDF в браузере (п. 29) и поток
  ответа при включённом сжатии (п. 7–8).
- У всех учётных записей настроен второй фактор: в разделе «Пользователи» в столбце
  «Второй фактор» у всех «Настроен».
- Тестовые учётные записи убраны. Удаления учётных записей в портале нет: тестовые
  записи блокируются («Заблокировать») либо им сбрасывается пароль.
- Копии `BIFROST_ENCRYPTION_KEY` и `PORTAL_SECRET_KEY` сохранены вне ВМ.
- Резервная копия снимается и восстанавливается (п. 41–44г); копии хранятся вне ВМ как
  секрет (`docs/runbook.md` §4.4).
- В журнале Bifrost нет текста сообщений и вложений (п. 45, 45а).
- Адрес клиента в журнале аудита — настоящий (п. 35); у сисадмина выяснено, подменяет ли
  роутер адрес источника при пробросе. Если подменяет — до проброса выполнить шаг 5.1.

### 1–4. DNS, сертификат, запуск, проброс

`docs/domain-setup.md`, шаги 1–5: A-запись, `make cert`,
`make gateway LLM_HOSTNAME=llm.<домен> TLS_MODE=corp`, проверка портов, проброс.

Сертификат выпускается через DNS и от проброса не зависит, поэтому шаги 1–4 можно
сделать заранее. Портал перенастраивать не нужно: он живёт на том же origin, что и API,
и ни имя хоста, ни порт в его конфигурации не участвуют. Пользователи, чаты, база знаний
и настройки второго фактора сохраняются. Сессии привязаны к старому адресу, поэтому все
входят заново.

Пробрасывается только `18443 → 8080` (Caddy). Админ-порт Bifrost (`127.0.0.1:8081`),
vLLM (`127.0.0.1:8000`) и остальные порты не пробрасываются.

### 5. Проверить снаружи [ВМ]

Не из сети заказчика и без VPN (например, с мобильного интернета). Базовые проверки и
смоук-тесты — `docs/domain-setup.md`, шаг 6; дополнительно:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://llm.<домен>:18443/api/governance/virtual-keys # 404
curl -sS -o /dev/null -w '%{http_code}\n' https://llm.<домен>:18443/metrics                     # 404
curl -sS -o /dev/null -w '%{http_code}\n' https://llm.<домен>:18443/docs                        # 404
curl -sSI https://llm.<домен>:18443/ | grep -i -E 'strict-transport|content-security|x-frame'   # заголовки есть
curl -sS -o /dev/null -w '%{http_code}\n' -X POST https://llm.<домен>:18443/v1/async/chat/completions # 404
curl -sS -o /dev/null -w '%{http_code}\n' https://llm.<домен>:18443/v1/skills                   # 404
curl -sSI https://llm.<домен>:18443/ | grep -i alt-svc                                          # пусто
nc -vz -w 5 195.122.229.203 443                                                                 # недоступен
nc -vz -w 5 195.122.229.203 8081                                                                # недоступен
```

Снаружи открыт только 18443; из `/v1` доступны только `/v1/chat/completions`,
`/v1/completions`, `/v1/embeddings` и `/v1/models`.

В браузере: страница входа без предупреждений о сертификате; вход с паролем и кодом;
чат и поиск по базе знаний работают; старые чаты на месте.

#### 5.1 Адрес клиента — обязательная проверка

Выполняется сразу после проброса, до того как адрес сообщён сотрудникам (шаг 7).

1. С внешнего устройства (не из сети заказчика, без VPN) один раз войти с неверным
   паролем.
2. На ВМ: `make portal-audit EVENT=login_failed LIMIT=5` — в поле адреса должен быть
   внешний адрес этого устройства.
3. Повторить из офисной сети заказчика (шаг 6): адрес — внутренний адрес этого ПК, он
   не должен совпадать с адресом из п. 2 и с адресом роутера.

Если у разных клиентов в журнале один и тот же адрес (роутер подменяет источник при
пробросе — SNAT), ограничение по адресу работает
против своих: 20 неверных попыток входа от кого угодно за 5 минут закрывают вход и ввод
кода второго фактора **всем**, кто виден под этим адресом, до конца этих 5 минут.
Сотрудники видят «Слишком много попыток входа. Попробуйте снова через …». Варианты:

- исправить NAT у сисадмина, чтобы до ВМ доходил настоящий адрес клиента (основной);
- если исправить нельзя — поднять `auth.ip_limit.max_failures` накладкой конфигурации
  (`docs/runbook.md` §3.6) до значения, которого перебор с одного адреса не достигнет
  случайно, и перезапустить `portal-api`:

  ```yaml
  # deploy/portal/config.override.yaml
  auth:
    ip_limit:
      max_failures: <число>
  ```

  ```bash
  sudo docker compose -f deploy/docker-compose.yml restart portal-api portal-worker
  ```

Ограничение по логину (5 неудач подряд — блокировка логина с нарастающим сроком) от
адреса не зависит и остаётся в силе при любом варианте.

#### 5.2 Известное свойство: блокировка логина

Зная логин сотрудника, посторонний может держать его вход закрытым, вводя неверные
пароли: это цена защиты от подбора. Признак — записи `login_failed` с `lock_seconds` в
`make portal-audit EVENT=login_failed` с чужих адресов. Что делает администратор:

- в разделе «Пользователи» у строки сотрудника — пометка «Вход временно заблокирован
  до …, после неудачных попыток»; в меню строки — «Снять блокировку входа». Пароль и
  второй фактор остаются прежними, сотрудник сразу входит;
- свою блокировку администратор в интерфейсе снять не может: это делает другой
  администратор или `make portal-unlock-login LOGIN=<логин>` на ВМ;
- ограничение по адресу (шаг 5.1) этим не снимается;
- против настойчивого автоматического перебора снятие не помогает — счётчик начинается
  с нуля, блокировка наступит снова. Тогда адрес источника закрывают на роутере
  (сисадмин).

### 6. Доступ из офисной сети заказчика и из VPN

Во внутреннем DNS заводится запись `llm.<домен>` → `192.168.25.8`: ВМ сама слушает
18443, поэтому тот же адрес `https://llm.<домен>:18443` работает изнутри без hairpin NAT
— `docs/domain-setup.md`, шаг 7.

### 7. Сообщить новый адрес

- Сотрудникам — `https://llm.<домен>:18443`, VPN для портала больше не нужен.
- Приложениям — `base_url=https://llm.<домен>:18443/v1`; ключи `sk-bf-...` прежние.
- Старый адрес `https://192.168.25.8` перестаёт работать: сертификат теперь на имя.

### 8. Убрать временное

- Удалить тестовый корень Caddy с ПК: Windows — `certutil -user -delstore Root "<имя>"`
  (точное имя — в `certmgr.msc`); macOS — «Связка ключей» → удалить сертификат; Firefox
  — Настройки → Сертификаты.
- Удалить строки `llm.internal` из файлов `hosts`, если использовался вариант Б.
- `deploy/caddy-root.crt` на ВМ больше не нужен.

### 9. После открытия

- Продление сертификата: Let's Encrypt действует 90 дней, продлевает таймер
  `llm-cert-renew.timer`; проверять `systemctl list-timers llm-cert-renew.timer` и
  журнал — `docs/domain-setup.md`, шаг 8.
- Первые дни смотреть журнал аудита портала (`make portal-audit`) и логи Caddy
  (`make logs SERVICE=caddy`): перебор паролей и сканеры появятся сразу — это ожидаемо;
  важно, что блокировки срабатывают.
- Обновления безопасности ВМ и образов — регулярно (`docs/runbook.md` §4.2): сервис
  теперь стоит лицом к интернету.
- Потерянный телефон сотрудника: резервный код или сброс второго фактора
  администратором («Сбросить второй фактор» или `make portal-reset-2fa LOGIN=<логин>`);
  уволенный сотрудник блокируется в тот же день («Заблокировать»).
- Обновление кода: `git pull` и повтор текущего этапа установки — `make portal`
  (`docs/runbook.md` §4.2).
