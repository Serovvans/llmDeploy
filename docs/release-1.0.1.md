# Релиз 1.0.1: «Все схемы» у подключения к базе заказчика — раскатка на работающий 1.0

Пояснения — `runbook.md` §3.6, §3.12. Всё — **[ВМ]**: на ВМ не выполнялось. Команды от `root`,
в `tmux`. Команда с ошибкой — стоп, дальше не идти. В релизе: у подключения к базе заказчика
вместо списка схем можно выбрать «Все схемы» — в схему попадают таблицы всех схем, которые
разрешено читать учётной записи, кроме служебных схем PostgreSQL и таблиц расширений (PostGIS);
границу задают только права учётной записи. Предел схемы увеличен до 3000 таблиц и 60 000 столбцов;
если база больше, в интерфейсе — «N таблиц — не все». Подключения со списком схем работают как в 1.0.

```bash
export LIVE=/root/LLM/llmDeploy               # рабочий клон: из него запущен сервис
export REL=/root/LLM/llmRelease               # релизный клон: создаётся на шаге 1
export BAK=/var/lib/docker/portal-backups     # копии: не на диске /
grep -E '^(COMPOSE_PROFILES|GPU_MEM_UTIL)=' "$LIVE/deploy/.env"   # значения для шага 2
```

Ниже `PROFILES=embeddings,rerank GPU_MEM_UTIL=0.81` — замените на значения из `.env`
(профиль `portal` не указывать).

Новых переменных `.env`, ключей конфигурации, сервисов и внешних файлов нет; флаг `db.enabled` и
накладка `deploy/portal/config.override.yaml` не меняются. Пределы схемы (`db.snapshot_max_tables`
3000, `db.snapshot_max_columns` 60000) приходят с образом из `db.yaml`. Миграция `0012_db_v101`
только добавляет поле `all_schemas` (по умолчанию «нет»): прежние подключения остаются со списком
схем. Пересобираются образы `portal-api` и `portal-web`.

## Перед началом

- Работает 1.0: `cd "$LIVE" && make ps && git log -1 --oneline` — все сервисы healthy.
- Владелец слил `feat/db-all-schemas-1.0.1` в `main` и отправил: `git -C "$LIVE" fetch && git -C "$LIVE" log -1 --oneline origin/main` — коммит релиза 1.0.1 (далее `<релиз>`). `git -C "$LIVE" status --short` — пусто.
- Релизного клона нет: `ls "$REL"` — «нет такого файла». Есть (от прошлой раскатки) — убедиться, что своего в нём нет (`git -C "$REL" status --short` пусто, `deploy/.env` нет), и `rm -rf "$REL"`.
- Место: `df -h /var/lib/docker "$BAK"` — разные устройства.
- Подключения включены по `release-1.0.md` (`db.enabled: true`) и есть хотя бы одно рабочее; иначе шаги 8–10 отложить до их включения.
- Окно — в часы с малой нагрузкой.

## Подготовка (сервис работает)

1. Релизный клон: `git clone "$(git -C "$LIVE" remote get-url origin)" "$REL" && cd "$REL" && git checkout <релиз>` — `ls "$REL/deploy/.env"` сообщает «нет файла».
2. `cd "$REL" && make release-prepare LIVE="$LIVE" PROFILES=embeddings,rerank GPU_MEM_UTIL=0.81` — собраны образы, в конце напечатаны команды окна и отката; вывод сохранить, записать `<прежний коммит>`. Ошибка сборки — стоп: повторить после восстановления доступа к PyPI и npm.
3. `cd "$REL" && make release-rehearse LIVE="$LIVE"` — строка «репетиция миграций прошла за N с» (применяется 0012 на копии рабочей базы). Иначе — стоп.

## Бэкап (начало окна; сообщить сотрудникам о перерыве)

4. `cd "$REL" && make release-backup LIVE="$LIVE" DIR="$BAK"` — «Копия готова: <путь>», в `ls "$BAK"` нет `.partial`. Путь записать: это единственный путь отката кода после миграции.

## Обновление

5. `cd "$LIVE" && git checkout <релиз>` — `git log -1 --oneline` показывает `<релиз>`.
6. `cd "$LIVE" && make portal PROFILES=embeddings,rerank GPU_MEM_UTIL=0.81` — завершилась без ошибки (миграция `0012` применяется при старте `portal-api`). Ошибка — «Откат».

## Проверка

7. `cd "$LIVE" && make ps && make smoke-portal` — всё healthy, `ИТОГ: PASS`. Иначе — «Откат».
8. Критерий 46 **[ВМ]**, часть 1 (администратор портала): «Управление» → «Базы данных» → «Изменить» у рабочего подключения → «Схемы базы» → «Все схемы» → «Сохранить и проверить». Ожидание: в блоке «Проверка» — «Подключение работает, лишних прав нет». «Лишние права» — подключение «Временно не используется»: передать список администратору базы, до исправления вернуть «Только перечисленные» и список схем; остальные шаги не выполнять.
9. Критерий 46, часть 2: в меню строки подключения «Обновить схему». Ожидание: «Схема обновлена: N таблиц», в списке подключений под адресом — «все схемы». Написано «— не все» — таблиц в базе больше предела: администратору базы сузить права учётной записи до нужных схем и повторить.
10. Критерий 46, часть 3: «SQL-помощник» → «Схема базы» → это подключение. Ожидание: таблицы сгруппированы по схемам, `public` первой, затем по алфавиту; ожидаемые схемы есть, служебных (`pg_catalog`, `information_schema`) и таблиц PostGIS (`spatial_ref_sys`) нет. Служебные в списке — «Откат», сообщить разработчику.

Всё прошло — релиз принят. Иначе — «Откат».

## Откат

1. Откат кода. У миграции `0012` нет обратного хода: код откатывается только с восстановлением копии шага 4 (`portal-design.md` §8.5); она же возвращает подключения к состоянию до миграции, переключать их отдельно не нужно. Созданное после копии теряется.

   ```bash
   docker ps -a --filter name=portal-api --format '{{.Image}}'   # тег = 12 символов <релиз> — новый
   cd "$LIVE" && git checkout <прежний коммит>
   cd "$REL" && make release-rollback LIVE="$LIVE" FROM=<путь копии шага 4>   # ввести yes
   cd "$LIVE" && make ps && make smoke-portal                    # healthy, смоук прошёл
   ```

   Если образ `portal-api` прежний (новый не стартовал) — без копии:
   `cd "$LIVE" && git checkout <прежний коммит> && cd "$REL" && make release-rollback LIVE="$LIVE"`.
   Сбой шага 6 до записи `.env`: `cd "$LIVE" && git checkout <прежний коммит> && make up`.
   Сбой до шага 5 — ничего не откатывать.
2. Только отказ от режима (код остаётся): у каждого подключения «Изменить» → «Схемы базы» → «Только перечисленные» → схемы → «Сохранить и проверить».
